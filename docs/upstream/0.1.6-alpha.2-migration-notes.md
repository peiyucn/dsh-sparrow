## ★ 核心结论：**插件不会导致用户升级后无法启动 dsh**（2026-09-18 专项核验）

> 本节回答 owner 的收窄目标——「只要保证 dsh 升级的用户不会因我们的插件导致无法启动 dsh」。
> 结论：**不会**。已逐环核验三重保障，且**无需改代码**。

### 保障一：模块顶层静态导入全部有效（无链接期失败面）

插件对官方包的**值导入**（非 `import type`）只可能是链接期失败点——它在模块加载阶段发生，
不在 `apply` 的异常保护范围内（根 AGENTS《扩展与宿主兼容》）。逐一核验六活跃插件 + 已退役插件的
全部顶层值导入，**alpha.2 里全部存在**：

| 插件 | 顶层值导入（官方包） | alpha.2 核验 |
| :--- | :--- | :--- |
| archive-manage | `dsh-session`: `SessionId` / `SessionSeq` / `SessionHeader`（+ `import * as`）；`dsh-workspace`: `WorkspaceId` | ✅ 全在（`dsh-session` 经 `export * from './types.ts'` 通配导出） |
| chat-fim | `dsh-credentials`: `credentialRef`；`dsh-session`: `SessionId`；`ui-primitives`: 3 个图标/钩子 | ✅ |
| codebuddy-credits | `dsh-llm`: `LlmAdapter` / `LlmError` / `assertUsableApiKey`；`dsh-credentials`: `credentialRef`；`dsh-launch-environment`: `launchEnvironmentOf`；`schemastery` 默认导出；`ui-primitives` 2 个钩子 | ✅ |
| file-manage | `dsh-credentials`: `credentialRef`；`dsh-llm`: `LlmError`；`ui-primitives`: 2 个图标 | ✅ |
| nav-pin | （无官方值导入；纯 CSS 注入） | ✅ 天然免疫 |
| theme-tone | `dsh-client-store`: `defineStore` / `EngineStoreHandle`；`schemastery` 默认导出 | ✅ |
| vision-bridge（已退役） | `dsh-llm`: `createUserMessage` / `ReasoningEffortId`；`dsh-tools`: `defineTool` | ✅ |

> 图标类导出（`IconArchiveOutline20` 等 5 个）最初在 `index.ts` 里查不到而被标 MISS，
> 复核后确认它们在 `ui-primitives/src/icons/index.tsx` 定义并**经通配导出**（两版行号基本一致）
> → **不是缺项**。

### 保障二：宿主非白名单 entry 失败一律只告警

* `packages/boot/app-boot/src/index.ts:875-884` `auditStartupEntries()`：
  收集全部 inactive/failed entry 后，**只有 `requiredStartupEntryIds` 内的才 `throw StartupError`**，
  其余 `warn(...)` 后继续。
* `requiredStartupEntryIds` 只有 7 项：`agent-loop` / `webserver` / `modules` / `connection` /
  `headless-runner` / `acp` / `sdk-jsonrpc-server`。
  **我方 7 个 entry id（`dsh-archive-manage`、`dsh-chat-fim`、`dsh-file-manage`、`dsh-nav-pin`、
  `llm-codebuddy-credits`、`dsh-theme-tone`、`dsh-vision-bridge`）无一在其中。**
* `inactiveEntries()` 的收集口径覆盖全部失败形态：`disabled` 表达式抛错、
  **`fiber === undefined` → 'failed to import'**、`FIBER_FAILED`（= `apply` 抛错，正是我方插件自停用的形态）、
  `FIBER_PENDING`（服务等待）。

### 保障三：加载器连链接期错误都兜住

`vendor/loader/src/config/entry.ts:175-184` 的 `_init()`：

```ts
private async _init() {
  let exports: any
  try {
    exports = await this.parent.tree.import(this.options.name, this.getOuterStack)
  } catch (error) {
    this.ctx.logger.error(error)
    return                      // ← 不抛，只记日志
  }
  ...
}
```

即**即便将来某个官方包改名/删导出导致模块顶层导入失败，也只让该 entry 不激活**，
不会中断加载器遍历、不会阻止其余 entry（含 required 的那 7 项）启动。

### 综合判定

| 最坏情形 | 实际后果 | 是否阻断 dsh 启动 |
| :--- | :--- | :--- |
| 某插件 `apply` 抛错（兼容门不通过） | 该插件 inactive + 一条告警 | **否** |
| 某插件模块顶层导入失败（链接期） | 该 entry 记 error 日志、不激活 | **否** |
| 插件依赖的服务缺失 | 该 fiber PENDING + 告警 | **否** |
| HMR 因缺原生插件自停用（官方自身问题） | HMR 不可用 + 告警 | **否**（`hmr` 不在白名单） |

→ **满足 owner 的收窄目标，且不需要为 alpha.2 做任何改动。**
唯一的用户可见损失是 **nav-pin 在 alpha.2 上宽度钳制失效**（观感回退，不崩、不影响启动），
按 owner 口径留到 rc 线正式适配时一起修。

## HMR 默认开启 × `--expose-internals`（**已重新定级：不阻断启动**）

> **本节结论经二次核验后下调**（2026-09-18）。初判曾写「唯一可能升级即打不开的路径」，
> 后来读到宿主启动审计的源码，证明该失败**只会让 HMR 这一个 entry 自停用并告警，宿主照常启动**。
> 原始事实链保留在下面（仍然准确），但**风险定级以「判定」一节为准**。

### 事实链（逐环已核）

1. alpha.2 `packages/bundle/base/cordis.patch.yml` 把 hmr 行改成默认启用：

   ```yaml
   - id: hmr
     name: '@deepseek-ai/dsh-hmr'          # alpha.1: @deepseek-ai/cordis-plugin-hmr
     disabled: !!js "!ctx.get('profileContext')"   # alpha.1: true
     config:
       root: []                             # alpha.1: ['.']
   ```

   即：**任何通过 `dsh <profile>` 启动、带 `profileContext` 的运行（含 launcher 的 `dsh web`）现在都会装载 HMR 服务**。

2. `packages/boot/hmr/src/index.ts:181-183` 的构造函数：

   ```ts
   if (!this.ctx.loader.internal) throw new Error('--expose-internals is required for HMR service')
   ```

3. `vendor/loader/src/internal.ts:108-118` 解析内部 loader 有**两条路**：
   先试 `process.execArgv.includes('--expose-internals')` → `require(id)`；
   失败后回退 `require('node-addon-require-builtin').requireBuiltin(id)`。

4. 全程 grep a2 全树：`--expose-internals` **只出现在 desktop 相关**（`apps/desktop/src/host-process.ts:116`、
   `apps/desktop/scripts/prepare-dsh.ts:75`、`apps/desktop-host/src/index.ts:28`）与测试。
   **CLI 非 desktop 路径从不传** → 非 desktop 完全依赖回退 2 的原生插件。

5. `vendor/loader/package.json` 把 `node-addon-require-builtin: ^0.1.6` 声明为
   **optional peer**（`peerDependenciesMeta.optional: true`），`packages/boot/app-boot/package.json`
   则把它列为**正式 dependency `^0.1.6`**。

6. 本机现状：`~/.dsh-launcher-panel/package` 里装的是 `node-addon-require-builtin@0.1.5`
   （对应宿主 0.1.5-rc.2）。npm 上 `0.1.6` **已发布**。

### 判定（**不阻断启动**）

关键在于宿主的启动审计只对**白名单内**的 entry 硬失败：

* `packages/boot/app-boot/src/index.ts:875-884` `auditStartupEntries()`：
  先收集全部 inactive/failed entry，**只有落在 `requiredStartupEntryIds` 里的才 `throw StartupError`**，
  其余一律走 `warn(...)`。
* `requiredStartupEntryIds`（同文件）只有 7 项：
  `agent-loop` / `webserver` / `modules` / `connection` / `headless-runner` / `acp` / `sdk-jsonrpc-server`。
  **`hmr` 不在其中**（base bundle 里的 id 就是 `hmr`，`cordis.patch.yml:28`）。
* `inactiveEntries()`（同文件）把任何 entry 的失败都收进 failures：
  `disabled` 表达式抛错、**`fiber === undefined` → 'failed to import'**、
  `FIBER_FAILED`（await 后取到 rejection，正是服务构造函数抛错的形态）、`FIBER_PENDING`。
  → HMR 构造函数抛错 = 该 entry `FIBER_FAILED` = 归入 **optional** → 只告警。
* 另有一层保险：`vendor/loader/src/config/entry.ts:175-184` 的 `_init()` 把
  `tree.import(...)` 包在 try/catch 里，**模块顶层导入失败（链接期错误）也只 `logger.error` 后 return**，
  连抛都不抛。

所以两件事同时成立：

* **不阻断 dsh 启动**——最坏结果是「HMR 这一个功能不可用 + 启动日志多一条告警」，
  dsh 本体、其余插件、launcher 打开 Web UI 全部照常。
* **但我方插件在 alpha.2 上会失去热重载**（若原生插件缺失）——这只影响开发体验，
  不影响用户使用；且它**不是我方的问题**（官方自身的可选依赖）。

**仍需实测**（但已不是「能不能启动」的问题）：确认 launcher 管理的 pnpm 安装是否带上
`node-addon-require-builtin@^0.1.6` + 平台二进制。带上了 → HMR 正常；没带上 → HMR 自停用 + 告警。
两种结果都不阻断启动。

> 注意与《扩展与宿主兼容》的关系：这是**宿主自身**的功能降级（HMR 不可用），不是插件造成的。
> 它**不会**阻断启动——宿主审计把它归入 optional（`hmr` 不在 required 白名单），
> 见上面《★ 核心结论 · 保障二》。初判曾以为这里需要「升级前的实测拦截」，现已更正：
> 无需拦截，实测只为确认 HMR 是否可用。

## profile 写入通道：我方「profile patch 保持 `[]`」约定被宿主打破

* alpha.1 事实（仍然成立）：我方约定 **profile 级 `cordis.patch.yml` 保持 `[]`**，
  插件经各插件 `package.json` 的 `dsh.profile.bundles` 装载；往 profile 级 patch 写 insert
  会与 bundle 层重复 → `duplicate loader entry id` 启动失败。
* alpha.2 新增：`packages/boot/plugin-manager` 提供 service `pluginManager`
  （`super(ctx, 'pluginManager')`），其 `writePluginEnabled` 会**注释保留式地改写**
  用户 profile 的 `cordis.patch.yml`（匹配不到 `{id, name}` 行就追加 `{id, disabled}`，
  否则翻转**最后一条**匹配行的 `disabled`）；`saveManifest` 则原子写 `<profile>/package.json`。
  触发点是**用户在插件管理页显式操作**安装/启停/卸载。
* 影响判定：
  * `duplicate loader entry id` 检查本身是**运行时**检查（built loader），
    alpha.1/alpha.2 该语义**未变**。
  * 但 profile patch 现在**有了一条宿主写入通道**——我方 README/spec 里若写了
    「本插件不改写 profile patch」之类断言需复核措辞：**我方不改写**仍然为真，
    而**宿主会改写**是新增事实。
  * HMR 现在监听 profile `cordis.patch.yml`、home `cordis.patch.yml`、profile `package.json`
    三处（`packages/boot/hmr/src/index.ts:214-236`）→ 上述写入会**实时触发重载**。
* **不确定**：插件管理页对「经 `dsh.profile.bundles` 装载、且自身带 `cordis.patch.yml`」的插件
  （正是我方形态）会写出什么形态的行，源码上未走到底；属实测项。

## 单向门：alpha.2 新增必读事件 `workspace/changes`（**门加深**）

alpha.1 笔记已论证「source(0.1.6) 写过的会话，切回 pkg(0.1.5-rc.2) 会直接报错」，
触发条件是较罕见的 `image/offload`。alpha.2 把触发条件变得**常见得多**：

* `packages/core/session/src/known-event-types.ts` 的 `KNOWN_SESSION_EVENT_TYPES`
  从 **57 项增至 58 项**，新增的正是 `'workspace/changes'`（`git diff` 确认，删除 0 项）。
* 写入方：`packages/deliverables/workspace-changes/src/recorder.ts:354`
  `this.session.append('workspace/changes', { turn: state.turn })` —— 即**每轮有文件改动就写一条**。
* `append()`（`packages/core/session/src/index.ts:719-747`）只组装 `type/seq/time/data` +
  可选 surface 元数据，**不自动打 `ignorable`**（`ignorable` 必须 writer 显式写，本处未写）。
* 读侧门：`packages/session/session-persistence/src/storage-contract.ts:75`
  `if (!KNOWN_SESSION_EVENT_TYPES.has(event.type) && event.ignorable !== true) throw`
  → 抛 `SessionFormatUnsupportedError`，**拒绝整个日志**（「refusing to interpret the log」）。
* 0.1.5-rc.2 的已知集合里**没有** `workspace/changes`（全树 0 命中）。

→ **结论：只要在 0.1.6-alpha.2 下跑过一个「有文件改动」的回合，该会话切回 0.1.5-rc.2 就打不开。**
比 alpha.1 的 `image/offload`（需图片配额触发）触发频率高一个量级。

* 这是官方**设计如此**（宁可拒绝也不误读），不是 bug；但它把一个「边界单向门」变成了「几乎必然的单向门」。
* 反向（pkg 写 → source 读）仍安全，0.1.6 认识 0.1.5 的全部词汇。
* `SESSION_FORMAT_VERSION` 两版**都是 3**（常量未变），所以**格式门（`assertHostCompatible`）拦不住这件事**——
  它拦的是常量版本，不是事件词汇表。若要在插件侧显式防，只能进一步校验事件类型集合，而官方未导出该集合的公开 seam。

### ⚠️ 单向门的真实后果比「打不开」更精确（2026-09-18 补充核验）

owner 问「source 升级后会不会影响 pkg 模式启动」。把读路径逐环核清后，后果面比初判**更窄也更准**：

* **不会让 pkg 模式起不来。** 会话**列表**读取只读 header、不校验事件：
  `session-persistence-jsonl/src/index.ts:461-491` 的 `list()` 只组装
  `{ header, revision, sizeBytes }`（`artifact.header`），**不调用 `validateStoredEvents`**。
  → 0.1.6 写过的会话在 0.1.5-rc.2 里**照常出现在侧栏**，启动与列表都不受影响。
* **只有「打开该会话」时才拒绝。** `validateStoredEvents` 的调用点在
  `session-persistence-jsonl/src/index.ts:627`（prepare/generation 路径，即打开/读取会话体时）
  与 `:525`（generation 校验），不在 list 路径上。
  → 实际症状是「**某个具体会话点开报格式不支持**」，不是「dsh 打不开」。
* 拒绝是**整个日志级**（`storage-contract.ts:75` 抛 `SessionFormatUnsupportedError`），
  所以那个会话在旧版本下**无法降级读取**——只能在新版继续用，或从备份恢复。

→ 对 owner 决策的意义：升级 source 试跑的风险是「**部分会话在 pkg 模式下不可读**」，
而非「pkg 模式不可用」。**备份 `~/.dsh/sessions` 仍然必要**（保证可回退到升级前状态），
但不必担心把 pkg 模式弄瘫。

## source 升级会不会影响 pkg 模式启动？（2026-09-18 专项核验）

owner 问：「现在报 src 模式下的 dsh 升个级，会影响咱们 pkg 模式启动么？」

### 结论：**不会影响 pkg 模式的启动能力**；唯一风险是「部分会话在旧版不可读」

### 前提事实（本机实测）

| 面 | 事实 |
| :--- | :--- |
| pkg 安装目录 | `~/.dsh-launcher-panel/package`（`managedPackageDir()`，`server.ts:570-572`） |
| source checkout | `~/.dsh-launcher-panel/source`（`managedSourceCheckout()`，`:575-577`），当前 `git describe` = **`dsh-v0.1.5-rc.2`** |
| 两者关系 | **完全独立的两个目录**，`managedPackageDir` 与 `managedSourceCheckout` 无重叠 |
| `DSH_HOME` | **两者共用** `~/.dsh`：`spawnSource`（`:1181-1190`）与 `spawnPkg`（`:1193-1211`）**都不设 `DSH_HOME`**；`resolveDshHome()`（`common.ts:106-109`）与 runMode 无关 |

### 一、升级动作本身：**零影响**（不运行就完全不碰）

`ensureCheckoutReady`（`server.ts:1321+`）对 source 的全部写操作都带 `--dir <checkout>` 限定：
`pnpm --dir <checkout> install`（`:1356`）、`--dir <checkout> run clean`（`:1383`）、
`--dir <checkout> run build`（`:1394`），且 git 操作只在 checkout 内。
→ **不触碰 `package` 目录**。只升级不运行 = 对 pkg 零影响，且可 `git checkout dsh-v0.1.5-rc.2` 随时回退。

### 二、升级后**运行** source：共用 `~/.dsh`，逐面核验

| 共享面 | 会不会被 source(0.1.6) 写坏 → 影响 pkg(0.1.5) 启动？ |
| :--- | :--- |
| `sessions/` | **会影响读取，但不影响启动**：列表只读 header（见上一节），只有打开具体会话才校验事件 → 症状是「个别会话打不开」，**不是 pkg 起不来** |
| `profiles/web/`（package.json + `cordis.patch.yml`） | **低风险**：`normalizeShippedProfile`（`profile.ts:798-821`）只在 bundle 列表**恰好等于已退役的 installation-owned 元组**时才回写，我方的 user-owned 列表（含 6 个 `@dsh-sparrow/*`）**永不重写**；残留的 `patchReload: "live"` 在 alpha.2 变成被忽略的键（不再校验、不再抛错） |
| `profiles/web/node_modules/` + `.dsh-module-fallback/` | **低风险**：两者解析都按**包名**（`resolveBundleDir` 用 install-anchor 优先），pkg 跑用 package 里的官方代码、source 跑用 checkout 里的，互不污染。`.dsh-module-fallback` **不是本版新引入**——本机该目录 mtime 是 2026-08-29，且已装的 0.1.5-rc.2 `dsh-app-boot/lib/index.js:316` 就认识它 |
| `settings.yaml` | **低风险，未实测**：本机该文件**没有** `llm-deepseek.protocol`（只有 `models`），与 alpha.1 笔记判断一致。0.1.6 若写入新键，0.1.5 读同一 section 是否容忍未知键**未从源码判死** → 标「不确定」（但 settings 是 section 级合并，插件/官方都按 section 读，风险低） |
| `storages/`、`attachments/`、`.credentials.yaml`、`.env` | 路径级隔离（不同文件名/子目录），未见冲突 |
| `cache/attachments/request-images` | 0.1.6 移到新路径、旧的不自动清理 → 并存不冲突 |

### 三、真正要防的仍只有一条：单向门（与插件无关）

即上一节的 `workspace/changes`。**升级前备份 `~/.dsh/sessions`** 即可覆盖这一项；
按上面的精确化结论，它的最坏后果是「0.1.6 写过的会话在 pkg 下打不开」，
而不是「pkg 模式不可用」。**若想彻底规避**：给试跑的 source 一份**独立 `DSH_HOME`**
（设 `DSH_HOME=<某目录>` 启动 source），sessions / settings / profile 全部隔离，pkg 完全不受影响。

### 四、还有一个「不能同时跑」的限制（非本次升级引入）

两模式共用 `dsh.port` 默认 **3080**，且 0.1.5 起 session 有跨进程锁（同一 session 至多一个进程持有）
→ **不能同时运行** pkg 与 source。要先停一个再起另一个。
（launcher 同一时刻也只管理一个 server 进程，所以正常操作下不会撞上。）

### 五、额外提醒：source 模式的更新检查会一直提示

launcher 的 source 更新检查按「origin 上最大的 `dsh-v*` tag」判定（`server.ts:1605-1622`），
现在最大值是 `dsh-v0.1.6-alpha.2` → 停在 rc.2 的 checkout 会**持续显示「有更新」**。
source 模式没有通道概念（`dsh.npmChannel` 只管 pkg 模式），属既有设计。

### 六、升级前置：git 走 Clash 代理，升级时需开着 VPN（2026-09-18 实测）

**这不是配置问题，是操作前提。** owner 确认：`7897` 就是 Clash 的端口，升级时会自行开启 VPN。
记录在此仅为说明「升级若失败，先看代理有没有开」。

* 本机 git 全局走代理：
  `git config --global http.proxy` / `https.proxy` → `http://127.0.0.1:7897`。
* launcher 的升级**全程走 `git` 子进程**且**不介入代理**
  （`server.ts:1610/1651/1744/1750` 分别 `ls-remote` / `fetch` / `checkout`；
  全仓库 grep 无 `NO_PROXY` / `no_proxy` / 代理清理代码）→ 完全继承 git 的代理配置。
* **实测（Clash 未开启时）**：经代理失败
  （`Failed to connect to github.com:443 over proxy 127.0.0.1 after 2060 ms`）；
  **Clash 开启后即正常**——所以「升级失败」的第一排查项就是**代理开着没**。
* 另有一个与代理无关的观察：`GIT_OP_TIMEOUT_MS = 10_000`（`common.ts:63`，git 操作 10 秒超时），
  而实测**首次**连接偶发要 20s 上下、随后只要 1–2s。网络本身是间歇性慢，
  所以**点更新失败时重试一两次即可**，不必当成故障。

**升级时还要过的其他关口（均已实测可用）**

| 关口 | 实测 |
| :--- | :--- |
| `gh api`（另一条网络路） | ✅ 1s 返回 `dsh-v0.1.6-alpha.2` |
| npm registry（`pnpm install` 要用） | ✅ 5s 返回 `0.1.6-alpha.2` |
| pnpm store（原生插件可能已在缓存） | ✅ store 存在（`%LOCALAPPDATA%\pnpm\store\v11`） |

**结论**：升级动作本身与 dsh / launcher / 我们六个插件均无关；
**开着 VPN 即可正常升级**，偶发超时重试即可。

### 七、升级后的验收清单（给 owner 操作时用）

升级动作走完（launcher 会自动 `pnpm install` + `clean` + `build`）后，按此顺序看：

| # | 看什么 | 预期 | 不符时怎么办 |
| :--- | :--- | :--- | :--- |
| 1 | DSH 能否起来、Web UI 能否打开 | 正常打开 | 若打不开 → 见《★ 核心结论》；最可能是网络/构建问题，不是插件 |

### dsh-file-manage — **alpha.1 的破点仍在，且语义更硬**

* 四个依赖导出在 alpha.2 **全部仍在**：`DeepSeekFileId` / `DeepSeekFilesClient` /
  `MAX_STORED_FILE_BYTES` / `MAX_STORED_FILE_COUNT`（`llm-deepseek/src/index.ts`）→ 能力门不触发。
* **类型缺口仍在**：`FilesApiOptions` 仍要求必填 `protocol: DeepSeekProtocol`
  （`common/files-api.ts:74-79`），我方 `DeepSeekSurface` 的构造函数签名仍写
  `new (options: { baseURL: string; apiKey: string })` → **`npm run typecheck` 仍会红**。
* **协议错配更硬**：alpha.1 是 `this.path = protocol === 'messages' ? '/v1/files' : '/files'`；
  alpha.2 改成 `this.baseURL = protocol === 'messages' ? messagesApiRoot(options.baseURL) : options.baseURL.replace(/\/+$/u,'')`
  且 `this.path = '/files'`（`common/files-api.ts:155-163`）。其中

  ```ts
  // common/messages-api.ts:11-13
  export function messagesApiRoot(baseURL) {
    const base = baseURL.replace(/\/+$/u, '')
    return new URL(base).pathname.endsWith('/v1') ? base : `${base}/v1`
  }
  ```

  也就是说：**`/v1` 不再由 path 决定，而由 baseURL 是否已含 `/v1` 决定**。
  我方 `host.ts:56` 仍写死回退 `https://api.deepseek.com`（无 `/v1`）、且**不读 `protocol`**，
  构造 client 时也不传 `protocol` → 落到 chat-completions 语义的 `/files`。
  而官方默认协议 `messages`（schema 默认未变，`config.ts:81`）下模型上传走
  `https://api.deepseek.com/anthropic/v1/files`。
  → **面板列出/删除的仍不是模型实际在用的那份云端文件**。
* 结论与 alpha.1 一致：**用户可见的正确性问题**；修法见 alpha.1 笔记「修法」四条
  （读 `protocol`、按协议分叉 baseURL 缺省、把 `protocol` 传进 client、加协议门），
  并需**额外注意** alpha.2 的 `/v1` 语义——baseURL 该传「不含 `/v1` 的根」，
  由官方 client 自己补，**不要**自己拼 `/v1`。

### dsh-nav-pin — ⚠️ **实证破点：宽度钳制整段失效（本版唯一已坐实的破坏）**

这是 alpha.1→alpha.2 唯一**已用真实浏览器实测坐实**的破坏，且根因是官方的**样式层级搬迁**，
不是插件写错了。

#### 根因（逐环已核）

1. nav-pin 的宽度钳制块（`src/nav-pin.ts:88-102`，`widthCapBlock()`）**在 `[data-phase]` 元素上**捕获官方宽度：

   ```css
   [data-phase] { --dsh-nav-pin-official-width: var(--dsh-chat-content-width); }
   [data-phase] [data-conversation-scroll],
   [data-phase] [data-width-handle] {
     --dsh-chat-content-width: min(var(--dsh-nav-pin-official-width), max(640px, calc(...)));
   }
   [data-phase] [data-conversation-scroll] { --dsh-composer-card-max-width: calc(var(--dsh-chat-content-width) + 32px); }
   ```

   注意 `[data-phase]` 就是**捕获点**——它读的是**自己这一层**的 `--dsh-chat-content-width`。

2. `[data-phase]` 的宿主是 `.root`：alpha.1 `ConversationRoot.module.css:1-35` **把整套宽度变量声明在 `.root` 上**
   （同元素，捕获得到值）；alpha.2 `ConversationRoot.module.css:1-8` 的 `.root` **只剩 6 条定位/布局属性**，
   整套变量被搬到**后代** `.body`（`:348-365`），且全树**再没有别处**声明它
   （`--dsh-chat-content-width:` 在 a2 全树只有 `:358` / `:369` 两处，都在 `.body`/`.embeddedBody`）。

3. 自定义属性**不向上传播**：`.root` 上的 `var(--dsh-chat-content-width)` 取不到后代 `.body` 的值
   → `--dsh-nav-pin-official-width` 解析为**空**，于是
   `min(var(空), ...)` 整条失效 → **`--dsh-chat-content-width` 在滚动体上被反向覆盖成空值**。

4. 后果：`[data-phase] [data-conversation-scroll]` 命中的子树里，所有 `var(--dsh-chat-content-width)`
   消费者（官方 `ChatView.module.css:39`、`MessageItem.module.css:21`、`AssistantMarkdown.module.css:34-35`、
   `ConversationRoot.module.css:242/248/252` 的拖拽条定位、以及本插件重算的 `--dsh-composer-card-max-width`）
   **全部塌陷**——正是本插件那套钳制本来要修的问题面。

#### 实测证据（Playwright + 本机 Edge，2026-09-18）

用两个最小复现页分别还原两版的 DOM/变量层级，注入**逐字照抄** `src/nav-pin.ts` 的样式表
（`_poc/TEMP/navpin-{a1,a2,a2-control}.html`，本地 `python -m http.server 8971` 提供），
读取同一个消费者元素的 `max-width`：

| 页面 | 结构 | `--dsh-chat-content-width`（滚动体） | 消费者 `max-width` |
| :--- | :--- | :--- | :--- |
| `navpin-a1.html` | **alpha.1**：变量在 `.root`（= `[data-phase]` 同元素） | 有效值 | **768px** ✓ |
| `navpin-a2.html` | **alpha.2**：变量在后代 `.body` + nav-pin 规则 | **空** | **`none`** ✗ |
| `navpin-a2-control.html` | alpha.2 结构但**移除** nav-pin 宽度块 | 有效值 | **768px** ✓ |

* 第 2 行 vs 第 3 行构成对照：同一 DOM 层级下，**只有加上 nav-pin 的规则才塌**；
  去掉它，官方值正常 → **因果确认在插件规则 × 官方层级搬迁的交互上**，不是单纯官方回归。
* a1 基线 768px = `clamp(680px, 1200px*0.64, 920px)`；a2 同参数下本应相同，实测却是 `none`。
* 实测还确认 `.body` 自身仍持有有效值（`clamp(...)`）——即**官方那层是好的**，
  坏的是 nav-pin 把 `[data-phase]` 当捕获点这个假设。

#### 修法（待 owner 拍板后开工）

捕获点必须**跟着变量搬家**：

1. 若继续说「搬到 `.body`」——把捕获点从 `[data-phase]` 改为 **`.body` 级**的选择器。
   但 `.body` 是 CSS Modules 哈希类，**不能裸写**；可用官方在 `.body` 上加的
   **稳定属性标记**：`data-conversation-content=""`（`ConversationContent.tsx:186`）。
   即把 `[data-phase]` 换成 `[data-content-phase]`（同一元素上也有，`:187`）或
   `[data-conversation-content]`。
2. 更稳的做法是**不依赖具体层级**：改用官方自己声明的 `--dsh-conversation-column-width`
   （由 `ConversationWidthControls.tsx:135` 用 JS 写在 `.root` 上，两版都在 `.root`）**自行推导**内容宽，
   不再读 `--dsh-chat-content-width`——这样官方再搬一次也不破。
3. 修完必须**补一条回归测试**：现有 `nav-pin` 测试是纯字符串断言，**拦不住这类层级搬迁**
   （它只验 CSS 文本，不验级联结果）。建议按本次方法留一个最小 DOM 级联用例。
4. 同时复核 `alwaysVisibleRule` / `hoverRevealBlock` 两条：
   它们走 `[data-conversation-scroll] div:has(> nav[aria-label=…])`，与宽度无关；
   实测中 nav 的 aria-label 文案两版未变（`ui-chat/src/client/locale.ts:26,137`）、
   `TurnNavigator.tsx` 与 `TurnNavigator.module.css` **逐字符一致**
   → 这两条**预期仍有效**，但 `.slot` 的 `display: none` 压制关系需随宽度修复一起复验。

> **诚实标注**：上述三行实测用的是**还原结构的最小复现页**，不是真实 dsh 页面。
> 它精确复现了官方的变量层级与插件样式表文本，足以判定级联结果；
> 但**真实页面上的最终观感**（导航轨道位置、拖拽条可达性）仍需在真实宿主上复验——
> 列为升级后第一优先实测项。
