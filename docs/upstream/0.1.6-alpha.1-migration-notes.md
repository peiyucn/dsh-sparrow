## 唯一的真实破点：dsh-file-manage × DeepSeek Files 协议

`packages/llm/llm-deepseek` 在本版被拆成 `common/` + `protocols/{chat-completions,messages}/`，
并按协议分叉出两套 Files 语义。**两处独立问题**：

### A. 类型层：构造函数新增必填 `protocol`（**typecheck 会红**）

```ts
// 0.1.5-rc.2
interface FilesApiOptions { baseURL: string; apiKey: string; fetch?: typeof fetch }
// 0.1.6-alpha.1
interface FilesApiOptions { baseURL: string; apiKey: string; protocol: DeepSeekProtocol; fetch?: typeof fetch }
```

插件 `src/host.ts` 的惰性表面与三处 `new surface.DeepSeekFilesClient({ baseURL, apiKey })`
都少这一个字段 → `npm run typecheck` 失败。
运行期 `this.protocol` 为 `undefined`，`path = protocol === 'messages' ? '/v1/files' : '/files'`
取到 `'/files'`、鉴权取 `Bearer` ——**这条分支恰好等于旧行为，所以运行期不会因此崩，
真正的问题是它固定落在 chat-completions 语义上，与宿主实际协议可能不一致**（见 B）。

### B. 语义层：协议与 baseURL 强耦合（**用户可见的正确性问题**）

新 `resolveAdapterOptions`（`common/config.ts:207-208, 292-293`）：

```
protocol 默认 'messages'
baseURL = config.baseURL ?? $DEEPSEEK_BASE_URL ?? (protocol === 'messages' ? 'https://api.deepseek.com/anthropic' : 'https://api.deepseek.com')
Files 路径 = protocol === 'messages' ? '/v1/files' : '/files'
```

插件 `readLlmDeepseekSection` 只读 `baseURL` / `apiKeyEnv` 两个字段，**不读 `protocol`**，
且 baseURL 缺省回退写死 `https://api.deepseek.com`（`src/host.ts:18`）。

后果：新宿主默认协议下，模型上传的图片落在
`https://api.deepseek.com/anthropic/v1/files`，而插件列表会去打
`https://api.deepseek.com/files` ——**面板列出的不是模型实际在用的那份云端文件**（表现为空列表 /
数量对不上 / 上游报错，取决于端点行为，**未实测**）。

**本机正是这个配置**：`~/.dsh/settings.yaml` 的 `llm-deepseek` 节只写了 `models`，
**没有 `baseURL`**（`protocol` 也没有，走 schema 默认 `'messages'`）→ 两个缺省同时命中，
插件列表与模型上传分叉。owner 若在设置里显式配过 `baseURL`，则 B 缩为「协议字段仍缺，A 仍在」。

### 修法（待 owner 拍板后开工）

1. 读官方设置节的 `protocol`。`ctx.settings.describe()` 的 `value` 是**已解析值**
   （`SettingsDescriptor.value`：「Current resolved value」，含 schema 默认 `'messages'`），
   缺省按 `'messages'`；
2. baseURL 缺省改为**按协议分叉**——`'messages'` → `https://api.deepseek.com/anthropic`，
   否则 `https://api.deepseek.com`（与官方 `resolveAdapterOptions` 同口径）；
   现有 `$DEEPSEEK_BASE_URL` 环境回退保留（与官方同源）；
3. 把 `protocol` 传进 `DeepSeekFilesClient`（补上 A 的类型缺口）；
4. 能力门沿用现有 `deepSeekSurface()` 形状检查（四个导出仍在，无需新增），
   **另加一道协议门**：设置节读到的 `protocol` 不在已知集合 `['chat-completions','messages']`
   内即抛错自停用——官方本版的协议字段是新的语义面，能力探测（有没有这个方法）发现不了，
   按根 AGENTS《扩展与宿主兼容》第二档「格式 / 版本门」处理。

#### 与官方归档页的能力对比（2026-09-15 逐项核验源码）

官方那页的全部能力就是：**读 `archivedSessionIds` + 每行一个「取消归档」**。
`ArchivedSections.tsx` 里没有单个删除 / 移动 / 批量入口，只有列表 + 搜索 + 恢复按钮。

| 能力 | 官方页（0.1.6-alpha.1） | dsh-archive-manage |
| :--- | :--- | :--- |
| 列出已归档会话 | ✅ | ✅ |
| 取消归档 | ✅ 单条 | ✅ 单条 + 整棵子会话树 |
| 搜索 | ✅ title / workspace | ✅ |
| 移入回收站（可恢复） | ❌ | ✅ |
| 彻底删除（不可逆） | ❌ | ✅ 标题强确认 |
| 游离会话识别与清理 | ❌ | ✅ 三差集 + 空白徽章 |
| 子会话树联动（任意深度） | ❌ | ✅ 以父为单位 |
| 复制回收站完整路径 | ❌ | ✅ |
| live 会话锁定提示 | ❌ | ✅ |

**关键佐证**：官方全树**没有任何 session 级删除 API**——`session-controller` 的
`@Remote` 里没有 delete/remove，`sessionPersistence` 契约里没有 `delete(sessionId)`，
`workspace-controller` 的 `delete` 是删 **workspace** 不是删会话。
所以「会话文件的移除」这件事官方至今没有对外开口子，本插件是唯一路径。

#### 但核心卖点已被官方悄悄修掉了（**这才是真正需要复看 README 的地方**）

插件 README 的第一句卖点是：

> DSH's archive marker only hides a session from the sidebar — **the @ mention list does not
> filter by the archive marker**, so archived sessions keep crowding @ candidates.

这条在 0.1.5-rc.2 当时是事实。但核验 0.1.5-rc.2 与 0.1.6-alpha.1 的
`packages/context/session-reference/src/index.ts`（官方 @ 提到的候选来源，
经 `ui-reference` 的 `trigger: '@'` source 消费）：

* `listCandidates()` 全文 **`archive` 零命中**（两个版本都是）
* 它调 `ctx.sessionQuery.listSessions()` 后只过滤 `record.header.id !== agent.id`，
  再按 label/cwd 匹配 —— **不读归档集、也没读 workspace registry**

即：**官方 @ 列表从始至终就没按归档集过滤**，两个版本一致。
所以插件那句卖点**至今仍然成立**，没有失效；只是它是「官方一直没做」，
而不是「官方做不了」——**官方只要接上 `archivedSessionIds` 就能一行修掉**。

不过要诚实标注一个**未核实的相邻面**：`ui-workspace` 侧确实有 `tree.ts` / `WorkspaceBrowser.tsx`
在**侧边栏列表**里按 `archivedSessionIds` 过滤（`sessionVisible()`）。也就是
**侧边栏过滤了、@ 列表没过滤**——两者不一致这件事，官方 0.1.6 仍未收口，
仍是本插件存在的理由。

官方 2026-09-12 的设计笔记（`.agents/notes/implemented/feature/2026-09-12-session-unarchive-settings-page.md`）
把归档集称作「a durable display filter」、把隐藏范围限定为 **every Workspace grouping surface**——
`@` 列表不是 grouping surface，所以**官方是明知范围而只做了侧边栏**，
不是漏掉。这也意味着「@ 列表是否该纳入归档过滤」是官方明确划在范围外的，
本插件的这一条卖点在可预见期内仍然有效。

该笔记另有一句对本插件有利的自陈：归档集里**summary 未加载的孤儿条目**
「a future cleanup surface can address the remaining orphan entries」——
即官方**承认孤儿/游离条目尚无清理面**，这正是本插件 stray 会话那一块的价值。

#### 结论

* README 的 ① 卖点（@ 列表不过滤归档）——**仍成立**，且官方设计笔记证明这是**有意划在范围外**
  （归档集只覆盖 “Workspace grouping surface”），不是遗漏 → 短期内不会失效
* README 的 ② 卖点（trash / 彻底删除 / 游离会话 / 子会话树）——**官方确实没有**；
  官方自己承认孤儿条目待「a future cleanup surface」
* 新增的官方归档页**不构成退役理由**，构成本插件「取消归档」这一条的**功能重复**；
  可考虑：把「取消归档」保留（与 trash 联动需要），但在 README 里点明官方也有一个入口
* **已知遗留依旧**：跨进程 session 锁缺口（另一 dsh 进程持有时本进程探不到，归档会移动其目录）
  在 0.1.6-alpha.1 未获官方新 API 支持，本版**不构成修它的时机也不是阻碍**

  （`packages/bundle/web-app/src/startup.ts:52`）→ `buildWebArgs` 与 `DSH_NO_OPEN_MIN_VERSION` 仍正确
* 官方品牌构建契约未变：`DSH_BUILD_CLIENT_PROFILE=official`、
  `build:official` 脚本、`.dsh-build/client-build-environment.json`
  （`scripts/client-build-environment.ts`，`DSH_CLIENT_BUILD_PROFILE: 'official'`）
* Node engines 未变 → `NODE_ENGINES` 校验与 `DSH_CLI_ENTRY_GUARD_MIN_VERSION` 仍正确
* `import.meta.main` 守卫仍在（`apps/cli/src/bin.ts` 末尾）→ 静默退出诊断仍有效
* **一处体验变化（非破点）**：source 模式的更新检查按「origin 上最大的 `dsh-v*` tag」判定，
  现在会取到 `dsh-v0.1.6-alpha.1` → 面板对停在 rc.2 的 checkout 会**持续显示「有更新 v0.1.6-alpha.1」**，
  点更新即 checkout 到 alpha。source 模式没有通道概念（`dsh.npmChannel` 只管 pkg 模式），
  该行为是既有设计、非本版引入。owner 需知悉这一点再做更新决定。

## 本机并存：source 与 pkg 共用 `DSH_HOME` 的单向门（2026-09-15 核验）

若打算用 launcher 把 **source checkout** 升到 0.1.6-alpha.1，同时保留 **pkg 0.1.5-rc.2**：

### 升级动作本身是隔离的

* pkg 装在 `~/.dsh-launcher-panel/package`，source 在 `~/.dsh-launcher-panel/source`
  （`managedPackageDir` / `managedSourceCheckout`）
* source 模式的 Update = `git fetch <tag>` + `git checkout --detach <tag>` + 在**该 checkout 内**
  `pnpm --dir <checkout> install / clean / build`（`ensureCheckoutReady`，`server.ts:1330-1405`）
* 全部 `--dir` 限定在 checkout → **不触碰 package 目录**。只升级不运行 = 对 pkg 零影响

### 但 `~/.dsh` 是共用的

`spawnSource` 与 `spawnPkg` **都不设 `DSH_HOME`**（`server.ts:1181-1211`；
`resolveDshHome()` 与 runMode 无关，`common.ts:106-110`）→ 两种模式读写同一个 `~/.dsh`：
`sessions/`、`settings.yaml`、`profiles/web/`、`storages/`、`attachments/`、`cache/`。

### 单向门：0.1.6 写过的会话，0.1.5-rc.2 可能**拒绝读**

两边 `SESSION_FORMAT_VERSION` 都是 **3**（无格式迁移，看起来安全），但 0.1.6 新增了事件类型
`image/offload`（`compaction-image-offload/src/projection.ts` 经 declaration merging 注册进
`SessionEventMap`）。链路逐环已核：

1. 读路径 `validateStoredEvents`（`session-persistence/src/storage-contract.ts:75`）：
   `!KNOWN_SESSION_EVENT_TYPES.has(type) && ignorable !== true` → 抛 `SessionFormatUnsupportedError`
   「refusing to interpret the log — it was likely written by a newer harness」——
   **拒绝整个日志，不是跳过单条**
2. `image/offload` 由 `session.append('image/offload', { targets })` 写入
   （`compaction-image-offload/src/image-offload.ts`）
3. `append()` **不自动打 `ignorable`**（`core/session/src/index.ts:703-731`：信封只组装
   `type/seq/time/data` + `surfaceOp`/`sourceEventSeqs`；`ignorable` 必须 writer 显式写，官方没写）
   → 属 **required-on-read**
4. 0.1.5-rc.2 的 `KNOWN_SESSION_EVENT_TYPES` 里**没有** `image/offload`（两版逐项 diff 确认）

→ **结论：source(0.1.6) 写过的会话，切回 pkg(0.1.5-rc.2) 打开会直接报错**。
反向（pkg 写 → source 读）安全，因为 0.1.6 认识 0.1.5 的全部词汇。
触发条件是 `IMAGE_OFFLOAD_REQUIRED`（图片请求超限时 offload 最老的图），不是每次必写，
但只要写过就中招。

> 这是官方**设计如此**（宁可拒绝也不误读），不是 bug；但它构成一个真实的单向门。

### 其余共用面的核验结果

| 面 | 结论 |
| :--- | :--- |
| `profiles/web` 的 bundles | **安全**。含 8 项（官方 base/web-app + 6 个 sparrow），不等于官方模板或 installation-owned tuple → `normalizeShippedProfile` 判为 user-owned，**不重写**（`app-boot/src/profile.ts:694-716`，两版一致） |
| profile 的官方 bundle 解析 | **安全**。`resolveBundleDir` 用 install-anchor 优先 → pkg 跑用 package 里的官方代码，source 跑用 checkout 里的，互不污染（`profile.ts:739-757`） |
| profile 的 lock | 0 个 `@deepseek-ai/*`，官方包不在 profile 里 |
| 同时运行 | **不行**。两模式共用 `dsh.port`（默认 3080）；且 0.1.5 起 session 有锁，同一 session 至多一个进程持有 |
| `settings.yaml` | **未实测、低风险**。0.1.6 若写入新键（如 `llm-deepseek.protocol`），0.1.5 读同一 section 是否容忍未知键未核 |
| 图片缓存路径 | 0.1.6 移到 `DSH_HOME/cache/attachments/request-images`，旧的不自动清理 → 二者并存不冲突 |

### 若要试 0.1.6 的安全做法（按风险从低到高）

1. **只升级 source、不运行** —— 零影响，可随时 `git checkout dsh-v0.1.5-rc.2` 回退
2. 试运行时给 source 一份**独立 `DSH_HOME`**（隔离 sessions / settings / profile）
3. 共用 home 试跑前**备份 `~/.dsh/sessions`**，并把 0.1.6 写过的会话视为只能前进

## 建议（待 owner 拍板，非本人决定）

* **不建议现在把版本线推到 alpha。** 按本仓库《发布（npm 包）》「官方版本跟随：不硬跟每个官方预发布、
  一事一议；rc 线内对齐官方最新」——0.1.6 还在 alpha，`latest` 仍是 0.1.5-rc.1，
  全量六插件齐发（根版本号对齐）宜等官方进 rc 线。
* **但 dsh-file-manage 的协议缺陷值得单列一节**：它是**用户可见的正确性问题**，
  且即使 owner 留在 rc.2 线，只要用户升到 0.1.6 就会中招。可选口径：
  ① 现在做 file-manage 补丁版（`0.1.5-rc.2.2`）只修协议一致性 + 前向兼容；
  ② 等 0.1.6 进 rc 线时与整套适配一起做。
* 无论选哪条，**实机验证清单**至少含：nav-pin 宽度轴与恒显规则、theme-tone 在新增面板上的浮层表面、
  file-manage 列表与模型实际上传的 Files 命名空间一致、chat-fim 主模型跟随。
  本机升级宿主前需留档（当前宿主 0.1.5-rc.2 是否保留由 owner 定）。
