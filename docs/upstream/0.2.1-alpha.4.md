## 4) alpha.4 新出现、要跟的项

### 4.1 🟠 新契约：插件兼容性**先读 `engines.dsh`**（⚠️ **已在 alpha.4 生效**，不是「将来」）

**新 guide**：`docs/upgrade-guide/v0.2.1-alpha.3/plugin-engines-dsh/`（alpha.4 才落盘，§7 有方法论说明）。
guide 正文逐字（英文）：「In v0.2.1-alpha.3, installation and profile startup judged a plugin or bundle only by its
`peerDependencies` … **In the next release, an own `engines.dsh` range decides alone and those peers are ignored**;
the peer rule applies only when `engines.dsh` is absent.」

**代码已落地**（`packages/boot/app-boot/src/plugin-compatibility.ts`，alpha.3 → alpha.4 **+41/−27**）：

```ts
// alpha.4
const engines = Object.hasOwn(fields, 'engines') ? objectOf(fields.engines, 'Plugin manifest engines') : {}
if (Object.hasOwn(engines, 'dsh')) {
  const range = engines.dsh
  if (typeof range !== 'string') throw new Error('Plugin manifest engines.dsh must be a string')
  return satisfies(runtimeVersion, range) ? {} : { 'engines.dsh': range }   // ← 单独决定，忽略 peers
}
if (!Object.hasOwn(fields, 'peerDependencies')) return {}
// … 否则仍按 @deepseek-ai/dsh / dsh-* 的 peer 判定（alpha.3 的行为）
```

同批还有一处**记录字段改名**：`PluginCompatibility` / `IncompatiblePlugin` 的 `peers` → **`requirements`**
（alpha.3 版该字段叫 `peers`，实测）。

**我方暴露（已逐条核实）**：

| 检查 | 实测 | 结论 |
| :--- | :--- | :--- |
| 5 个插件有没有声明 `engines.dsh`？ | **都没有**（两个有 `engines`，但只有 `node` 键：codebuddy-credits / theme-tone） | ⇒ `Object.hasOwn(engines,'dsh')` 为 false，**走 peer 规则**，行为与 alpha.3 完全一致 |
| `engines: { node: ... }` 会不会被判「manifest 不可读」？ | 不会——`objectOf()` 只拒绝**非对象 / null / 数组**；`{node:…}` 是合法对象 | ⇒ **不受影响**（guide 原文也把受影响作者限定为「声明了 `engines.dsh`，或把 `engines` 声明为非对象值」的） |
| 我方有没有读 `peers` / `requirements` 这些记录？ | `rg` 零命中（不引用 `PluginCompatibility` / `IncompatiblePlugin`） | ⇒ 改名对我方无影响 |

⚠️ **但这是一条要写进「DSH 插件契约」的长期约束**：**今后给插件加 `engines.dsh` 就等于「停用 peer 判定」**——
它会**单独决定**兼容性，我们的 `peerDependencies` 范围（以及 `check:dsh-pin` 守卫锚定的那 85 处声明）
**不再放宽也不再收窄**它。所以：
* **短期**：不要加 `engines.dsh`——保持 peer 规则，现有守卫链继续有效。
* **如果将来要加**：那个 range 必须**自己覆盖所有支持的 DSH 版本**，且 `workspace:` 值在里面**视为不兼容**
  （必须写语义化版本范围），同时 `check:dsh-pin` 的「单一真值 = peer 声明」口径要一并更新。

### 5.1 ⚪ 「UI 里配自定义模型的推理等级」——看着像命中，实测不命中

这条 release note 描述的能力对应的实现是 `packages/client/ui-settings-models/src/client/ModelReasoningEfforts.tsx`（alpha.4 新增，247 行）
与同目录的 `ModelRow` / `ProviderEditor` / `CustomProviderCard` / `ModelsSection` / `store` / `locales` 改动。

**为什么它「像」命中**：dsh-codebuddy-credits 正是一个**自定义模型 API 的 provider**（`CodeBuddyAdapter extends LlmAdapter`，
经 `ctx.llm.registerAdapter` / `registerConfigurableProviders` / `registerModelDiscovery` 注册），
而且在 `settings.models.provider-card` 槽里挂了自己的 Key 配置卡（`client/index.ts:192-196`，key = `llm-codebuddy-credits`）。
「给自定义模型的每个模型配推理等级」正是我们 `catalog.ts` / `adapter.ts` 在做的同一件事（`thinkingLevelMap` → `efforts`）。

**为什么实测不命中**——实现里有**两道门**，都把范围限死在 `pi-ai` 路由：

```ts
// ModelReasoningEfforts.tsx:1
/** Reasoning-level declarations for a model on a hand-declared pi-ai route. */
// ModelReasoningEfforts.tsx:72 —— 校验逻辑逐字「Mirror the pi-ai refusals of a hand-declared reasoningEfforts」

// ProviderEditor.tsx:47
type EditorLayout = 'deepseek' | 'pi-ai' | 'unknown'
// ProviderEditor.tsx:156
if (ns === 'llm-pi-ai') return 'pi-ai'
// ProviderEditor.tsx:227-231
// Only a hand-declared pi-ai route's rows edit reasoning levels — the one
() => layout === 'pi-ai' && props.declared === true ? reasoningLevelChoices(namespace, schema) : []
```

* 新编辑器只在 **`layout === 'pi-ai' && declared === true`** 时出现，`layout` 由 provider 命名空间算出
  （只有 `llm-pi-ai` 映射到 `'pi-ai'`，其余一律 `'unknown'`，官方注释逐字「unknown namespaces get the hint alone」）。
* 我方 provider 是**自己注册的 Cordis `LlmAdapter`**，命名空间不是 `llm-pi-ai`，模型元数据来自 CodeBuddy 服务端
  `/v3/config`（`catalog.ts` 的 `declaredEfforts()`）⇒ **不落在这道门内**，该编辑器不会出现在我方 provider 上。
* 它写的是 **pi-ai profile 里 `models` 的 `reasoningEfforts` 字段**（`ModelReasoningEfforts.tsx:53-59` 的 `withEfforts()`），
  与我方「从服务端能力推导 `thinkingLevelMap`」**不是同一个配置面、不会互相覆盖**。

⇒ **判定：不命中。** 但这条要记进基线：如果将来官方把这套「按模型声明推理等级」的 UI **推广到非 pi-ai 的第三方 provider**，
那就会与 codebuddy 的 `efforts` 推导面**重叠**（届时需决定「以服务端为准」还是「以用户声明为准」）。
**本轮它只覆盖 pi-ai，故暂无冲突。**

**顺带部分解决 α.3 报告 §8 的一个遗留未核实项**：α.3 报告记「官方 `ui-settings-models` 22 文件改动未逐个核，
我方 `priority: -1` 遮蔽官方 ModelSelect 是否仍生效未核实」。
实测 alpha.4 里 **`packages/client/ui-model-selection/` 只有 `package.json` 变了、源码零改动**
⇒ 我方遮蔽的**目标面本身没动**（遮蔽是否生效仍需真机验证，但「官方没改这个面」已经落地为事实）。
另外「22 文件」那个数字是 α.3 的统计口径；alpha.4 的 `ui-settings-models` 是 **15 个文件**（含 2 个新增）。

## 7) 方法论修正：guide 目录名与落盘/生效的关系（本轮再收一格）

alpha.3 报告 §7 第 6 条记的是「**目录名标的是「宣布变更的那个 release」，实际落盘常在下一次发布**」。
本轮这个新 guide 给出了更准的表述：

* `plugin-engines-dsh` 的目录是 **`v0.2.1-alpha.3/`**，但它在 **alpha.3 的树里不存在**（40 份 guide 没有这个目录），
  **alpha.4 才落盘**；而它描述的那项变更（读 `engines.dsh`）**在 alpha.4 已经生效**（代码 +41/−27，见 §4.1）。
* 它的正文也自证了这一点：先说「**In v0.2.1-alpha.3**, … judged only by peerDependencies」，再说「**In the next release**,
  an own `engines.dsh` range decides alone」——而「the next release」= alpha.4，正是承载这个文件的 tag。

⇒ **更准的规则**：**guide 的目录名 = 变更前的那个版本（基线）；变更的生效点 = 承载该文件的 tag**。
两者之间隔着一次发布（目录名标的是上一版，文件与生效一起出现在下一版）。
这也解释了上一轮看到的「`v0.2.1-alpha.1/` 的 19 份 guide 在 alpha.1 tag 上 0 份、只在 alpha.2 上存在」——
那 19 份描述的正是 α.1 → α.2 的变更。**推论**：rc 出来时，**凡是目录名等于「上一个 tag」的 guide，
其描述的变更在 rc 上已经生效**，必须当既成事实读，不能只看 diff。
