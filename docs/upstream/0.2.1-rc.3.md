## 0) 一句话结论

* **契约面是纯增量，代码层面没有必须改的**：我方 10 个槽位 / 13 处注册全部仍在；活跃插件 import 的
  32 个官方包里只有 5 个有源码改动（其中 1 个仅注释），新增的是三个 More 菜单 actions 槽，
  删改的只有内部注入面。
* **但版本门必须跟**：五个活跃插件的 peer 精确钉 `0.2.1-rc.2`，rc.3 宿主会把它们当不兼容
  **静默 skip**（`profile.ts:760-761` 判定并抛、`:766` 收进 `skippedBundles`，「nothing is printed」）⇒
  用户升到 rc.3 后表现是「插件全没了」，不是报错。所以这一版不能因为 release note 短就跳过。
* **左栏 More 不会自动列我们的面板**：rc.3 实装的菜单内容只有「安装插件 / 创建插件」两行；
  设计稿里的 pin / 自定义入口列表没上（`EntryMenuContent.tsx:34` 对 sidebar / rightbar 把 entries 丢空），
  pin 状态只有内存实现且**没有 UI 入口**（`panel-pins.ts:26` 无 persist，`EntryMenuContent` 不渲染 pin 按钮）。
* **「咱们的放进更多」技术上能做、不建议做**：往新公开槽 `sidebar.panellist.actions` 注册一行即可，
  但 More 是插件发现面不是导航面，且 rc.3 没有 pin UI ⇒ 只放更多里 = 图标消失、用户无法放回。详见 §5。
  **owner 已决定本轮搁置（2026-10-24）**，不写 spec、不改插件。
* **发布通道**：按规则 rc 线发 `latest`（不是 `next`）。当前官方 `latest` 仍是 `0.2.1-rc.2`、rc.3 只在
  `next`，所以开放项只剩**时机**——建议等官方把 `latest` 移到 rc.3 再打 tag（§7）。

3. **官方模型列表**：`dsh-llm-deepseek` 吸收 account 线的 listing 代码（`listing.ts` / `listing-cache.ts` /

4. **分析埋点**：新增 `sidebar_menu_click` / `more_menu_item_click` / `code_work_view_toggle` 等事件，

## 5) 「咱们的放进更多」可行性（回答 owner 的问题）

> **决定（2026-10-24，owner）**：本轮不做 More 集成，不改插件、不写 spec；等官方把 pin / 自定义
> 实装后再评估是否需要。以下内容留档，供那时参考。

### 5.1 rc.3 的 More 实际是什么

* 左栏 More 按钮是 `<nav>` 里的最后一个 `.panelRow`，**只在 `sidebar.panellist.actions` 有注册时出现**
  （`ui-sidebar/src/client/index.ts:66-69`、`SidebarRoot.tsx:347`）。
* 菜单内容由默认加载的 `ui-entry-customization` 注册，实装只有两行：
  **「安装插件」（打开插件列表）/「创建插件」（起一个 Creator 草稿）**。
  设计稿里「列出本区可自定义条目 + pin 开关」的部分**没实装**：
  `EntryMenuContent.tsx:34` 只对 `conversation` 渲染 entries（用于折叠视图），sidebar / rightbar 不渲染；
  组件里也没有任何 pin 按钮调用 `onPinnedChange`。
* 因此：**我方 archive / files 两个面板不会自动出现在 More 里**；它们只是照旧占左栏图标。

### 5.2 技术上能不能放进去

能。新槽是公开契约（`docs/subsystems/slots.md` 明确写了「Other plugins may register menu items into them」），
做法示意（未跑通）：

```ts
ctx.slots.inject('sidebar.panellist.actions', () => ctx.slots.register({
  name: 'sidebar.panellist.actions', id: 'archive-open', locale: 'archive-manage',
  inject: () => ({ open: () => ctx.layout.selectPanel('archive') }),
}, MenuRow))
```

同时把 `sidebar.panellist` 的图标注册去掉（否则图标和菜单行重复）。面板本身继续注册在 `main`。

### 5.3 三个方案

| 方案 | 做法 | 代价 |
| :--- | :--- | :--- |
| A（推荐）不动 | 保持 `sidebar.panellist` 图标；等官方把 pin / 自定义实装后，条目会自动获得「可隐藏」能力 | 左栏图标继续占位；但这是官方认可的入口层级 |
| B 只放更多 | 去掉图标，往 actions 槽注册一行 | **rc.3 没有 pin UI ⇒ 用户无法把它放回左栏**；入口深一层、无图标、可发现性明显下降 |
| C 两边都放 | 图标 + 菜单行 | 同一入口出现两次，语义重复；菜单行还会和官方两行混排 |

**建议 A**：More 的定位是「插件发现 / 创建」，不是导航；设计稿里的完整形态（列表 + pin + 持久化）
还没上线，等它上线后我们的面板天然变成可隐藏，不需要现在自造一套。若确实想减少左栏图标，
更合适的做法是先把两个面板合并成一个（archive 与 files 都是「云端数据管理」），而不是塞进 More。

### 5.4 另一种读法：把「我们的插件源」放进更多

如果 owner 的意思是「让用户从 More 里发现 dsh-sparrow 这一套插件」，那倒是**贴着 More 的定位**：
官方 `pluginMarket` Remote 有 `listIndexes()` / `setIndexes(urls)`（`ui-plugin-market/src/client/market-store.ts:178,288`），
理论上可以注册一行「添加 dsh-sparrow 插件源」——读现有列表、追加 `https://dsh.pyai.site/market/index.json`、
写回，再打开插件列表。但有三条硬前提，本轮**未验证**：

1. `ctx.remote.pluginMarket` 对第三方 client 插件是否可见（目前只有官方包在用）；
2. `setIndexes` 是**整体替换**，必须读-改-写且处理并发，写坏会清掉用户已有的索引源；
3. 这属于「替用户改配置」的动作，需要 owner 认可 + spec + 明确文案（官方在索引源弹窗里专门写了第三方信任提示）。

按仓库纪律（新功能先写 spec），这条不放进本轮适配。

## 7) 发布通道与时机

* **通道按规则走 `latest`**（`AGENTS.md`《发布（npm 包）》：alpha / beta 发 `next`，rc 与稳定版发 `latest`）。

  `latest`，只是不抢在官方 promote 之前发。tag 前照旧由 owner 当次确认。
