### 5.2 玻璃与合成边界（本次最要紧的一条机制）

**关键机制**：带 `backdrop-filter`（非 `none`）的元素会成为**它后代的 backdrop root**，同时成为 `position: fixed` 后代的**包含块**。

- 早期把玻璃挂在**顶栏本体**与**输入卡本体**上（色调档）⇒ **渲染在这两棵子树里的官方弹层**（模型选择菜单、顶栏动作区弹层、官方输入触发器菜单）自己的 `blur(40px)` **只能采样子树** → 模糊失效，只剩半透明底色 ⇒ 背后对话文字没被糊、直接可读 = owner 看到的「全透明 / 串色」。官方深浅两档一直正常，正因为那两档下这几条规则被官方默认门关掉。
- **修法**：填充 + 渐变 + 模糊一并挪到 **`::before`**（伪元素没有后代 ⇒ 不会把任何官方弹层关进 root）；本体只留定位/层级/投影并让出底色；卡片本体补 `position: relative` + `z-index: 0` 保住层叠语义；伪元素补 `border-radius: inherit`；两条伪元素都 `pointer-events: none`。
- **真机证据**（3080 violet）：顶栏本体 `backdrop-filter: none` / `::before` = `blur(12px) saturate(1.15)`；卡片本体 `none` / `::before` = `blur(10px) saturate(1.45)` + `border-radius: 22px`；**打开模型菜单后，祖先链上带 `backdrop-filter` 的元素数 = 0**（改前是卡片的 `blur(10px)`）。

| # | owner 现象 | 根因 | 最终修法 |
| :--- | :--- | :--- | :--- |
| 5 | **弹层全透明 / 分类标题串色 / 联想对话框全透明** | 见上（backdrop root） | 玻璃全部挪到 `::before` |
| 6 | **「输入框玻璃边缘光效和之前不同」** | 上一轮挪玻璃时，**inset 边光留在了本体**；绘制顺序「元素自己的背景/box-shadow」先画、**负 z-index 子层随后盖上去** ⇒ `::before` 那道玻璃把 inset 环整个埋掉 | inset 边光与填充、渐变放进**同一层**（`::before`）；本体只留**外**投影 |
| 7 | **「think 那条黑框」** | 官方给吸顶行的底色是**不透明纯色** `var(--dsw-alias-bg-base)`（展开的 Think 行吸在滚区顶部、压住滚过去的正文）。官方档下 bg-base 就是地面纯色 ⇒ 看不出带子；我方地面是**渐变光带 + 颗粒** ⇒ 纯色底盖上去显成一条「黑框」 | 与顶栏同一套：把地面**原样重画**（同色 + 同渐变 + 同颗粒 + `fixed` 对齐），复用 `backingPaint()`；锚点收窄到官方自己加底的那个状态（`[data-expanded] [data-open] [data-disclosure-row]`，逐字对齐官方规则） |
| 8 | **6 个色调下背景有竖直分界线** | 面板被抬到 z=82 吃不到 z=80 背景层的光，由我方重画 —— **素材一直对，但合成方式不同构**：背景层深色轴整层 `mix-blend-mode: screen`、颗粒走 `::after` + `opacity` + `screen`（纯加法）；而面板把颗粒当**第 4 个背景层正常合成**（同时压暗） | 面板改成与背景层**逐项同构**：3 层渐变 + 独立 `::after` 颗粒（贴图/opacity/混合模式**直引**背景层常量），深色轴补 `background-blend-mode: screen` |

**逐像素复验**（面板左缘 `x=704`，逐列取中位 R 值以滤掉正文文字）：跨缘差值 **现在 1 档 vs 关掉我方图层后 3 档** ⇒ 分界线消失。

### 5.3 材质归属：材质归官方、质感归我们

owner 给定的口径：「**透明和模糊和官方默认一样就行**」+「用 dsh 官方新代码的接入方式接入」+「不碰官方黑白色」。

| 归属 | 内容 |
| :--- | :--- |
| **材质**（填充 / 模糊 / 圆角 / 阴影） | **官方**的 —— 我们一个字都不写（写了就是「画两遍」或「改坏」） |
| **质感**（颗粒 + 光，`background-image`） | **我们的**，只在 `SURFACE_ANCHORS` 那张表里叠 |
| **色调** | 走 `ctx.theme.overrideTokens` 染官方 token ⇒ 官方材质**自带色调** |

据此撤掉的旧兜底：`SURFACE_ANCHORS` 曾给每个锚点刷一层**不透明** `background-color: var(--dsh-theme-tone-panel)` —— 那是 0.1.5 时代官方弹层底色散落、多为实色时的兜底；0.1.7 官方统一成「半透明 + 模糊」后，这层不透明底**把官方玻璃整块盖掉**。现该表**只叠 `background-image`**。

同样撤掉的还有一整块 `MENU_MATERIAL_ANCHORS`（`MENU_FILL_VARIABLE` / `MENU_BLUR_VARIABLE` 一并删除）：它给每个菜单锚点刷一对 `background-color + backdrop-filter`，本意是「兜住官方没配成对的地方」，但 0.1.7 官方**到处都配好了** —— 官方画在**元素自己身上**的是同值覆盖、无碍；画在 **`::before`** 上的则是**同一个 50% 色叠两次 ⇒ 等效 0.75**（owner：「子代理卡片好像没有透明模糊吧？」）。

> ⚠️ **粘性分组标题是这条规则的有意例外**（标题要挡住滚过去的行，而官方给它的填充是半透明的）—— 详见 §5.4。

这一条 owner 报了四轮，是本次适配**返工最多**的一处。owner 四句原话合起来就是全部约束：

1. 「把分类标题的背景色去掉，有点突兀，咱们的和官方的一起处理。」
2. 「透明和模糊和官方默认一样就行。」
3. 「给修坏了又。又重叠了。**只是把那个背景去掉，不是变成透明的**。」
4. 「背景条又出来了…那条背景条**要和菜单底色一致**，这样就看不出来有那一条。」

②+③+④ 推出：底色**必须挡住滚过去的行**（不透明），**又必须和卡片同色**（看不出那条）。难点在于卡片是**半透明玻璃**，表面不是静态色而是一摞合成：

> 卡片 = [颗粒] 叠在（菜单填充 叠在 [地面] 上）　　← 地面 = 底色 + 三段光 + 颗粒

标题要挡行就必须自带不透明底，于是唯一能让它"看不出"的写法是**把上面那一摞逐层重画一遍**，只把最下面的「页面内容」换成静态的「地面」。

**最终写法**

```
background-color = bg-base                  ← 不透明地面底色（挡行；它只是底色，不是"白板"）
background-image = 颗粒, 填充渐变, 地面        ← 颗粒 + 三段光，固定对齐视口
```

合成 = [颗粒] 叠在（填充 叠在 地面上），与卡片**逐层同源**，实测两轴差都在 1 级以内。

三条必须记住的细节：

1. **层序**：`background-image` 列表**在前的画在上面**。写成「填充, 颗粒」就成了 [填充] 叠在（颗粒 叠在 底 上），与卡片正好调个个儿 —— 既偏色，颗粒又被填充 alpha 压掉 42%。实测两个方向都错：浅色轴标题偏亮 **+5.2 级**、深色轴偏暗 **−10 级**，正是 owner ④ 说的「背景条又出来了」。
2. **双 token 分叉**：官方把菜单填充收进 `--dsw-menu-surface-fill`（`MenuSurface.module.css:26`），`--dsw-specific-menu` 只是**别名**（`body { --dsw-specific-menu: var(--dsw-menu-surface-fill) }`）。本插件以前只染别名 ⇒ 卡片用官方值、标题用我方染过的值 ⇒ 又一条色差带。**现两个名字一起染、同值**。
3. **`background-attachment: fixed` 与值数补齐**：地面是整屏 `position: fixed` 层、百分比按视口解析；少了它，26px 的小条会把 `ellipse 80vw 45vh` 压成硬边光带。且 `background-attachment` **值数必须等于层数** —— CSS 值少于层数时整串**重复补齐**，少写一个光层就会被压扁。

**不写 `backdrop-filter`**：标题在菜单内部、菜单自己已是 backdrop root，补模糊只会采样子树里**正在滚动的行**（实测 31.719/px，比不写更脏 19.885/px）。

**圆角：由滚动容器承担，标题保持方角。** owner 要过圆角（「和菜单的圆角一致」），但实测证明**写在标题上必然漏** —— 圆角在角上啃出一块缺口，滚动的行从缺口里透出来（`.ccb-model-option` 悬停底铺满整行宽、行文字从 x=8 起）。改由**滚动容器**统一圆上两角：容器顶角的裁剪**同时作用于标题条与行** ⇒ 缺口里既没有条、也没有行，露出的是菜单自己的玻璃；标题方角 ⇒ **结构上不可能漏**。真机实测 10 个滚动位置全部 0 泄漏。

- 半径走变量 `--dsh-theme-tone-menu-inner-radius`，默认给官方菜单的同心值（16 − 内边距 4 = 12 = `--dsw-radius-md`）；菜单外圆角不同的在自己的菜单元素上覆盖它（codebuddy 菜单 20 ⇒ 16px）。
- 右上角补一个 `--dsh-scrollbar-width`（所有行的右边缘在内容盒上，比容器右边缘靠左一个滚动条宽，不补就是「左圆右方」）。
- **只圆上两角** —— 下两角若也圆，滚到底时最后一行会被啃掉。

⚠️ **已知近似（诚实记录）**：卡片是玻璃，其背景是**被 blur 过的动态内容**，无法静态算出，只能取「地面」这个唯一可静态确定的参照 ⇒ 菜单压在正文上时残留误差随内容而定（通常 1–5 级）。另有一处系统性差异：我方颗粒画在菜单元素自己的 `background-image` 上，而官方 `.material` 是它的**负 z 子元素**、自带 `blur(40px)` ⇒ 官方卡片上的颗粒被自己那层模糊糊掉（实测同一位置 `sd`：卡片 0.6 vs 标题带 2.1）。两害相权取前者（owner 用的 codebuddy 选择器卡片与标题**逐层同源、差 ≤1 级**）。

> 📌 **交付版另有一条通道**（rc.2 期补的，见 [`0.1.7-rc.2.md`](0.1.7-rc.2.md) §6.4）：正因为元素级这层
> 被官方材质洗掉，交付版把同一串图层**又画了一份到 `::after`**（`content:''` + `z-index:-1`）。
> 也就是说上面这条「已知近似」描述的是**元素级那一层**；真正让质感可见的是 `::after` 那层。

**为什么不能给标题填「和卡片完全一样的颜色」**（决定性实验）：因为**卡片的颜色根本不是一个固定值**。把菜单定住、只换它背后的东西：

| 菜单背后放什么 | 卡片 | 标题 |
| :--- | ---: | ---: |
| 正常界面 | (53.0, 52.9, 63.6) | (53.9, 53.1, 62.7) |
| 一块**白板** | **(172.9, 172.9, 179.4)** | (53.9, 53.1, 62.7) |
| 一块**黑板** | **(48.7, 48.1, 54.5)** | (53.9, 53.1, 62.7) |

卡片是玻璃，颜色 = 填充 叠在**被糊掉的背后内容**上，背后一换它就跟着变（**48.7 ↔ 172.9，差 124 级**）；而标题不透明、自己画自己 ⇒ 纹丝不动。所以**任何固定色都只能近似** —— 要"一样"的那个东西本身在动。唯一能做到**逐像素相同**的办法是「标题什么都不画 + 不吸顶」（实测差 ≤0.2 级），但那会丢掉「滚动时钉住分组名」这个官方行为，owner 没有选它。

### 5.10 运维：两个高频疑问

**「改了插件代码，需要重启 dsh 吗？」——不需要，刷新即可**（已核实）：

- 服务端按**内容派生的 `rev`** 拼 bundle URL（如 `/plugins/??@dsh-sparrow/dsh-nav-pin/client.js&rev=399479857a18`），文件一变 `rev` 就变，而 `?rev=` 变化即绕过 `immutable` 缓存。
- **实测**：普通刷新（非强制）的页面上抓 bundle 响应体，核到当轮标记（nav-pin 含 `shouldDriveGlow`、theme-tone 含 `dsw-menu-backdrop-filter`）；行为侧派发 `pointermove` 后光带变量从「未设置」→ `50px`，说明新监听确实在跑。
- 所以流程是：**改代码 → `npm run verify` → 刷新页面**（若浏览器仍跑旧 bundle，强刷一次）。只有**新增/移除插件条目**（`package.json` 的 bundles 变化）才需要重启。

**⚠️「设置改了不生效」先查孤儿写锁**（官方原子写锁**有意不自动回收**，见 `packages/util/atomic-write/src/index.ts`：
*"The contender never removes an existing lock because file age cannot prove that its owner stopped; orphan recovery is an operator action."*）。

症状极具迷惑性：前端先乐观显示新值 → 写盘被拒 → 官方 `adopt()` 拿回权威值 → 界面**几秒后弹回旧值**，于是「任何插件改动看起来都没生效」。

```
POST /api/settings/mutate  →  200
{"ok":false,"error":{"code":"settings/rejected",
 "message":"atomic-write: timed out waiting for the writer lock at
            <用户主目录>\\.dsh\\profiles\\web\\package.json.lock"}}
```

**排查手法（可复用）**：怀疑「设置改了不生效」时，先在页面里挂 `fetch` 钩子抓 `/api/settings/mutate` 的**响应体** —— `ok:false` 且带 `settings/rejected` 就是写盘被拒；再看错误里那个 `.lock` 路径与 PID 是否已成为死进程。这比反复刷新页面有效得多。（实例：锁文件内容 = PID 15852 已不存在、锁写入时间比 dsh 启动早 3 分 49 秒 ⇒ 前一次进程异常退出的遗留死锁。）
