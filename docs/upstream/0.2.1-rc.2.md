## 4) 命中与处置

### 4.1 🔴 P0：`webRuntime` → `webStartup` + 绑定地址（4 个插件）

* 事实：4 个 `trust.ts` 的 `officialTrustedHosts` 请求期读 `ctx.get('webRuntime')`；rc.2 上恒 `undefined`
  ⇒ `allowedHosts` 恒空 ⇒ 非回环部署（LAN / 容器 Pod IP）**静默 403**，用户症状「插件打不开、dsh 没事」。
* 处置：`officialTrustedHosts(ctx)` 改为合并三份来源并去重——`webStartup.trustedHosts`（rc.2 主来源）、
  `webRuntime.trustedHosts`（旧宿主回退）、`ctx.get('webServer').host` 监听绑定地址（IPv6 加方括号、去 `%zone`，
  与官方 `isBindAddressAuthority` 同口径）。三处读取全部 try/catch + 形状校验，缺失只忽略、绝不抛穿。
  签名不变，`host.ts` 调用点未动；`src/host.ts` / `src/web.ts` 的过期注释同步。
* 测试：4 份 `trust.test.mjs` 重写官方信任面 describe（新服务采纳 / 旧名回退 / 双服务合并去重 / 绑定地址任意端口 /
  IPv6 / 形状不对不抛穿），`chat-fim/test/route.test.mjs` 补「老宿主只有 webRuntime」接线用例。
* 剩余风险：**未真机抓包**（本机无 LAN 部署条件），判定链每一环有源码证据。

### 4.6 🟠 P1（owner 报障）：theme-tone 滚动 / think 时卡顿

* 现象：对话页滚动明显卡顿、生成中（thinking）尤其明显。仓库此前两次定位：`:has()` 的样式重算（已用运行期锚点消掉，
  现存活 `:has()` = 0）与 `background-attachment: fixed` 的每帧栅格化（座底/缺口已有相位快档）。
* 本轮定位到一处**清单外**的结构性浪费：client half 的 `MutationObserver`（`body` 子树 `childList + class`）
  在**每次 DOM 变动**都跑同一套 `probeWorkstart`（`getComputedStyle(::after)` 强制样式解析）+
  `maintainAnchors`（多次全文档 `querySelectorAll`）+ `startPhaseSettle`（多帧 `getBoundingClientRect` /
  `getComputedStyle` 收敛重测）。流式输出每帧都有 `childList` 变动 ⇒ **思考全程每帧一次强制布局**，
  与官方渲染抢主线程；rc.2 又给流式行加了更多 `:has()` 规则，样式重算基数变大，体感更明显。
* 处置：
  1. **结构探测节流**：新增 `PROBE_MIN_INTERVAL_MS = 200`，rAF 合并 + 尾随定时器（流式结束一定补跑一次），
     高频率变动从 60Hz 降到 5Hz；尾随定时器随 `ctx.effect` 清理。
  2. **相位重测分两条路**：`class` 变动（右栏开合等布局动画）仍**立即**收敛重测；`childList`（流式输出每帧都有、
     也可能出现座位/卡片元素重建）走**节流入口**（200ms + 尾随）—— 既不在思考全程每帧测几何，
     又不会在切会话后停在 `fixed` 慢档。
  3. 新增 3 条源码级守卫（节流常量 + 尾随清理、相位只挂 class、结构探测回调里不得无条件重测相位）。
* **未真机复测**：本会话无有头浏览器量具（此前 M0/M9 量具见 `docs/spec/07` §4、`10`）；
  需 owner 本机按同一固定交互序列复测 P95 帧时长再确认收益。

## 6) ⚠️ 发布通道：必须先由 owner 拍板（阻塞点）

* 现状：插件 peer **精确**钉 `0.2.1-rc.2`；官方 npm `latest` 仍是 `0.2.0-rc.2`、`0.2.1-rc.2` 只在 `next`。
* 后果：若把插件 `0.2.1-rc.2` 发到 `latest`，**默认 `latest` 用户**装到后会被 app-boot 版本门拒
  （`plugin-compatibility.ts`：精确 peer 不满足），表现为「装不上 / 被停用」。
* 可选方案（需 owner 当次确认，二选一）：
  1. **只发 `next`**：偏离仓库 AGENTS「rc 发 latest」的现行规则，但对应当前官方通道，最安全；
  2. **等官方把 `latest` 移到 0.2.1 线再发 `latest`**：与现行规则一致，但发布时间不确定；
* 无论选哪个，**同版本号不可重发**；若选 1，后续官方 promote 后可用 publish.yml 的 promote 把同版本移上 `latest`。
