## 8. 真机复验后的追加修复（owner 报障 → 修复 → 再验证）

首轮「verify 全绿」不等于真机没问题。owner 在 3080 实测后报了四个现象，逐一定位并修复（全部有真机 A/B 证据）：

| # | owner 现象 | 根因（两版官方契约对照） | 修法 | 真机证据 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | **顶栏崩了** | 会话顶栏槽位在 rc.1 被嵌进 `header[data-slot='conversation.header']`（两层槽位都是 `display:contents`）；旧规则的 `[data-slot='conversation.session.header'] > *` 于是命中官方 `.titleRow`，把它抽成绝对定位浮层 | 改打真正生成盒子的那个 `<header>` | 门一开 header **40px → 10px**，修复后保持 40px、`titleRow` 留在行流 |
| 2 | **菜单全透明**（官方默认模式） | `--dsw-specific-menu` 在 rc.1 从 `var(--dsw-alias-bg-layer-3)`（不透明）变成 `rgba(...,.58)/.5`（半透明玻璃色），官方新增 `--dsw-menu-backdrop-filter` 并规定必须成对使用；我方四个插件都当不透明底色用、从未配 blur | 四个插件的全部消费方（含 sticky 分组标题）补 `backdrop-filter: var(--dsw-menu-backdrop-filter)` | 菜单 `backdropFilter` **none → blur(40px) saturate(1.5)** |
| 3 | **宽度拖拽条没了、两边挤** | `--dsh-chat-content-width` 在 0.1.5 定义在 `.root`(=`[data-phase]`)，rc.1 改到 `.body`(其子元素)；nav-pin 的捕获点写在 `[data-phase]` 上 → 解析为空 → `min(空,…)` 让整条属性 invalid | 捕获点改到「`[data-phase]` 下含滚动体的直接子元素」（两版都成立：rc.1 自带、0.1.5 继承） | 拖拽条 **10px → 0px**，修复后恢复 w=10px、x=406/1144、`cursor:col-resize`；模型标签也不再被截断成「DeepS…」 |
| 4 | 菜单分类标记改坏了 | 同 #2（sticky 分组标题也吃同一个半透明 token） | 同上 | `.ccb-model-groupTitle` 补配对 |

> ⚠️ **#2 里"给 sticky 分组标题补 `backdrop-filter`"这半条已被推翻**（2026-09-25，第九轮）：
> 标题在菜单内部、菜单自己已是 backdrop root，补模糊只会采样到滚动的行；而且 owner 随后

### 第四轮真机报障（owner：「折腾半天还是原样」——真根因是**挂载点**，不是规则）

owner 一次性报了「全透明 / 列表内分类标题有背景色 / 纹理不统一 / 联想对话框全透明 / 两边改宽度的调在顶部穿模 / 色调选完来回跳」，
并质疑「是不是一直在干无用功」。**先自证「代码有没有到机器上」**，再谈效果：

1. **代码确实到了**：`GET /?token=…` 的页面里六个 `@dsh-sparrow/*/client.js` 全在；
   服务端发出的 theme-tone bundle（`rev=e2be356e1090`，1.23 MB）里新加的标记字符串（`groupTitle` / `menu-backdrop-filter` / `width-handle-pointer-y` / `grain`）全部命中。
   故「改了没生效」这个假设被排除 —— **失败是真失败**。
2. **真根因（第 14 条）**：带 `backdrop-filter`（非 `none`）的元素会成为**它后代的 backdrop root**，
   同时成为 `position: fixed` 后代的**包含块**。而这一轮之前，本插件把玻璃**挂在顶栏本体与输入卡本体上**
   （只在色调档生效）—— 于是**渲染在这两棵子树里的官方弹层**（模型选择菜单、顶栏动作区弹层、
   官方输入触发器菜单：其锚点就是 `closest('[data-composer-card]')`）自己的
   `backdrop-filter: var(--dsw-menu-backdrop-filter)`（官方 `blur(40px)`）**只能采样子树** → 模糊失效，
   只剩半透明底色（深色轴 `#30313680`）→ 背后对话文字没被糊、直接可读 = owner 看到的「全透明 / 串色」。
   官方深浅两档一直正常，正因为那两档下这几条玻璃规则被官方默认门（`body:not([data-dsh-theme-tone-plain])`）关掉。
   同一条机制还解释「顶部穿模」（顶栏被浮层化后压在拖拽条上，见下一轮）与「一个透一个不透」
   （官方弹层模糊被我们弄没，而我们自画的卡片是不透明填充）。

| # | owner 现象 | 根因 | 修法 | 证据 |
| :--- | :--- | :--- | :--- | :--- |
| 14 | **弹层全透明 / 分类标题带子串色 / 联想对话框全透明**（色调档；官方档正常） | 玻璃挂在**顶栏本体**与**输入卡本体**上 ⇒ 它们成为官方弹层的 **backdrop root**（且是 `fixed` 弹层的包含块）⇒ 弹层自己的 `blur(40px)` 失效 | 填充 + 渐变 + 模糊一并挪到 **`::before`**（伪元素没有后代 ⇒ 不会把任何官方弹层关进 root）；本体只留定位/层级/投影并为伪元素让出底色（顶栏 `background-color: transparent`、卡片同）；卡片本体补 `position: relative` + `z-index: 0` 保住原有层叠语义，伪元素补 `border-radius: inherit`（22px 圆角）；两条伪元素都 `pointer-events: none` | **真机 3080（色调档 violet）实测**：顶栏本体 `backdrop-filter: none` / `position: absolute` / `z-index: 82`，`::before` 拿到 `blur(12px) saturate(1.15)` + 固定定位渐变栈（观感不变）；卡片本体 `none`，`::before` 拿到 `blur(10px) saturate(1.45)` + `border-radius: 22px`；**打开模型菜单**：菜单自身 `backdrop-filter: blur(40px) saturate(1.5)`、`background-color: rgba(55, 53, 70, 0.5)`（色调染色 + 官方 alpha），**祖先链上带 `backdrop-filter` 的元素数 = 0**（改前是卡片的 `blur(10px)`） |

**教训**：`backdrop-filter` 不只是「给这个元素加模糊」——它**改变了整棵子树的合成边界**。
凡是**可能承载官方弹层**的容器（顶栏、输入卡、各种 dock），玻璃只能挂伪元素；
「规则生成出来了」不等于「界面上有效果」，必须看**目标元素与它祖先链的 computed style**。

**另一个真教训（我自己的失误）**：第三轮把 #12/#13 的验收停在「生成的 CSS 里有这条规则」，
没有验到浏览器实际合成 —— 于是 owner 复验时看到的仍是原样。**验收点必须落在目标元素上**。

**三条根因**（都修了）：

1. **层序反了**。CSS `background-image` 列表**在前的画在上面**，第九轮写的是
   `linear-gradient(填充), 颗粒` → 合成成了 **[填充] 叠在（颗粒 叠在 底 上）**；
   而卡片是 **[颗粒] 叠在（填充 叠在 地面 上）**（菜单元素自己的 `background-image` 压着自己的
   `background-color`）。两层调个个儿 ⇒ 既偏色，颗粒又被填充的 alpha 压掉 42%（卡片是满强度）
   ⇒「一条更亮/更暗、且更平的带子」。
2. **漏了「地面」**。卡片是玻璃，它显示的是「填充 叠在**地面**上」；地面 = 底色 + 三段光 + 颗粒。
   标题只有不透明底色 ⇒ 地面那几层（尤其颗粒）在标题上丢了。
   定案把地面**原样重画**（`grainOverGradients()`，逐字同源）：
   `background-image` = **颗粒、填充、地面**，后四层配 `fixed`（地面是整屏 `position: fixed` 层，
   百分比按视口解析 —— 少了它，26px 的小条会把 `ellipse 80vw 45vh` 压成硬边光带）。
   地面颗粒的混合模式跟着轴走：浅色 `multiply` / 深色 `screen`（元素**内部**的图层用
   `background-blend-mode`，跨元素的 `mix-blend-mode` 在这里不适用）。
3. **两个填充 token 分叉**。官方 0.1.7 把菜单填充收进 `--dsw-menu-surface-fill`
   （`MenuSurface.module.css:26` 的 `.material` 读它），`--dsw-specific-menu` 只是**别名**
   （真机样式表：`body { --dsw-specific-menu: var(--dsw-menu-surface-fill) }`）——

   同一张卡片与它自己的标题各读一个 ⇒ 又一条色差带。
   顺带发现旧快照是 **0.1.7-rc.1** 的深色值 `rgba(48,49,54,.5)`（rc.2 是 `rgba(67,69,74,.45)`）——
   连"官方默认"那一档都发着过期色（本插件承诺过官方档 = 逐像素不介入）。
   现两个名字**一起染、同值**，基底与 rc.2 对齐。

**附带修好的**：官方默认档（owner 现在的深色轴就是这一档）以前把 `--dsw-specific-menu`

现在官方档下写进去的就是官方自己的值（实测卡片 `(42,43,46)`，等于官方 `#43454a73` 叠 `#151517`）。

⚠️ **已知近似（诚实记录，第十轮更新）**：
* 卡片是玻璃，背景是**被 blur 过的动态内容**（可能是对话正文），这一层无法静态算出，
  只能取"地面"这个唯一可静态确定的参照 ⇒ 菜单压在正文上时残留误差随内容而定（通常 1–5 级）；
* **官方 `MenuSelect`（`.material` 那张卡）另有一处系统性差异**：我们的颗粒画在菜单元素自己的
  `background-image` 上，而 `.material` 是它的**负 z 子元素**、自带 `backdrop-filter: blur(40px)` ——
  于是官方卡片上的颗粒被**自己那层模糊糊掉**（实测同一位置的 `sd`：卡片 0.6 vs 标题带 2.1），
  而标题带上的颗粒是满强度。用一张按官方结构（真机类名 `._material_ri079_21` +
  `._7KE1Ra_groupTitle`）搭的合成卡片实测：标题带比卡片**暗约 2 级**（另一条"不打颗粒"的写法
  则亮 3.3 级）—— 两害相权取前者（owner 用的 codebuddy 选择器卡片与它**逐层同源、差 ≤1 级**）。
  这一点已记进 `surface.ts` 的注释，需要时可按结构再分流一条规则。

**测试**（第十轮）：`surfaces.test.mjs` 那条用例重写为**六项契约 + 一项合成判据**：
层序（颗粒在最上）/ 地面逐字同源 / 逐层 `attachment` 与 `blend-mode` **值数等于层数**
（CSS 值少于层数时整串重复，少写一个光层就会被压扁）/ 深色轴只改混合模式 /
不得有模糊 / 两个填充 token **每个轴同值**。守卫做过突变验证：把层序改回"填充在上"、
把深色轴混合模式改成 `normal`、把两个 token 拆成不同值，用例都会变红。

**第十一轮（owner 提的做法）：切**同心圆角**——「和菜单的圆角一致」**

owner 在看过第十轮的实测后问了一句「**为什么不能做成和选择列表的背景色完全一样呢？**」，
并给出做法：「**官方原样，但把这个条变成圆角的，和菜单的圆角一致**」。

**先回答"为什么不能填同一个颜色"**（这一条做了**决定性实验**，不再推演）：
因为**卡片的颜色根本不是一个固定值**。把菜单定住、只换它**背后**的东西：

| 菜单背后放什么 | 卡片 | 标题 |
| :--- | ---: | ---: |
| 正常界面 | (53.0, 52.9, 63.6) | (53.9, 53.1, 62.7) |
| 一块**白板** | **(172.9, 172.9, 179.4)** | (53.9, 53.1, 62.7) |
| 一块**黑板** | **(48.7, 48.1, 54.5)** | (53.9, 53.1, 62.7) |

卡片是玻璃（`rgba(71,70,87,.45)` + `blur(40px)`），颜色 = 填充 叠在**被糊掉的背后内容**上，
背后一换它就跟着变（**48.7 ↔ 172.9，差 124 级**）；而标题不透明、自己画自己 ⇒ 纹丝不动。
所以**任何固定色都只能近似** —— 要"一样"的那个东西本身在动。
唯一能做到**逐像素相同**的办法是「标题什么都不画 + 不吸顶」（实测差 ≤0.2 级），
但那会丢掉"滚动时钉住分组名"这个官方行为，owner 没有选它。

**本轮实现**：填充与层序**一个都不动**（第十轮的配方继续生效），
**只给标题加同心圆角**：

| 菜单 | 圆角 | 内边距 | 同心内圆角 |
| :--- | ---: | ---: | ---: |
| 官方 `MenuSurface` `.surface` | 16px（`--dsw-radius-lg`） | 4px | 12px（`--dsw-radius-md`） |
| 本仓库 codebuddy `.ccb-model-menu` | 20px | 4px | **16px（`--dsw-radius-lg`）** |

统一取 `--dsw-radius-lg` —— 它**正是官方菜单自己的圆角 token**（与 owner「和菜单的圆角一致」
的字面要求一致），且对 codebuddy 那个 20px 菜单**恰好就是同心值**。

**切圆治的是哪一半**：标题上沿那两角**本来就被菜单自己切掉了**
（菜单 `overflow: hidden` + 20px 圆角），所以可见边界是**下沿那道横贯全宽的直边** ——
那才是"看着像一条背景条"的来源。切圆之后它读成一个"圆角块"而不是"一条带"。

**实测（真机 0.1.7，同一套取样）**：

| 变体 | 滚动前 | 滚动后 | 与卡片差 |
| :--- | ---: | ---: | ---: |
| 切圆后（本轮） | 66.33 | **66.33（逐像素不变）** | ≤1 级 |
| 不透明 + 方角（第十轮） | 66.32 | 66.32 | ≤1 级 |
| **官方填充 + 圆角** | 72.45 | **95.84（+23 级 ⇒ 露行）** | +8 级 |

⚠️ **切圆不是把底变透明**：上表第三行就是"官方原样 + 圆角" —— 它确实圆了，
但**行会从底下透上来**（滚动差分 +23 级）。owner 第三轮否掉的正是这一版。
本轮两条同时成立：**不透明底照旧** + 圆角。

**顺带纠正上一轮我自己的一条判据错误**：第十轮我说"切圆后下两角可能有 12 级偏差"，
那是取样区选错（采在 x=4..10 的 padding 空白处，那里本来就没内容）。
本轮把取样移到**行文字实际所在**的 x=12..130，并用**滚动差分**判：切圆后该区在
4 个滚动位置上完全一致（55.27 → 55.22），而不透明版与"官方原样"版的差别一目了然。

**测试**：`surfaces.test.mjs` 增加"圆角 = `--dsw-radius-lg` 且走 token"一条，
并给深色轴那条辅助规则加了"不得重复声明 `border-radius`"；
`picker-sticky.test.mjs` 增加一条"切圆但不得变透明"（圆角与不透明底两条断言同时钉住）。



### ⚠️ 最要紧的一条：官方**孤儿写锁**会让「所有设置修改静默失效」

owner 报「刚才这些问题一个都没修好，我没重启 dsh，是否需要重启？」——**跟插件与重启都无关**，
是官方原子写锁留下的一个**孤儿锁**把设置写入整条通道堵死了：

```
POST /api/settings/mutate  →  200
{"ok":false,"error":{"code":"settings/rejected",
 "message":"atomic-write: timed out waiting for the writer lock at
            C:\\Users\\DJ028191\\.dsh\\profiles\\web\\package.json.lock"}}
```

现场证据：锁文件内容 = PID **15852**，该进程**已不存在**；锁写入时间 **15:19:59**，
而 dsh 进程启动于 **15:23:48**（比锁晚 3 分 49 秒）——即一个**前一次进程异常退出的遗留死锁**。

官方源码对这个设计有明确说明（`packages/util/atomic-write/src/index.ts`）：

> *The contender never removes an existing lock because file age cannot prove that its owner
> stopped; **orphan recovery is an operator action**.*

也就是说官方**有意不自动回收**，只能人工删。它的表现极具迷惑性：
前端先乐观显示新值 → 写盘被拒 → 官方 `adopt()` 拿回权威值 → 界面**几秒后弹回旧值**，
于是「任何插件改动看起来都没生效」。

**owner 的关键补充**帮助纠偏了我的初判：「深色的三个色调没有这个问题，只有浅色有问题」——
实测后明白：深色那三个是**早就保存过**的值（配置里已有），显示正常；浅色每次都是**新写入**，
每次都撞锁。**不是浅色轴有 bug，而是「任何新写入」都坏了**，浅色只是恰好总需要新写入。

清除孤儿锁后的对照实测（同一实例、同一页面）：

| 项 | 清锁前 | 清锁后 |
| :--- | :--- | :--- |
| 切浅色 | 2.1s 后**弹回 dark** | **4.2s+ 稳定 LIGHT** |
| `settings/mutate` 返回 | `ok:false`（锁超时） | `ok:true` |
| 深色选 violet | — | 落盘 `darkTone: violet`、mtime 更新 |
| 浅色选 sakura | — | 保持选中、`gate: TONE`、`bgBase: #fff` |

**排查手法（可复用）**：怀疑「设置改了不生效」时，先在页面里挂 `fetch` 钩子抓
`/api/settings/mutate` 的**响应体**——`ok:false` 且带 `settings/rejected` 就是写盘被拒，
再看错误里那个 `.lock` 路径与 PID 是否已成为死进程。这比反复刷新页面有效得多。

### 「改了插件代码，需要重启 dsh 吗？」——**不需要，刷新即可**（已核实）

owner 问过两次，用证据定案（`link:` 装载的插件）：

* 服务端按**内容派生的 `rev`** 拼 bundle URL，如
  `/plugins/??@dsh-sparrow/dsh-nav-pin/client.js&rev=399479857a18`；
  文件一变 `rev` 就变，而 `?rev=` 变化即绕过 `immutable` 缓存。
* **实测**：在**普通刷新**（非强制）的页面上抓那两个 bundle 的响应体，核到我这一轮的标记 ——
  nav-pin 含 `handle glow follows pointer` / `shouldDriveGlow`；
  theme-tone 含 `syncRow` / `setTone` / `dsw-menu-backdrop-filter`。
* **行为侧**同样实测：普通刷新的页面上派发一次 `pointermove`，光带变量
  `(未设置) → 50px`（= `clientY - box.top`），说明新监听确实在跑。

所以流程是：**改代码 → `npm run verify` → 刷新页面**（浏览器若仍跑旧 bundle，强刷一次）。
只有**新增/移除插件条目**（`package.json` 的 bundles 变化）才需要重启，改代码不需要。
