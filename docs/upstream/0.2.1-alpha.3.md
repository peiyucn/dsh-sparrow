* **上一轮记的 3 处命中在 alpha.3 全部原地存续，一处都没被修掉**：

     **真正的残留风险是「我们没有归一化服务端给的档位顺序」**（且只有可选档位、不可关思考的模型才暴露），
     详见 §4.3（初稿曾照抄上一轮写「`off` 无条件排首、恒成立」，实测不成立，已改）。

## 7) 方法论沉淀（供后续跟版复用）

1. **`rg` 的 lookahead 必须带 `-P`，否则静默假阴性。** 本轮用 `rg -o --no-filename "data-menu-group-start(?![\w-])"` 扫 rc.2，
   得到 **64/64 全部「私有」**的错误结论（连官方锚点都被判成我方私有）。加 `-P` 后同一命令给出正确的 13 私有 / 51 官方。
   ⇒ 凡是带 `(?!…)` 的扫描，**先拿一个已知命中的样本做阳性对照**。
2. **`tree` API 的 blob sha 是 git SHA-1，不是 sha256。** 判「文件有没有改」用它最省事（零下载），
   但**算法别写错**；本轮用「对磁盘 `package.json` 现算 `sha1("blob <len>\0"+bytes)` 与 tree 比对」自证：
   **374/374 全量一致**，从而证明解压树就是 tag 内容。
3. **`tar` 在 Windows 上不建符号链接，还会改行尾。** 磁盘比 tree 少 14 个文件不是「源码缺失」——14 个是 `mode: 120000` 的链接
   （4 个 `CLAUDE.md` → `AGENTS.md`、`.claude/skills` 等），另有 1 个中文名 `说明.txt` 被 GBK 乱码成 `璇存槑.txt`（同一文件）。
   对抗性复核又补了一条：16058 个磁盘文件里 **16054 个 sha1 与 tree 一致、3 个不一致**，全是
   `apps/desktop/**/*.cmd` 的 **CRLF 行尾转换**（LF 归一化后 sha1 与 tree 完全相同）——
   ⇒ 以后遇到「解压树 vs tree 差 N 个」，**先按 `mode` 分类、再按行尾归一化复算**，别急着说文件缺失。
4. **「官方自家怎么做的」是判定契约语义的最强证据。** 上一轮把 `efforts[0] === 'off'` 判成回归，
   但官方自家 provider 的 `REASONING_EFFORTS` **也是 `off` 开头**，官方回放测试**直接断言 `'off'`**。
   ⇒ 遇到「我方顺序/默认值似乎与文档不符」时，**先去读官方自己实现的同一个面**，再决定是不是回归（§9）。
   ※ 但这条也有反面：**「官方也这么干」只解决定性，不解决契约**——官方 guide 仍要求适配器把档位升序排列，
   而我们没归一化服务端顺序（§4.3 的残留问题）。两者要分开说。
5. **服务名 ≠ 行 id。** 上一轮把 `webStartup` 当成「profile 行名」而排除掉一条可行修法；
   实际行 id 是 `web-startup`，`webStartup` 是普通插件 `apply` 里 `ctx.provide` 的**服务**（rc.2 起就在）。
   ⇒ 判「插件能不能拿到某个服务」要 grep `provide(`，不要看 patch 文件的 `id:`。
6. **官方 guide 目录名 ≠ 引入版本，这条在 alpha.3 再次成立。** `v0.2.1-alpha.2/` 的 10 份 guide **在 alpha.2 tag 上 0 份**，
   是 alpha.3 才补档的；`v0.2.1-alpha.1/` 也在 alpha.3 又补了 3 份。⇒ **目录名标的是「宣布变更的那个 release」，实际落盘常在下一次发布**。
7. **`--dsw-*` 采集器会把「前缀族」当成 token。** `--dsw-static-neutral-` 这类带尾随连字符的条目，
   在存活扫描里必然「零精确命中」——**要去数带后缀的命中**（实测 231 / 388 / 149），别直接判死。
8. **`git diff` 的上下文行号不是文件行号** —— 引用行号一律用源码树直接读。
9. **采集脚本要按「语法形态」而不是「引号样式」覆盖，且必须做阳性对照。** 本轮初稿的符号采集只匹配
   `import { … } from '<spec>'`（带大括号的具名导入），于是**整条 `@deepseek-ai/schemastery` 说明符 + 它的
   default 导入被漏掉**，得出 31/63 而不是正确的 32/64（§3.1）。
   ⇒ 采集 import 至少覆盖 4 种形态：`import x from`（default）、`import {a,b} from`（named）、
   `import * as x from`（namespace）、`import 'x'`（side-effect），**并拿一条已知会命中的样本做对照**。

## 9) 结论修正记录

### 9.1 对**上一轮**（alpha.2 报告）的两处修正

**修正一：`reasoning.efforts` 的定性 —— 「行为偏差」不成立。**

* 上一轮 §4.3 的原话：「官方新增「取首个条目当最低强度」的消费点，我们的顺序以 `off` 开头 ⇒ 官方生成的会话标题会取到「关闭思考」」，
  定性为 🟠 行为偏差，列为 rc 的 P1 改造项。
* 实测事实：官方**自家** provider `packages/llm/llm-deepseek/src/model-info.ts:10-31` 的 `REASONING_EFFORTS`
  顺序就是 **`off` → `low` → `high` → `max`**；官方回放测试
  `packages/test-support/llm-replay/tests/llm-replay.spec.ts:1475-1477` 断言
  `efforts[0].id === 'off'` 且 `prepared.config.reasoningEffort === 'off'`。
* ⇒ 「`off` 排第一」就是官方定义的**最低强度**。这条的**定性错在**把文档的「低→高」读成了「`off` 不算最低」。
* **但真问题没有消失，只是换了位置**：我方**没有归一化服务端给的档位顺序**（`catalog.ts` 在 `off` 之后直接沿用
  `supportedEfforts` 原序，固定档位/不可关思考分支甚至没有 `off`）⇒ 与官方 guide 的「必须升序排列」契约不符。
  修法建议保留（显式 rank 排序），**理由改成「满足契约 + 不假设服务端有序」**，不是「修 `off` 被选中」（§4.3）。

**修正二：`webStartup` 的可得性 —— 「profile 行名、插件拿不到、alpha.1 不存在」不成立。**

* 上一轮 §4.1 的原话：「⚠️ **不要**去注入 `webStartup` 服务本身（那是 profile 行名，插件拿不到，且 alpha.1 上不存在）」。
* 实测事实（对抗性复核独立复跑，**完全成立**）：
  * `webStartup` 由**普通 Cordis 插件** `packages/bundle/web-app/src/startup.ts` 的 `apply` 里 `ctx.provide(WEB_STARTUP_SERVICE, {…})` 提供
    —— rc.2 `:80`、alpha.1 `:98`、alpha.2/alpha.3 `:114`；常量 `:23 export const WEB_STARTUP_SERVICE = 'webStartup'`。
  * `cordis.patch.yml` 里的**行 id** 才是 `web-startup`（rc.2 `:161`、alpha.3 `:168`）。服务名与行 id 是两回事。
  * 官方自带回归测试 `packages/bundle/web-app/tests/startup.spec.ts:53-72` 就是用一条**普通行**声明 `inject: [webStartup]`、
    在 `config` 里读 `ctx.webStartup.trustedHosts` 并断言值等于 provider 的值。
* ⇒ 「旧名兜底双读」在实现上没有障碍；对 rc.2 而言**单读 `webStartup` 就能同时覆盖 rc.2 与 alpha.3**。
  但**双读仍要保留**，因为 §4.1 新增的那条（`lanAddresses` 消失）意味着 rc.2 的语义**不是**alpha.3 的子集。
