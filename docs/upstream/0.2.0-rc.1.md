# dsh-sparrow × dsh 0.2.0-rc.1 适配报告

> 适配对象：官方 checkout tag **`dsh-v0.2.0-rc.1`**（`4878cdabd8`，release PR #5387；
> 本机安装 `@deepseek-ai/dsh@0.2.0-rc.1`）
> **本文件只记 rc.2 → 0.2.0-rc.1 的增量**；rc.2 的完整报告见 [`0.1.7-rc.2.md`](0.1.7-rc.2.md)，
> 其中 `DeepSeekFilesClient` 构造签名 `apiKey → headers` 那次**真破坏**不在本版重演。
> 触发：owner 升级到 0.2.0 后报「刚适配的 0.1.7 插件又都用不了了，唯独 nav-pin 还活着」。

---

## 1. 结论

**直接原因仍是版本门**：peer 写的是精确 `0.1.7-rc.2`，运行时是 `0.2.0-rc.1` ⇒ 五个活跃插件在 profile 启动时被整批跳过。

**但与 rc.2 那次有一个关键区别：本版没有一处真破坏。** 按 §4 的 14 类 seam 逐项审计，**零回归**——官方 0.2.0-rc.1 对本插件群依赖的 API、DOM 锚点、CSS 变量、槽位名、格式常量**全部保持兼容**。

因此本次「适配」的实质是：

1. **依赖升线 + 重建 + 重验证**（机械工作，无代码改动）；
2. **一次架构改动**：`dsh-nav-pin` 并入 `dsh-theme-tone`（owner 2026-09-29 决定，方案见
   [`09-nav-pin-merge.md`](../../plugins/dsh-theme-tone/docs/spec/09-nav-pin-merge.md)）。

**nav-pin 为什么"活着"**：它的 `peerDependencies` 里只有 `@deepseek-ai/cordis`，而版本门只检查
名字为 `@deepseek-ai/dsh` 或 `@deepseek-ai/dsh-*` 的 peer（`plugin-compatibility.ts:75` 直接
`continue`）⇒ 它**根本没参加考试**。这是漏考，不是健壮性；本次合并后该免疫自然消失。
同时它的源码对官方**零运行时依赖**（`src/` 里只有 `import type`），所以它也是全群里唯一
不受官方 API 变动影响的插件。

---

## 2. 根因：精确版本 peer 被 0.2.0-rc.1 判为不兼容

启动日志逐条写明（`~/.dsh-launcher-panel/logs/server.log`）：

```
dsh: skipping profile bundle "@dsh-sparrow/dsh-archive-manage": Error: Plugin
  @dsh-sparrow/dsh-archive-manage@0.1.5-rc.2.4 is incompatible with dsh 0.2.0-rc.1:
  peerDependencies {"@deepseek-ai/dsh-agent":"0.1.7-rc.2", …}. …
```

被跳过的正好五个 bundle（nav-pin 无此日志，即未被跳过）：
`dsh-archive-manage` / `dsh-chat-fim` / `dsh-codebuddy-credits` / `dsh-file-manage` / `dsh-theme-tone`。

**连带伤害**：profile 自己 `dependencies` 里钉的官方两个浏览器包
（`@deepseek-ai/dsh-browser-use@0.1.7-rc.2`、`@deepseek-ai/dsh-experimental-browser-use-playwright-mcp@0.1.7-rc.2`）
同样被 `disabling profile plugin row` —— 这就是该实例**没有浏览器工具**的原因，本次一并升线恢复。

**口径不变：继续精确匹配。** 依据是官方自己的**已发布**插件就这么写：

| 官方 npm 包 | 其 `dsh-*` peer |
| :--- | :--- |
| `@deepseek-ai/dsh-browser-use@0.1.7-rc.2` | `@deepseek-ai/dsh-brand = 0.1.7-rc.2`（精确） |
| `@deepseek-ai/dsh-experimental-browser-use-playwright-mcp@0.1.7-rc.2` | `dsh-browser-use` / `dsh-agent` / `dsh-tools` / `dsh-system-prompt` **全部精确** |

（两者只有不进版本门的 `@deepseek-ai/cordis` 用 `~4.0.4`。）

> **owner 定调（2026-09-29）**：dsh 仍在快速发展期，**每次版本变化都不是"换个版本号继续活下去"这么简单**。
> 该原则同时否掉了两种省事做法：**不设范围窗口**（会把没验过的版本放进来）、**不接受"白捡存活"**
> （nav-pin 那种靠零声明的免疫）。⇒ 每次跟版都是一次正式适配任务。

## 4. 0.2.0-rc.1 契约审计（本次核心）

### 4.1 方法

插件群的依赖面**全部来自源码里字面写出的记号**（选择器字面量、槽位名、变量名、导出符号名）。
故审计做成**双向比对**：对每一个记号，分别在本版与上一版的官方源码里查存续——

* **旧版有、本版无 ⇒ 回归**（这是唯一能自动判定的"真断"）；
* 两版都有：再与该版**改动文件集合**求交，落在改动文件里的进人工复核。

> 复现方式：脚本在 `TEMP/`（scratch，不入库）；判定口径 = `git grep -F` 两 tag 对比 +
> `git diff --name-only` 求交。**注意两个方法学坑**（首轮踩过）：
> ① 哈希类名后缀在**源码里不存在**（`[class*='_mask']` 的产物是构建后的 `hash_mask`），
> 必须改为到官方 `*.module.css` 里找同名 class；
> ② theme-tone 的选择器写在**模板字符串**里，其中的 `/* … */` 注释不会被常规注释剥离器去掉，
> 会产生"注释里提到过 = 依赖它"的假信号（`data-sidebar-right-float-host`、`data-dockkit-host` 就是这么冒出来的）。

### 4.3 官方本版实际改了什么（供以后对照）

* **绝大多数官方包只改了 `package.json` 里的版本号那一行**——包括本群插件声明为 peer 的
  `dsh-agent` / `dsh-host-webserver` / `dsh-session-persistence` / `dsh-session-query` /
  `dsh-storage-domain` / `dsh-workspace` / `dsh-credentials` / `dsh-attachment` /
  `dsh-launch-environment` / `dsh-llm` / `dsh-session-projection` / `dsh-tools` / `dsh-brand` /
  `dsh-system-prompt` 等。
* `dsh-session`：仅 `repair.ts` 复原逻辑重写 + `index.ts` 新增一个导出。
* `dsh-settings`：只新增了一个测试文件，**API 未动**。
* `dsh-llm-deepseek`：内部 `file-store` / `request-files` / `upload-index` 调整，**公开入口未动**。
* 客户端侧改动面很大（`packages/` 下共 **574** 个源文件有改动），主要落在
  `ui-chat` / `ui-conversation` / `ui-primitives` / `ui-plugin-manager` / `ui-settings-*` /
  `product-analytics`（新增埋点）等——但**没有触及本群插件依赖的任何一个锚点**。

### 4.4 审计边界（**必须一并读**）

上面的比对是 **token 级**的：它能抓**改名 / 删除**，抓不到**行为变化**——元素还在、选择器仍命中，
但结构或层级变了（换了祖先、`z-index` 变了、容器上下文变了、渲染顺序变了），扫描看不出来。

本版改动最大的几个官方文件恰好属于这类风险点，**只能靠真机验收兜**（见 §6）：

| 官方文件 | 谁在依赖 |
| :--- | :--- |
| `ui-conversation`（`apply.ts` / `input/*` / `skeleton/InputBar.tsx` / `contract/*`） | chat-fim 注入它；theme-tone 与 nav-pin 锚在对话区 |
| `ui-primitives` 的 `Menu/Modal/Tooltip` 样式 + `useAnchoredPosition` / `useAnchoredMaxHeight` | chat-fim / codebuddy-credits 用这两个 hook；theme-tone 锚 `[role='menu']` |
| `ui-chat` 的 `ChatView` / `MessageItem` / `ReasoningRow` | theme-tone 的表面锚点与 nav-pin 的容器上下文 |
| `ui-layout` 的 `AppFrame.module.css` | theme-tone 锚 `[data-side]` / `.handle` 与 z-index 分布 |

**不把"扫描零回归"当成"一定没问题"**——rc.2 那次的教训正是：`DeepSeekFilesClient` 的
`apiKey → headers` 是**导出符号一个没少**的运行期破坏，能力门和符号扫描都抓不到。

## 7. 遗留与后续

* **【上游缺陷】会话列表冷启动 40–90 s（`readFirstZstdLine` O(n²)）**：症状是「打开/刷新页面后
  侧边栏列表空几十秒，之后突然全出现」，被误判成"会话丢了"或"归档插件弄坏了列表"。
  实测 `session/list` 87.7 / 47.7 / 40.2 s，同进程 `modelCatalog` 仅 44–55 ms。
  根因、实测数据、建议修法与复现脚本另立一档：
  [`session-list-cold-start-on2.md`](session-list-cold-start-on2.md)。
  我方已把自己那半收敛（归档插件三项启动扫描不再与官方抢同一次全量扫盘）。**需上报上游。**
* **profile 两个浏览器包已升线（2026-09-29 完成）**：`~/.dsh/profiles/web/package.json` 两条已改
  `0.2.0-rc.1` 并重装；重启 profile 后实测**零 `skipping profile bundle`、零 `disabling profile plugin row`**，
  浏览器工具恢复可用。
* **跟版检查脚本**：把"五个插件的精确 pin 必须等于单一真值"做成 `scripts/check-dsh-pin.mjs`，
  挂在根 `verify` 第一步（与 `check-no-local-paths.mjs` 并列），防止 pin 腐化成多个不同版本。
  （现状：五个活跃插件都已升到 `0.2.0-rc.1`，一致；已退役的 `dsh-vision-bridge` 仍钉 `0.1.5-rc.1`，不进 verify。）
* **本机 pnpm store 有一条坏索引（本轮卡住 verify 的真凶，与上游无关）**：
  `esbuild@0.25.12` 的 store 索引条目把 `lib/main.js` 映射成了 **0.28.1 的内容**
  （88706 B → 97214 B，8 处 `0.28.1`），其余文件与 registry tarball 逐字节一致；
  CLI 因此报「主程序与二进制版本不匹配」，`bundle client` 步炸。两点经验：
  ① `pnpm store status` 报 **untouched**、`pnpm install --force` 报 **Already up to date**，
  两者都抓不到；② 判定用最小复现工程（空目录只装这一个包）比在出问题的仓库里猜快得多。
  修法：删掉 store `index.db` 里该包的索引行后重装（会重新下载），或整份 `node_modules` 重建。
  注意 `node_modules` 里的目录被删后 `pnpm install` 不会补——需同时删 `node_modules/.pnpm-workspace-state-v1.json`。
* **客户端半边的混版隐患**：`dsh.client.inject` 里的 `@deepseek-ai/dsh-client-*` **不参与版本门**，
  却会被 esbuild 内联进 `lib/client.js`（external 白名单只有 react 系 + cordis + store + slots + primitives）。
  本版 `PLATFORM_MODULES` 未变，故当前无实际风险；是否 external 化或另加一道客户端格式门，单独评估。
* **应急通道**：跟版尚未完成、但需临时恢复时，可用
  `dsh plugin --profile web allow-version <包@版本> --dsh-version 0.2.0-rc.1 --accept-risk`
  （按「包@版本 + 精确 dsh 版本」授权，升级不继承）。属应急手段，不替代跟版。
