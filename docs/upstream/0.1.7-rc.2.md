# dsh-sparrow × dsh 0.1.7-rc.2 适配报告

> 适配对象：官方 checkout tag `dsh-v0.1.7-rc.2`（`787b746b80`）
> **本文件只记 rc.1 → rc.2 的增量**；rc.1 的完整报告见 [`0.1.7-rc.1.md`](0.1.7-rc.1.md)。
> 触发：owner 升级到 rc.2 后报「几乎所有插件又挂了」（六个活跃插件在启动时被版本门整批跳过）。

---

## 1. 结论

rc.2 让六个插件全部启动失败的直接原因是**版本门**（peer 依赖是**精确版本** `0.1.7-rc.1`，运行时是 `0.1.7-rc.2`，官方用 `semver.satisfies` 精确比对 → 全部判为不兼容并 skip）。

升线到 rc.2 之后，**只有 file-manage 有一处真破坏**（官方 `DeepSeekFilesClient` 构造签名 `apiKey` → `headers`），其余五个插件 typecheck / 测试零改动即可用；theme-tone 另有一处**必须跟着 rc.2 新材质架构走**的绘制层（官方新的 `MenuSurface` 把材质画进了 `z-index: -1` 的子元素）。

---

## 2. 根因：精确版本 peer 被 rc.2 判为不兼容

启动日志逐条写明了 skip 原因：

```
dsh: skipping profile bundle "@dsh-sparrow/dsh-theme-tone": Error: Plugin
  @dsh-sparrow/dsh-theme-tone@0.1.5-rc.2 is incompatible with dsh 0.1.7-rc.2:
  peerDependencies {"@deepseek-ai/dsh-settings":"0.1.7-rc.1"}. …
```

官方判定代码（`packages/boot/app-boot/src/plugin-compatibility.ts:71-79`）：

```ts
const requirement = ['workspace:^','workspace:~','workspace:*'].includes(range) ? runtimeVersion : range
if (requirement.trim() === '' || !semver.satisfies(runtimeVersion, requirement, { includePrerelease: true })) {
  peers[name] = range
}
```

即：**peer 写什么就按什么判**。仓库既定口径是「只承诺版本号所标示的那一条线」，写的是**精确** `0.1.7-rc.1`，所以 rc.2 一上线，六个插件里的五个（nav-pin 没有 dsh peer，不受影响）就被整批跳过 —— 这是**设计如此**的 fail-safe，不是 rc.2 的 bug。

**口径不变**：本次仍写精确 `0.1.7-rc.2`；日后每次 dsh 升 rc 都是同一件「正式适配任务」。

> ⚠️ 针对该口径的**待办**：`pnpm-workspace.yaml` 的 `minimumReleaseAgeExclude` 需要逐条放行 24h 内的新版本（pnpm 不支持带版本的 glob）。发布满 24h 后可整段删。

## 4. rc.2 真正影响我们的契约变化

### 4.1 `DeepSeekFilesClient` 构造签名 `apiKey` → `headers`（**真破坏**，唯一一处）

```diff
 interface FilesApiOptions {
   baseURL: string
-  apiKey: string
-  /** Use the DSH account header; omitted for ordinary API keys. */
-  accountCredential?: boolean
+  /** Provider-resolved authentication headers for this endpoint. */
+  headers: Readonly<Record<string, string>>
   fetch?: typeof fetch
 }
```

`packages/llm/llm-deepseek/src/files-api.ts:139-149`（rc.2）：构造只存 `headers`，请求时 `Object.entries(this.authHeaders)` —— 传旧参数 `apiKey` 时 `authHeaders` 是 `undefined`，**每次 list / delete 都在运行期抛错**，而**导出符号一个没少**，能力门（只查存在性）抓不到。

> **这正是「只钉 URL」抓不到的那类破坏**：URL 归一化没变，**变的是参数名**。

落点（`plugins/dsh-file-manage`）：

- `src/files.ts`：新增 `API_KEY_HEADER` / `authHeaders(apiKey)`；新增 `probeFilesClientShape(Client)` —— 用官方 client 自己的 request 路径跑一次**无网络**往返（fetch 由探针注入、端点是 RFC 2606 的 `.invalid`、带 2s 超时兜底），断言 key 头真的被发出去。
- `src/host.ts`：`DeepSeekSurface` 的构造面改成 `{ baseURL, headers, fetch? }`；三处构造点改为 `headers: authHeaders(connection.apiKey)`；`deepSeekSurface()` 里加**形状门**——探针不过就抛 `UNSUPPORTED_HOST`（宿主半边按既有约定自停用，文案「升级本插件后自动恢复」）。
- `test/base-url.test.mjs`：stub fetch 除 URL 外**同时钉住认证头**（`x-api-key` / `anthropic-version` / `anthropic-beta`），并补形状门的正反用例（rc.2 官方 client → true；只认 `apiKey` 的旧签名 → false）。

### 4.2 官方新材质层：`MenuSurface` 把填充 + 模糊画进 `z-index:-1` 的**子元素**

rc.2 新增共享菜单原语 `packages/client/ui-primitives/src/MenuSurface.tsx` + `MenuSurface.module.css`：

```css
.surface { isolation: isolate }           /* 自己成层叠上下文 */
.material { position: absolute; inset: 0; z-index: -1;   /* ← 官方材质是**子元素** */
            background: var(--dsw-menu-surface-fill);
            backdrop-filter: var(--dsw-menu-backdrop-filter) }
```

绘制顺序（元素自身背景 → **负 z-index 子层** → 块级 → 行内 → …）意味着：**我们画在元素 `background-image` 上的颗粒与光，会被官方这层材质整个盖住**。

修法：把同一串图层**再画一份到 `::before`**（`::before` 默认是行内级、`position: static`，绘制在「负 z-index 子层」**之后**）——
`plugins/dsh-theme-tone/src/surface.ts`：`SURFACE_ANCHORS` 与 `COMPOSER_CARD_ANCHORS` 各补一条 `…::before { background-image: … !important }`，**两层都留**（材质画在元素自己身上的那些面只有前一条生效）。

**真机 A/B 像素证据**（隔离实例 3098，官方 `[data-menu-material="translucent"]` 菜单，145×110）：

| 状态 | computed style | 与「无 `::before` 层」的像素差 |
| :--- | :--- | :--- |
| 元素 | `background-image` = 我方颗粒 SVG；`backdrop-filter: none` | — |
| `::before` | `background-image` = 我方颗粒 SVG；`position: static`；`z-index: auto` | 剥掉 `::before` 规则后：**mean abs diff 12.663 / px，最大通道差 181，92.48% 像素变化（>6）** |
| 子元素 `._material_*` | `position: absolute; z-index: -1; background: rgba(67,69,74,.45); backdrop-filter: blur(40px) saturate(1.5)` | 官方材质，画在我们元素级图层**之上** |

⇒ 那条 `::before` 不是冗余，**是 rc.2 下质感可见的唯一通道**。

### 4.3 菜单填充 token 改名（对 Windows 无影响）

`--dsw-specific-menu` 不再直接是 rgba，而是 `var(--dsw-menu-surface-fill)`（浅 `rgba(248,249,250,.58)` / 深 `rgba(67,69,74,.45)`），且 `html[data-platform='darwin'] body` 上另给近不透明值（macOS 原生 vibrancy 无法 backdrop-blur）。

我们所有弹层都用**官方成对写法**（`background: var(--dsw-specific-menu)` + `backdrop-filter: var(--dsw-menu-backdrop-filter)`），在 Windows（本机即 `data-platform` ≠ darwin）上语义不变 ⇒ **零改动**。

### 4.4 其余 rc.2 变更（核对过，不影响我们）

| 变更 | 核对结论 |
| :--- | :--- |
| `SESSION_FORMAT_VERSION` | rc.2 仍为 **4**（`packages/core/session/src/types.ts:89`）⇒ archive / chat-fim 的格式门集合 `[0,3,4]` 不变 |
| 官方 `llm-deepseek` 内部重构（`resolveAuth` / `discoverModels` / `listModels` / `MESSAGES_TOOL_CHANGES_BETA`） | 全是官方 adapter 内部面；codebuddy-credits 只用 `@deepseek-ai/dsh-llm` 的公开接口，typecheck 全绿 |
| 新圆角 token `--dsw-radius-*`、`--dsw-mask-blur: none`、新增 `focus.css` / `onboarding.css` | 我们没声明过这些面，不受影响 |

## 6. rc.2 期的追加修复（owner 真机报障）

升线之后 owner 在自己实例上陆续报了四条，都在 rc.2 上定位并修复。**这四条都是 rc.2 期的改动**，不属 rc.1 报告的范围。

### 6.1 顶栏浮层后右侧滚动条跑到顶栏下面

owner：「**咱们 theme-tone 的 bug，顶栏透明后，右侧滚动条也会跑上去。**」

**根因是一句 CSS 事实**：**滚动条画在滚动容器的 padding box 上，`padding-top` 只推内容、不推它。**
顶栏被浮层化后（rc.1 起），官方那条「顶栏在流内占 76px」的几何就没了，滚区顶到 y=0、正文首行被顶栏盖住 —— 因此本插件给滚区补了 `padding-top: 76px`。但滚动条不吃这一套：轨道与滑块仍从 y=0 起画，**前 76px 正落在半透明顶栏下面**（顶栏 = 70% 填充 + `blur(12px)`），于是以 1~3 级的淡痕透出来。

**修法**：改用 `border-top: 76px solid transparent` —— 同样是「推内容」，但它把 **padding box 整体下移** 76px ⇒ 滚动条与内容一起回到官方位置。配对声明 `box-sizing: content-box`（官方 `.scrollBody` 本来就是），否则 border-box 会让那 76px 从内容高度里扣掉。

真机三档对照（滑块染不透明橙，只在滚动条那一列逐像素扫描）：

| 档 | 滚区 clientHeight | 滑块顶端 y |
| :--- | ---: | ---: |
| 官方默认（顶栏在流内） | 680 | **78**（= 76 + 官方轨道 2px 边距） |
| 改前 `padding-top: 76px` | 756 | **0** ← 画进顶栏带 |
| **本版 `border-top: 76px`** | **680** | **78** ← 与官方逐项相同 |

复验：`offsetHeight` 仍 756（总高不变）、输入框座位位置逐像素不变、不产生页面级纵向溢出。验收含**改前对照**（把 `padding-top` 用提权选择器压回去，顶栏带内立刻露出 419px ⇒ 证明判据真能抓到这个现象）。

### 6.2 主题比官方卡 —— 定位到 `:has()` 选择器

owner：「**咱们主题明显比官方的卡。**」

**先造一个干净的判据**：前两轮我拿「官方档 vs 色调档」做 A/B，那个变量不干净（DOM 与 CSS 同时变）。改成**消融实验**：把页面切到色调档，**只** `styleEl.disabled = true/false` 切换本插件那三张样式表 —— DOM、色调值、React 树全不动，差值**纯粹**归因于本插件 CSS。

| 指标 | 插件 CSS 关 | 插件 CSS 开 | 倍数 |
| :--- | ---: | ---: | ---: |
| 变动密集 p95（150 帧 × 每帧插 6 节点） | 34.25 ms | **65.50 ms** | **1.91×** |
| 变动密集 样式重算 | 2.39 s | **6.37 s** | **2.67×** |
| 滚动 p95 | 18.45 ms | 18.95 ms | 1.03×（无差异） |
| 打字 p95 | 18.25 ms | 18.05 ms | 0.99×（无差异） |

⇒ 成本全在**样式重算**，且**只在有 DOM 变动时**出现 —— 流式输出正是最密集的场景。（顺带否掉「滚动/合成问题」这个猜测。）

**再把 151 条规则拆成变体**定位来源（同负载、两轮平均）：

| 变体 | 规则数 | 样式重算 |
| :--- | ---: | ---: |
| 原样 | 151 | **3.192 s** |
| 去掉全部 `:has()` | 139 | **1.216 s** ← 回到地板 |
| 只留 `:has()` | 12 | **2.809 s** ← 12 条吃掉约 62% |
| 151 条**平凡**规则（`.zzz-N{color:inherit}`） | 151 | 1.256 s ← 与空表持平 |
| 空表 | 0 | 1.382 s |

⇒ **规则条数无关**（平凡规则 ≈ 空表），**开销集中在 `:has()` 上**。逐条隔离后最贵的三条里两条是**重复守卫**：`[role=menu]:has([role=group]) > :has([role=group])`（+1.533s）、`[role=menu]:has([role=group]) [role=group] > :first-child`（+1.381s）。

**修法：删掉冗余的守卫**（严格等价，不是近似）。后半段本身已经要求 `[role='group']` 存在，那个 group 在菜单里 ⇒ 菜单自然有分组 ⇒ `:has([role='group'])` 冗余：

```
menu:has(group) group > :first-child  ≡  menu group > :first-child
menu:has(group) > :has(group)         ≡  menu > :has(group)
```

真机逐元素验证（菜单**开着**与**关着**两态）：命中集合数量与逐个 `isSameNode` **完全一致**（开 3/3、3/3、1/1；关 0/0、0/0）。收益（真机，交付物 vs 运行时注入旧写法，各三轮交替）：**样式重算 6.314s → 5.157s（0.82×，省 18%）**，两轮对照各自复现（0.77× / 0.85×）。

⚠️ 给菜单本体上料的那条**必须保留** `:has()` —— 那里没有别的锚点能表达「带分组的菜单」，去掉会命中页面上所有菜单。测试里同时钉住这两侧（不得删过头）。

**同时否掉的两个猜测**（都做了对照，避免「看起来像」就当结论）：① **`background-attachment: fixed` 的多层渐变**（静态审计强烈怀疑的那条）：把 `fixed` 换成显式视口盒后滚动 p95 **无差异**；② **两条 `body` 子轴 `:has()`**：逐条实测净增 **≈ 0**（−0.34s / +0.02s，均在噪声内）—— 它们命中 0 个元素，而**只有命中元素的 `:has()` 才付费**。另外量了**颗粒贴图**（`feTurbulence` 的 octaves 4/2/1、换成 PNG 噪声）：栅格化与滚动 p95 全部落在噪声内 ⇒ **纹理本身不是瓶颈**，不值得为性能换实现。

### 6.3 颗粒强度降到 75%

owner：「**现在所有噪点是统一的配置么？我想把噪点往下降一点。**」

**答：是统一的** —— 唯一旋钮 `GRAIN_ALPHA = { light, dark }`（见 [`0.1.7-rc.1.md`](0.1.7-rc.1.md) §5.6），派生两路：伪元素路（`opacity: var(--dsh-theme-tone-grain-alpha)`）与浮层路（alpha 预乘进 SVG，因为 `background-image` 图层没有独立 opacity）。两个 token 都是插件在运行期写进 **`body` 行内 style 的同一次写入**，改动时两路**同步跟随**（0.0975 → 0.05 → 0.02 逐档一致）⇒ 本来就统一，**不需要改造**。

**降强度**：深色轴 `.13` → **`.0975`**（= 75%）。真机 8× 放大逐档对比后由 owner 选定。实测（对话列内 64×64 无文字干净区）：

| alpha | 均值（亮度） | 标准差（纹理） | 相对原值 |
| ---: | ---: | ---: | :--- |
| 0.13（原） | 23.83 | 2.273 | — |
| **0.0975（本值）** | **21.23** | **1.719** | 纹理 −24% |

差值图（|改后 − 改前| ×12）单调均匀、无局部假象。浅色轴 `.16` **本次不动**。

> ⚠️ **深色轴降强度会同时压暗底色**（23.83 → 21.23）—— `screen` 加法混合的物理必然（白点在暗底 = 加亮），不是取值没调好。要「纹理变淡但底色不变」得另配底色补偿，**本轮没做**。

交付物复核：伪元素路 `::after` opacity = 0.0975；浮层路（菜单）元素本体与 `::before` 两处烘的 alpha 也都是 0.0975 ⇒ **两路一致**。
