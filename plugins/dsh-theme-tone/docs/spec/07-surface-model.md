# 07 · 表面模型（统一）— dsh-theme-tone

> **本篇是「抬升面」（弹层 / 顶栏 / 停靠卡 / 输入卡）的唯一规范。**
> 与 `05-surfaces.md`、`04-glass.md` 冲突时，以本篇为准；那两篇保留为「机制与实证记录」。

## 1) 为什么需要这一篇（审计实证，不是感觉）

owner 连续四次反馈都指向同一件事：**同类元素的配置不一致**。

| owner 原话 | 表面症状 | 真实根因（已查证） |
| :--- | :--- | :--- |
| 「弹出元素还是噪点太重了，和背景不是一个档位」 | 弹层颗粒偏重 | 弹层**被画了两遍**（元素级 + `::after`），地面只有一遍 |
| 「设置弹窗的打光和其他的好像不一样」 | 设置弹窗缺一道光 | 浮层配方**漏了左光**（`LEFT_VARIABLE` 在 surface.ts 里从未出现） |
| 「设置页 / 子代理 / 后台任务 / 模型列表的顶光，明显比别的元素强」 | 弹层光偏强 | 无补偿；且「份数」不一致（见 §1.2） |
| 「todo 列表我刚发现没有打光了」 | todo 无光 | 它走了**另一份配方**（`menuSurfaceLayers`，只有底光） |
| 「顶部的光被顶栏挡住了」 | 顶栏那条带偏暗 | 顶栏光跟着填充 α 一起乘了 0.7 |

**结论：这些不是五个 bug，是「一个模型缺位」的五个症状。** 所以本篇先定模型，再改代码。

### 1.1 现状：同一件事有四条路

| # | 谁 | 在哪 | 画什么 |
| :--- | :--- | :--- | :--- |
| 路 1 | 地面 | `backdrop.ts`（插件自有 fixed 层） | 三道光 + `::after` 颗粒 |
| 路 2 | 面板族 | `surface.ts` 的 `surfaceLayers()` | 颗粒 + 三道光（元素级 **与** `::after`） |
| 路 3 | 矮条族 | `surface.ts` 的 `menuSurfaceLayers()` | 颗粒 + **只有底光** |
| 路 4 | 顶栏 / 输入卡 / 右栏 | `glass.ts` 自画 | 三道光（按各自的规则重采样）+ 自己的模糊 |

同一份「质感配方」被抄了四遍，任何一次调整都要改四处 —— 漏一处就是 owner 看到的那种不一致。

### 1.2 现状：同一个面上，各层的**份数不一样**（computed style 实测）

| 表面 | 元素级 | `::after` | 净结果 |
| :--- | :--- | :--- | :--- |
| 地面 | 3 道光 | 颗粒 | 每道光 **1 份**、颗粒 **1 份** |
| 设置弹窗 | 3 道光 + 颗粒 | 3 道光 + 颗粒 | 每道光 **2 份**、颗粒 **2 份** |
| 模型菜单（分组） | **1 道光** + 颗粒 | 3 道光 + 颗粒 | 底光 **2 份**、顶/左光 **1 份**、颗粒 **2 份** |

第三行是最刺眼的：同一个菜单上，**底光被画两遍、顶光和左光只画一遍**。

机制（已逐条核验，见 §8 核验脚本）：

* 分组菜单元素**同时匹配**两条规则 —— 通用的 `[role='menu']` 与专用的
  `[role='menu']:has([role='group'])`；
* **元素级**由专用规则胜出（特异度更高）⇒ 只有 2 层（颗粒 + 底光）；
* **`::after`** 只有通用规则那条（专用规则**没有** `::after` 版本）⇒ 仍是 4 层（三道光）；
* 净结果：底光 2 份、顶光 1 份、左光 1 份、颗粒 2 份。

**这就是「配置不统一」的字面含义** —— 不是谁没调好，是两条规则各自只覆盖了一半。

### 1.2b 关键条件：元素级那层**有没有被盖住**，取决于**谁渲染了这个弹层**

「画了两遍」只有在**两层都可见**时才等于「重一倍」。官方有些组件会渲染一个
`z-index: -1` 的材质子元素（`MenuSurface.tsx:35` 的 `data-menu-material="translucent"`
+ `.material` 带 `backdrop-filter`），它盖在元素背景之上，会**把元素级那层洗掉** ——
那种情况下双层无害。而**插件自有组件不会渲染它**。

真机实测（computed style + DOM）：

| 表面 | 渲染者 | 官方材质子元素 | 元素级那层 |
| :--- | :--- | :--- | :--- |
| 模型菜单（`.ccb-model-menu`） | **本仓库 `dsh-codebuddy-credits`** | **无** | **直接可见** ⇒ 与 `::after` 叠加 |
| 设置弹窗 | 官方 `Modal`（`.dialog` 本身无材质子元素） | **无** | **直接可见** ⇒ 与 `::after` 叠加 |

⚠️ **口径说明**：上表「模型菜单」测的是**插件自有**的菜单；官方 `MenuSurface` 系
（`ModelSelect` / `MenuView` / `TabMenu` / `PopupSelectView`）源码里**确实有** `.material`。
两类都命中我们的 `[role='menu']` 锚点。

⇒ **同一个锚点，因渲染者不同而得到两种结果**（洗掉 / 叠加）。这是 §1 那种
「同类元素观感不一致」最根本的来源 —— **它不可从我们的锚点表预测**，因为取决于官方组件实现。
**M2（收敛为单载体）正是为消除这种不可预测性。**

> 本条修正过一次：初版把上表第一行写成「模型菜单」，未注明它是插件自有的
> —— 而那次测量的结论（无材质子元素）**不能**外推到官方 `MenuSurface`。
> 这类「拿一个样本代表一类」的推断正是本仓库反复踩的坑，故保留此注。

### 1.3 现状：三套强度口径 + 一个变量两条管线

| 项 | 地面 | 弹层 | 顶栏 |
| :--- | :--- | :--- | :--- |
| 光强系数 | 1.0（基准） | 0.7（`POPUP_LIGHT_COMPENSATION`） | 1.0（`HEADER_LIGHT_SCALE`） |
| 颗粒强度载体 | CSS `opacity` + 运行期变量 | **烘进贴图**（`<rect opacity>`） | — |
| 颗粒混合 | `mix-blend-mode: screen` | 无 | — |
| 运行期可调 | ✅ | ❌（烘死了） | — |

**同一个「噪点统一变量」在两条管线上含义不同** —— 这就是 owner 说
「我记得不是统一的一个变量么」却调不动弹层的根本原因。

## 2) 统一模型

### 2.1 一句话

> **任何一个抬升面 = 底色 + 颗粒 + 三道光（顶 / 底 / 左）。**
> 这四层的**来源、几何、强度**全部由下面三张表决定；除此之外不允许有第四种写法。

### 2.2 构成（自下而上）

> **「四层」= 颗粒 + 顶光 + 底光 + 左光**（我们画的部分）。
> 底色**不算**在这四层里 —— 它是官方的，我们只染值、不新增层。

| 序 | 项 | 来源 | 归属 |
| :--- | :--- | :--- | :--- |
| — | 底色 / 材质 | 官方 token（我们只染值） | 官方 |
| 1 | 三道光（顶 / 底 / 左） | `--dsh-theme-tone-{top,bottom,left}` | 我们 |
| 2 | 颗粒 | `--dsh-theme-tone-grain-*` | 我们 |

### 2.3 表面只有三类（按**尺度**分，不按组件分）

| 类 | 几何尺度 | 成员（举例） |
| :--- | :--- | :--- |
| **A 地面** | 视口 | 背景层 |
| **B 面板** | 自身盒子 | 对话框 / 菜单 / 卡片 / hover 卡 / 顶栏 / 右栏 / 输入卡 |
| **C 矮条** | 自身盒子（扁） | todo / goal-bar / queue-dock / 分组菜单 |

**三类都拿那四层**，差别只在几何与强度 —— **不再有「某类没有某道光」这种配置**。

## 3) 规范表（normative）

### 3.0 新增锚点的**三条前置条件**（MUST —— 2026-09-27 血泪）

> 这一节是因为我在**同一天、同一个锚点上**连犯两次而补的。两条都**不是**"调参"，
> 而是 `::after { position: absolute; inset: 0; z-index: -1 }` 这个载体的**前提条件**。
> **新加任何锚点，先逐条验证这三条，再谈观感。**

| # | 前置条件 | 不满足会怎样 | 怎么补 |
| :--- | :--- | :--- | :--- |
| **P1** | 元素自己**形成层叠上下文** | `z-index:-1` **逃逸到父层**，被元素**自己的不透明背景**盖住 ⇒ **纹理完全不可见**（实测 0/40000 绿点） | `isolation: isolate` |
| **P2** | 元素是**定位祖先**（自己或祖先链上有 positioned） | `inset:0` 的包含块退到**视口** ⇒ **纹理铺满全屏**（实测卡外 78013/78750 红点） | `position: relative`（**仅 static 元素**：见 P2 警告） |
| **P3** | 锚点带 `body ` 前缀 | `gatedAnchor()` 静默不替换 ⇒ **官方默认档也生效**，破坏「官方默认不动」底线 | 写 `body …` |

**哪一条缺，症状完全不同**，别混（我混过）：

| 缺失 | 症状 | 实例 |
| :--- | :--- | :--- |
| P1 | **完全看不到**纹理 | 归档页 / 云文件页（`z-index:auto` + 无上下文） |
| P2 | 纹理**满屏乱铺** | 问答卡（`.card` 是 `static`） |

⚠️ **P2 的补法只能给"实测为 static"的元素用**：本表多数锚点本就是 `absolute` / `fixed`，
统一盖上 `position: relative` 会**把绝对定位改成相对定位** ⇒ 弹层当场错位。
故维护 `STATIC_SURFACE_ANCHORS` 白名单（新增前先实测 computed `position`）。

> 归档/云文件的 dialog 自带 `relative` ⇒ 只缺 P1；
> 问答卡的 `.card` 两样都缺（static + 无上下文）⇒ P1+P2 都要。
> **这就是"codebuddy 弹层能行、别的面不行"的完整答案**：
> codebuddy 弹层带 `z-index:20`（P1 天然满足）；官方 `.card` 一样都没有。

### 3.1 图层构成（MUST）

* 每个表面**必须**同时拿到：颗粒、顶光、底光、左光。缺任何一个都是 bug。
* 每层**只允许由一个绘制载体承担**。禁止「元素级 + 伪元素各画一份」。
* **载体可以是哪个由锚点决定**（不强制统一为 `::after`）：
  * 官方材质在元素自身 / 有负 z 子元素 ⇒ 用 `::after`（当前主通道）；
  * 官方已占用 `::after`（如 QueueDock 的 `.panel::after` 是 0.5px 描边）⇒
    **补官方自己的 `::before`**，不抢官方层（`OFFICIAL_BEFORE_LAYER_ANCHORS`）；
  * **但同一锚点下，那四层必须落在同一个载体里**，不得拆开。

> 为什么必须收敛到单载体：现状的双层不是设计，是历史叠加的产物 —— 它让强度变成
> 「两层之和」，任何按单个 alpha 做的定标都失效（我为此连错两轮：先定 0.33、后改 0.7）。

> ⚠️ **2026-09-27 验证**：单载体（只留 `::after`）在**官方 `MenuSurface` 系菜单**上成立
> —— 官方那个 `z-index:-1` 的 `.material` 子元素**不会**盖住我们的 `::after`。
> 判据是布尔而非像素：用**与插件同款选择器**（特异性相等）把 `::after` 设纯红、
> 把 `.material` 设纯蓝，同开时读到 `(255,0,0)` ⇒ 红在上。
> 「怎么证明探针真的生效」这一步是必需的 —— 我先前两次得出"被盖住"的结论，
> 都是探针本身错了（一次坐标取整、一次 CSS 特异性）。

> ⚠️ **别把「玻璃」当成「少画一层」的许可证**：顶栏那类玻璃**同样出颗粒**
> （它走 `grainOverGradients()` 把颗粒与三道光一起画）。我曾在上一版本条里写
> 「玻璃只出三道光、不出颗粒」—— 那是**凭印象写的**，与源码不符，已删除。
> 玻璃与实色面的差别在**混合方式与自身填充**，不在"少一层"。

### 3.2 几何（三档，常量化）

| 档 | 顶光 | 底光 | 左光 | 收束（顶/底/左） |
| :--- | :--- | :--- | :--- | :--- |
| A 视口 | `ellipse 80vw 45vh at 50% -10vh` | `ellipse 70vw 45vh at 50% 112vh` | `ellipse 38vw 58vh at 0% -6vh` | 62% / 95% / 68% |
| B 面板 | `ellipse 120% 42% at 50% -12%` | `ellipse 110% 52% at 50% 112%` | `ellipse 42% 58% at 0% 0%` | 76% / 76% / 76% |
| C 矮条 | 同 B | 同 B | `ellipse 38% 50% at 0% 0%`（缩一档） | 同 B |

**矮条档曾经的「省略顶光与左光」被否决**：那会让 todo / goal-bar / queue-dock
完全没有光（owner 已实测发现）。**矮条真正需要的是更小的几何，不是更少的层。**

> 注：C 档当前不存在（那三个锚点正走 `menuSurfaceLayers`，只有底光）——
> 本行是 **M3 的目标值**，实现时须真机复核「矮条上顶光是否读得出」；若读不出，
> 回到 §7 Q2 重新决策，**不得**默默退回「省略」。

### 3.3 强度（一张表，每个数都要有实测理由）

| 类 | 光强系数 | 颗粒 alpha | 理由 | 置信度 |
| :--- | ---: | :--- | :--- | :--- |
| A 地面 | 1.0 | `GRAIN_ALPHA` 原值 | 基准，owner 已定值 | 高 |
| B 面板 | 0.7 | 同原值 | 同一屏幕位置上与地面**等 alpha**（解析解 0.69） | **中**（见下） |
| C 矮条 | 0.7 | 同原值 | 与 B 同族；几何更小已足够压「整条变亮」 | **低**（M3 后复测） |
| 顶栏 | 1.0 | — | 它是**玻璃**，光要透出来；按填充 α 压会让整条带偏暗 | 中 |

**规则：强度系数只能来自本表。** 任何就地写死的系数（如某条规则里手写 `70%`）都算 bug。

> ⚠️ **0.7 的置信度只到「中」，理由必须写清**：
> 那个解析解（逐点解 `alpha浮层 = alpha地面`，得 0.69）**本身是可信的** ——
> 它只依赖两边锁定常量，且与一次独立的像素实测吻合（解析预测 0.47、实测 0.48）。
> **但它解的是「单层」的 alpha**，而现状是**两层叠加** ⇒ 叠加后的实际观感会**更强**，
> 所以 0.7 很可能是**偏亮**的。
> 早先那次「按总量定标得 0.33」的扫描虽然被我判为量具错误（只覆盖元素级），
> 但它指向的方向（**实际需要比 0.7 更低**）与这个推理一致。
> ⇒ **M5 必须在 M2（单载体）之后重新定标一次**，届时 0.7 大概率要下调。
> 这不是「0.7 错了」，是**它的前提（单层）在现状下不成立**。

### 3.4 颗粒（MUST：单一来源、单一管线）

* **唯一常量**：`GRAIN_ALPHA`（每轴一档）。运行期经由 `--dsh-theme-tone-grain-alpha` 可调。
* **唯一管线**：伪元素 + `background-image: <贴图>` + `opacity: var(--dsh-theme-tone-grain-alpha)` + 该轴的 `mix-blend-mode`。
* **废弃「把 alpha 烘进贴图」那条管线**（`grainTileUri(alpha)` 预乘）：
  它让运行期变量对弹层失效，是「一个变量两条管线」的来源。
* 贴图本身**不带 alpha**（单一 `GRAIN_DATA_URI`）。

> 副作用（正面）：弹层与地面**共用同一个运行期变量** ⇒ owner 再调噪点，两处一起动。
> 副作用（需实测确认）：`mix-blend-mode` 会让同 alpha 的观感与现状不同 ⇒ §3.3 的
> 0.7 需在实现阶段重新定标一次（这次是**同口径**的，不再有双层混淆）。

> ⚠️ **为什么载体必须是 `::after`（不是随便选一个）**：实测三种载体的**有效可见度**
> （把该伪元素设纯绿、读有效 alpha `(g−base.g)/(255−base.g)`，取样取表面正中、避开圆角）：
>
> | 载体 | 对话框（无官方材质子元素） | 官方菜单（有 `.material`） |
> | :--- | ---: | ---: |
> | **`::after`** | **1.00** | **1.00** |
> | `::before` | 0.99 | **0.57**（被 `.material` 半盖） |
> | 元素级 | 最差 | 最差 |
>
> ⇒ **`::after` 是唯一处处足额的载体**。这条约束同时**否决了 M5**
> （把颗粒拆到另一个载体，以便用 CSS `opacity` 单独调它）—— 详见 08 §9.3。

## 4) 性能预算（硬约束）

> owner：「咱们现在还是比官方原版卡」。性能与视觉**同级**，不是事后优化。

### 4.1 实测基线 —— ✅ M0 已换量具，得到**可重复**结论

> owner：「咱们现在还是比官方原版卡」。**这条观测为真，且已量化。**

旧量具（累计耗时）同条件三次给出 +13.5 / +6.7 / **−3.6 ms**，离散度大于信号 —— **已废弃**。
M0 换成 **每帧 rAF 间隔的 P95**（对样本数不敏感，直接对应「卡顿」体感），
固定交互序列（5×wheel + 30×mousemove），预热后记录，两档各 3 轮：

| 档位 | 轮 1 p95 | 轮 2 p95 | 轮 3 p95 | 离散 |
| :--- | ---: | ---: | ---: | ---: |
| 插件开启 | 24.2 | 24.0 | 24.1 | **0.2 ms** |
| 官方默认档 | 19.1 | 19.6 | 19.3 | **0.5 ms** |

| 指标 | 插件均值 | 官方均值 | **差** | CV（插件/官方） |
| :--- | ---: | ---: | ---: | ---: |
| p50 | 17.2 | 16.7 | +0.5 | 1% / 0% |
| **p95** | **24.1** | **19.3** | **+4.8 ms** | **0.8% / 2.6%** |
| p99 | 28.0 | 23.1 | +4.9 | 2% / – |

⇒ **量具可用**（CV 均 < 5%），**插件确实比官方慢 ≈4.8 ms@P95（≈0.29 帧）**。
方向与 owner 的手感一致，幅度可复现（第二次独立运行：25.6 vs 21.5 = **+4.1 ms**，同量级）。

⚠️ **归因尚未成功**（如实记录）：按「关掉某张样式表看 P95 回落」做的第一次归因**不可信** ——
我的分类器把两张表都判成「含 backdrop-filter」，于是「关 glass」实际把两张都关了，
读数（18.5 / 18.4）互相矛盾且低于官方档（21.5），说明分类错误。
**M9 需改用「按唯一内容特征逐表识别」再归因**（例如按各表独有的选择器字符串匹配）。

⚠️ **归因已完成（M9，2026-09-27）—— 结果出乎意料，见 §4.1b。**

### 4.1b ⚠️ 性能的头号来源是**地面层的 `mix-blend-mode`**（占全部增量）

M0 那次归因失败的原因已查清：插件把六张样式表**拼成一张** `<style>` 注入，
所以「按样式表开关」不可用（两张表都含 `backdrop-filter`，分类器把它们判成了同一张）。
M9 改用**按规则类别逐条禁用**（遍历 CSSOM、把某类规则的 `style` 清空）：

| 类别 | 规则数 | 字节 | 关掉后省 |
| :--- | ---: | ---: | ---: |
| `backdrop`（`.dsh-theme-tone` 背景层） | 15 | 3208 | **3.9 ms** |
| `overlay`（伪元素覆盖层） | 26 | 17283 | **3.7 ms** |
| `anchor`（锚点规则） | 27 | 6457 | −1.4 ms（噪声） |
| `mask`（遮罩变量） | 1 | 48 | −0.3 ms（噪声） |

**两项各 3.8 ms 却不相加** ⇒ 说明有共享的来源。逐个假设检验后定位到：

> 真正的大头是**背景层的 `mix-blend-mode: screen`**：单独去掉它省 **4.88 ms**，
> 而插件相对官方的总增量就是 **4.87 ms** —— 去掉后**与官方持平（−0.01 ms）**。
> （`backdrop`/`overlay` 之所以"各省 3.8"，是因为它们都把颗粒画在那一层混合之上，
> 拿掉任一侧都会连带削弱整个混合层的可见工作量。）

复核方式：10 轮交替顺序（screen / normal / 官方各 5 轮，A/B 交替两遍）以排除漂移。

#### ⚠️ 2026-10-08 修正：上面这轮归因**量具不可信**，结论已被取代

那次用的是**累计耗时**（含首帧、受调度抖动影响），离散度可达 ±90 ms —— **大于**单个规则的真实效应。
当时就自相矛盾（本表同时列出「两类各 3.8 ms」「mix-blend 4.88 ms = 全部增量」，
而那两类正各自包含一层混合）。改用 **CDP `Paint` 分项 + 绘制次数 `paintN`**（计数比耗时稳得多）
并把判据改成**同轮内 A/B 交替取差**后，真实归因是：

| 归因对象 | 结论 |
| :--- | :--- |
| `mix-blend-mode: screen` | **有成本**（隐藏整层省 140–238 ms），但**随视口尺寸变化**，小视口测不出 |
| **`background-attachment: fixed`** | **主因**，且与图片面积无关、各视口一致 |

⇒ 「去掉 blend 就与官方持平」不成立（那是 1280×720 下的一次读数）；**主因是 `fixed`**。
完整实测见 [`10-fixed-attachment-cost.md`](10-fixed-attachment-cost.md)。
本节的旧数字**保留作历史记录**，不要再据此下结论。

### 4.1c 首先澄清：**「提高 alpha 补偿」这条路走不通**（已实测）

思路：`screen` 与 `normal` 在小 alpha 下差别不大，能否**提高 alpha** 补偿回来？
（把地面那三道光与颗粒的 alpha 调高，用 `normal` 达到同样的观感。）

实测（整屏 22374 点逐像素比对，基准 = 现状 screen；**两层同时**改 `normal`）：

| 补偿 | 与 screen 基准的平均差 |
| ---: | ---: |
| 100%（同 alpha，不补偿） | **1.293 级** |
| 115% / 130% / 145% / 160% / 190% / 230% | 2.69 级（**全部更差**） |

⇒ **补偿方向是错的**：提高 alpha 让整体更亮，离 screen 版更远（1.29 → 2.69）。
`screen` 在小 alpha 下不是「更弱」，而是**把噪声按加法提亮**（这正是颗粒质感的来源），
普通合成做不到这一点。

⚠️ 期间又踩了同一个坑并修正：第一次补偿测试用 `document.body.style.setProperty(...)`
去改地面的光变量 —— 而**地面的变量写在背景层元素自己的 inline style 上**，
body 上的同名变量对地面**完全无效**，于是读数恒为 1.292（那不是"补不回来"，是没改成）。
这正是本仓库记过的坑，我在同一件事上第二次踩到。

> ⚠️ **但这条只否掉了「补偿」这一个办法，不等于「无解」** —— 下一节发现
> **成本其实只在渐变那一层**，于是存在一个部分兼得的方案。两节合起来才是完整结论。

### 4.1d 能否既省这 5 ms 又保住观感？——**部分可以**（M9 追加实测）

关键发现：**成本在「三道光」那层的混合上，不在颗粒层上**（地面层结构是
`.dsh-theme-tone`（元素，画三道光）+ `.dsh-theme-tone::after`（颗粒），各自可单独设混合模式）。
四种组合实测（观感 = 与现状逐像素差，整屏 22374 点）：

| 组合 | 省 | 观感差 |
| :--- | ---: | ---: |
| ① 现状：元素 `screen` + 颗粒 `screen` | 0 | 0 |
| **② 元素 `normal` + 颗粒 `screen`** | **4.15 ms** | **0.744 级** |
| ③ 元素 `screen` + 颗粒 `normal` | −1.02 ms（更慢） | 0.535 级 |
| ④ 两层都 `normal` | 4.05 ms | 1.295 级 |

⇒ **② 是唯一「省得多 + 差得少」的组合**：省 4.15 ms，观感差只有两层都正常混合的 **57%**。
（③ 证明颗粒层不能省 —— 它反而更慢；④ 证明「都去掉」既省也没省更多、却差一倍。）

②的差异分布（正数 = 变暗）：

| 区域 | 平均差 |
| :--- | ---: |
| 顶光带 | 0.543 |
| 左光带 | **1.021** |
| 中部暗区 | 0.518 |
| 右下角 | 0.761 |
| 全屏 | 0.750（**最大 12.67**） |

⇒ 近似**均匀变暗**（各分区 0.52–1.02），但**局部最大 12.67 级** —— 光带边缘有可见台阶。
**alpha 补偿救不回来**：给渐变补 105%~145% 反而让差从 0.744 涨到 2.20（方向错了，
同 §4.1c：`screen` 是加法提亮，抬 alpha 只会整体更亮）。

### 4.1e 结论：三条路，交 owner 决定（Q7）

| 方案 | 性能 | 观感代价 | 风险 |
| :--- | :--- | :--- | :--- |
| **① 保持现状** | 慢 4.9 ms@P95（≈0.29 帧） | 0 | 无；已在 Q5 达标线（≤2 帧）内 |
| **② 渐变层改 `normal`、颗粒保留 `screen`** | **省 4.15 ms ⇒ 与官方持平** | 全屏均匀暗 0.75 级；光带边缘最大 12.67 级 | 最大 12.67 是**局部台阶**，肉眼可能看得见 —— 需真机复核 |
| ④ 两层都 `normal` | 省 4.05 ms | 1.295 级 | 最省但观感损失翻倍，不划算 |

> 我的建议：**先不做，或只做②并真机复核**。理由：
> * 现状 0.29 帧已在 Q5 达标线内，「更卡」的手感主要不该由它承担 —— 但 owner 说「还是比官方卡」，
>   而②是**唯一**能把这项归零的路；
> * ②的代价是**均匀变暗 0.75 级**（可接受，约等于亮度差 3%）+ **局部最大 12.67 级**（不可接受的风险点）。
>   局部台阶出现在光带边缘 —— 那正是 `screen` 让光「融进」背景的地方，`normal` 会留下硬边。
> * ⇒ **建议**：实现②并真机看光带边缘；若台阶可见则回退到①。**不要**为了这 4 ms 牺牲光带质感
>   （owner 反复强调过「打光」是他的核心关注点之一）。

### 4.2 静态结构成本（确定性统计，可重复）
| 模块 | 规则数 | 字节 | `:has()` | `backdrop-filter` | `position: fixed` | `!important` |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| surface.ts | 32 | 15164 | **8** | 0 | 0 | **36** |
| glass.ts | 19 | 7795 | 0 | **3** | 0 | 1 |
| backdrop.ts | 11 | 1844 | 0 | 0 | **1**（全屏 + `mix-blend-mode`） | 0 |
| **合计** | **62** | **24803** | **8** | **3** | **1** | **37** |

已知的三个结构性隐患：

1. **全屏 `mix-blend-mode` 层**（地面）：视口每帧都要参与混合。
2. **8 处 `:has()`**：每轮样式重算对全文档求值；其中 `body > :has(> [role='tree'])`
   （复杂度 7）与三处 `:has(> …)` 只为极少数浮层服务。
3. **37 处 `!important`**：与官方同特异度规则军备竞赛，任何官方改动都可能失配。

### 4.3 预算（MUST，实现阶段逐条核）

> 术语严格区分，勿混：
> * **层（layer）** = `background-image` 里的一项（颗粒 / 顶光 / 底光 / 左光）⇒ 每个表面**恒为 4**。
> * **载体（carrier）** = 实际参与绘制的盒子（元素本体 / `::before` / `::after` / 子元素）
>   ⇒ 每个表面**只许 1 个**。现状有 2 个（元素级 + `::after`），这是强度失控的根源。

| 约束 | 上限 | 现状 | 差 | 类型 |
| :--- | :--- | :--- | :--- | :--- |
| 每表面**层数** | 恰好 4 | 2 或 4（按表面而异） | ❌ | 静态 |
| 每表面**绘制载体数** | **1** | 2（元素级 + `::after`） | ❌ | 静态 |
| `:has()` 规则数 | **≤ 5**，每处配断言 | 8 | ❌ | 静态 |
| `position: fixed` 全屏层 | ≤ 1 | 1 | ✅ | 静态 |
| `mix-blend-mode` 全屏层 | ≤ 1 | 1 | ✅ | 静态 |
| `background-attachment: fixed` | **0（禁止）** | **13 处**（真实全量）：座底带 / 卡片缺口 / 顶栏 / 吸顶行 / 轨迹铺满 / 三处缝挡板 / 分组标题条… | ❌ | 静态 |
| `!important` | 仅用于压过官方同特异度规则，逐处注明理由 | 37（多数无注明） | ❌ | 静态 |
| 主线程增量 | **待量具（M0）后再定** | 不可测 | — | 时间 |

**只有「静态」列是可验收的**；时间项在 M0 完成前不设数值。

> `background-attachment: fixed` 已在本仓库踩过一次坑（百分比几何按视口而非盒子解析，
> 76px 高的顶栏会被重采样成硬边带），且滚动时要求整条带重新采样 ⇒ 列入禁止项。
> 顶栏改用**盒子内几何 + 显式 `100vw/100vh` 对齐**（右栏已经这么写了，可复用其做法）。
>
> ⚠️ **2026-10-08：又多了一条更硬的理由** —— 它还是**滚动卡顿的主因**
>（定位区 = 视口 ⇒ 每帧按视口栅格化；且与图片面积无关：声明尺寸缩到 1/225 也不省）。
> 已先修**两条真正在滚动容器内**的规则（座底带 + 卡片缺口），实测 Paint **−81%** / 绘制次数 **−56%**；
> 其余各条本页命中 0 或不参与滚动重绘，逐条处理留待后续 —— 见
> [`10-fixed-attachment-cost.md`](10-fixed-attachment-cost.md)。
> 上表原写「现状 1（顶栏）」是**旧统计的口径错误**（只扫了单张样式表）：真实是 **13 处**。

按单层 alpha 定出来的系数必然是错的（我已为此连错两轮：先定 0.33 后改 0.7）。

## 6) 验收标准

1. **构成一致**：任取一个抬升面，computed 层数 = 4（颗粒 + 三道光），各 1 份。
2. **强度一致**：同一类的光强与颗粒强度系数取自 §3.3 表，无就地硬编码。
3. **变量一致**：颗粒与光各只有**一个**运行期变量，改它即全场景同步。
4. **性能达标**：§4.3 七项逐条通过；主线程增量 ≤ +15%。
5. **官方默认不动**：`PLAIN_ATTR` 档下逐像素与官方一致（沿用既有守卫）。
6. **测试钉住**：上表每一项都有断言；关键项做**反向注入**（改坏能测出来）。
