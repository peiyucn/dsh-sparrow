# 07 · 表面模型（统一）— dsh-theme-tone

> **本篇是「抬升面」（弹层 / 顶栏 / 停靠卡 / 输入卡）的唯一规范。**
> 与 `05-surfaces.md`、`04-glass.md` 冲突时，以本篇为准；那两篇保留为「机制与实证记录」。

## 1) 为什么需要这一篇（审计实证，不是感觉）

owner 连续四次反馈都指向同一件事：**同类元素的配置不一致**。

| owner 原话 | 表面症状 | 真实根因（已查证） |
| :--- | :--- | :--- |
| 「弹出元素还是噪点太重了，和背景不是一个档位」 | 弹层颗粒偏重 | 弹层**被画了两遍**（元素级 + `::after`），地面只有一遍 |
| 「设置弹窗的打光和其他的好像不一样」 | 设置弹窗缺一道光 | 浮层配方**漏了左光**（`LEFT_VARIABLE` 在 surface.ts 里从未出现） |
| 「设置页 / 子代理 / 后台任务 / 模型列表的顶光，明显比别的元素强」 | 弹层光偏强 | 无补偿；且「份数」不一致（见 §1.2） |
| 「todo 列表我刚发现没有打光了」 | todo 无光 | 它走了**另一份配方**（`menuSurfaceLayers`，只有底光） |
| 「顶部的光被顶栏挡住了」 | 顶栏那条带偏暗 | 顶栏光跟着填充 α 一起乘了 0.7 |

**结论：这些不是五个 bug，是「一个模型缺位」的五个症状。** 所以本篇先定模型，再改代码。

### 1.1 现状：同一件事有四条路

| # | 谁 | 在哪 | 画什么 |
| :--- | :--- | :--- | :--- |
| 路 1 | 地面 | `backdrop.ts`（插件自有 fixed 层） | 三道光 + `::after` 颗粒 |
| 路 2 | 面板族 | `surface.ts` 的 `surfaceLayers()` | 颗粒 + 三道光（元素级 **与** `::after`） |
| 路 3 | 矮条族 | `surface.ts` 的 `menuSurfaceLayers()` | 颗粒 + **只有底光** |
| 路 4 | 顶栏 / 输入卡 / 右栏 | `glass.ts` 自画 | 三道光（按各自的规则重采样）+ 自己的模糊 |

同一份「质感配方」被抄了四遍，任何一次调整都要改四处 —— 漏一处就是 owner 看到的那种不一致。

### 1.2 现状：同一个面上，各层的**份数不一样**（computed style 实测）

| 表面 | 元素级 | `::after` | 净结果 |
| :--- | :--- | :--- | :--- |
| 地面 | 3 道光 | 颗粒 | 每道光 **1 份**、颗粒 **1 份** |
| 设置弹窗 | 3 道光 + 颗粒 | 3 道光 + 颗粒 | 每道光 **2 份**、颗粒 **2 份** |
| 模型菜单（分组） | **1 道光** + 颗粒 | 3 道光 + 颗粒 | 底光 **2 份**、顶/左光 **1 份**、颗粒 **2 份** |

第三行是最刺眼的：同一个菜单上，**底光被画两遍、顶光和左光只画一遍**。

机制（已逐条核验，见 §8 核验脚本）：

* 分组菜单元素**同时匹配**两条规则 —— 通用的 `[role='menu']` 与专用的
  `[role='menu']:has([role='group'])`；
* **元素级**由专用规则胜出（特异度更高）⇒ 只有 2 层（颗粒 + 底光）；
* **`::after`** 只有通用规则那条（专用规则**没有** `::after` 版本）⇒ 仍是 4 层（三道光）；
* 净结果：底光 2 份、顶光 1 份、左光 1 份、颗粒 2 份。

**这就是「配置不统一」的字面含义** —— 不是谁没调好，是两条规则各自只覆盖了一半。

### 1.2b 关键条件：元素级那层**有没有被盖住**，取决于**谁渲染了这个弹层**

「画了两遍」只有在**两层都可见**时才等于「重一倍」。官方有些组件会渲染一个
`z-index: -1` 的材质子元素（`MenuSurface.tsx:35` 的 `data-menu-material="translucent"`
+ `.material` 带 `backdrop-filter`），它盖在元素背景之上，会**把元素级那层洗掉** ——
那种情况下双层无害。而**插件自有组件不会渲染它**。

真机实测（computed style + DOM）：

| 表面 | 渲染者 | 官方材质子元素 | 元素级那层 |
| :--- | :--- | :--- | :--- |
| 模型菜单（`.ccb-model-menu`） | **本仓库 `dsh-codebuddy-credits`** | **无** | **直接可见** ⇒ 与 `::after` 叠加 |
| 设置弹窗 | 官方 `Modal`（`.dialog` 本身无材质子元素） | **无** | **直接可见** ⇒ 与 `::after` 叠加 |

⚠️ **口径说明**：上表「模型菜单」测的是**插件自有**的菜单；官方 `MenuSurface` 系
（`ModelSelect` / `MenuView` / `TabMenu` / `PopupSelectView`）源码里**确实有** `.material`。
两类都命中我们的 `[role='menu']` 锚点。

⇒ **同一个锚点，因渲染者不同而得到两种结果**（洗掉 / 叠加）。这是 §1 那种
「同类元素观感不一致」最根本的来源 —— **它不可从我们的锚点表预测**，因为取决于官方组件实现。
**M2（收敛为单载体）正是为消除这种不可预测性。**

> 本条修正过一次：初版把上表第一行写成「模型菜单」，未注明它是插件自有的
> —— 而那次测量的结论（无材质子元素）**不能**外推到官方 `MenuSurface`。
> 这类「拿一个样本代表一类」的推断正是本仓库反复踩的坑，故保留此注。

### 1.3 现状：三套强度口径 + 一个变量两条管线

| 项 | 地面 | 弹层 | 顶栏 |
| :--- | :--- | :--- | :--- |
| 光强系数 | 1.0（基准） | 0.7（`POPUP_LIGHT_COMPENSATION`） | 1.0（`HEADER_LIGHT_SCALE`） |
| 颗粒强度载体 | CSS `opacity` + 运行期变量 | **烘进贴图**（`<rect opacity>`） | — |
| 颗粒混合 | `mix-blend-mode: screen` | 无 | — |
| 运行期可调 | ✅ | ❌（烘死了） | — |

**同一个「噪点统一变量」在两条管线上含义不同** —— 这就是 owner 说
「我记得不是统一的一个变量么」却调不动弹层的根本原因。

## 2) 统一模型

### 2.1 一句话

> **任何一个抬升面 = 底色 + 颗粒 + 三道光（顶 / 底 / 左）。**
> 这四层的**来源、几何、强度**全部由下面三张表决定；除此之外不允许有第四种写法。

### 2.2 构成（自下而上）

> **「四层」= 颗粒 + 顶光 + 底光 + 左光**（我们画的部分）。
> 底色**不算**在这四层里 —— 它是官方的，我们只染值、不新增层。

| 序 | 项 | 来源 | 归属 |
| :--- | :--- | :--- | :--- |
| — | 底色 / 材质 | 官方 token（我们只染值） | 官方 |
| 1 | 三道光（顶 / 底 / 左） | `--dsh-theme-tone-{top,bottom,left}` | 我们 |
| 2 | 颗粒 | `--dsh-theme-tone-grain-*` | 我们 |

### 2.3 表面只有三类（按**尺度**分，不按组件分）

| 类 | 几何尺度 | 成员（举例） |
| :--- | :--- | :--- |
| **A 地面** | 视口 | 背景层 |
| **B 面板** | 自身盒子 | 对话框 / 菜单 / 卡片 / hover 卡 / 顶栏 / 右栏 / 输入卡 |
| **C 矮条** | 自身盒子（扁） | todo / goal-bar / queue-dock / 分组菜单 |

**三类都拿那四层**，差别只在几何与强度 —— **不再有「某类没有某道光」这种配置**。

## 3) 规范表（normative）

### 3.1 图层构成（MUST）

* 每个表面**必须**同时拿到：颗粒、顶光、底光、左光。缺任何一个都是 bug。
* 每层**只允许由一个绘制载体承担**。禁止「元素级 + 伪元素各画一份」。
* **载体可以是哪个由锚点决定**（不强制统一为 `::after`）：
  * 官方材质在元素自身 / 有负 z 子元素 ⇒ 用 `::after`（当前主通道）；
  * 官方已占用 `::after`（如 QueueDock 的 `.panel::after` 是 0.5px 描边）⇒
    **补官方自己的 `::before`**，不抢官方层（`OFFICIAL_BEFORE_LAYER_ANCHORS`）；
  * **但同一锚点下，那四层必须落在同一个载体里**，不得拆开。

> 为什么必须收敛到单载体：现状的双层不是设计，是历史叠加的产物 —— 它让强度变成
> 「两层之和」，任何按单个 alpha 做的定标都失效（我为此连错两轮：先定 0.33、后改 0.7）。

### 3.2 几何（三档，常量化）

| 档 | 顶光 | 底光 | 左光 | 收束（顶/底/左） |
| :--- | :--- | :--- | :--- | :--- |
| A 视口 | `ellipse 80vw 45vh at 50% -10vh` | `ellipse 70vw 45vh at 50% 112vh` | `ellipse 38vw 58vh at 0% -6vh` | 62% / 95% / 68% |
| B 面板 | `ellipse 120% 42% at 50% -12%` | `ellipse 110% 52% at 50% 112%` | `ellipse 42% 58% at 0% 0%` | 76% / 76% / 76% |
| C 矮条 | 同 B | 同 B | `ellipse 38% 50% at 0% 0%`（缩一档） | 同 B |

**矮条档曾经的「省略顶光与左光」被否决**：那会让 todo / goal-bar / queue-dock
完全没有光（owner 已实测发现）。**矮条真正需要的是更小的几何，不是更少的层。**

> 注：C 档当前不存在（那三个锚点正走 `menuSurfaceLayers`，只有底光）——
> 本行是 **M3 的目标值**，实现时须真机复核「矮条上顶光是否读得出」；若读不出，
> 回到 §7 Q2 重新决策，**不得**默默退回「省略」。

### 3.3 强度（一张表，每个数都要有实测理由）

| 类 | 光强系数 | 颗粒 alpha | 理由 | 置信度 |
| :--- | ---: | :--- | :--- | :--- |
| A 地面 | 1.0 | `GRAIN_ALPHA` 原值 | 基准，owner 已定值 | 高 |
| B 面板 | 0.7 | 同原值 | 同一屏幕位置上与地面**等 alpha**（解析解 0.69） | **中**（见下） |
| C 矮条 | 0.7 | 同原值 | 与 B 同族；几何更小已足够压「整条变亮」 | **低**（M3 后复测） |
| 顶栏 | 1.0 | — | 它是**玻璃**，光要透出来；按填充 α 压会让整条带偏暗 | 中 |

**规则：强度系数只能来自本表。** 任何就地写死的系数（如某条规则里手写 `70%`）都算 bug。

> ⚠️ **0.7 的置信度只到「中」，理由必须写清**：
> 那个解析解（逐点解 `alpha浮层 = alpha地面`，得 0.69）**本身是可信的** ——
> 它只依赖两边锁定常量，且与一次独立的像素实测吻合（解析预测 0.47、实测 0.48）。
> **但它解的是「单层」的 alpha**，而现状是**两层叠加** ⇒ 叠加后的实际观感会**更强**，
> 所以 0.7 很可能是**偏亮**的。
> 早先那次「按总量定标得 0.33」的扫描虽然被我判为量具错误（只覆盖元素级），
> 但它指向的方向（**实际需要比 0.7 更低**）与这个推理一致。
> ⇒ **M5 必须在 M2（单载体）之后重新定标一次**，届时 0.7 大概率要下调。
> 这不是「0.7 错了」，是**它的前提（单层）在现状下不成立**。

### 3.4 颗粒（MUST：单一来源、单一管线）

* **唯一常量**：`GRAIN_ALPHA`（每轴一档）。运行期经由 `--dsh-theme-tone-grain-alpha` 可调。
* **唯一管线**：伪元素 + `background-image: <贴图>` + `opacity: var(--dsh-theme-tone-grain-alpha)` + 该轴的 `mix-blend-mode`。
* **废弃「把 alpha 烘进贴图」那条管线**（`grainTileUri(alpha)` 预乘）：
  它让运行期变量对弹层失效，是「一个变量两条管线」的来源。
* 贴图本身**不带 alpha**（单一 `GRAIN_DATA_URI`）。

> 副作用（正面）：弹层与地面**共用同一个运行期变量** ⇒ owner 再调噪点，两处一起动。
> 副作用（需实测确认）：`mix-blend-mode` 会让同 alpha 的观感与现状不同 ⇒ §3.3 的
> 0.7 需在实现阶段重新定标一次（这次是**同口径**的，不再有双层混淆）。

## 4) 性能预算（硬约束）

> owner：「咱们现在还是比官方原版卡」。性能与视觉**同级**，不是事后优化。

### 4.1 实测基线 ⚠️ **当前量具不可用**（如实记录，勿引用为结论）

> owner：「咱们现在还是比官方原版卡」。**这条观测为真**（真机手感），但下面的量具
> **测不出来** —— 三次同条件重复，结果互相矛盾：

| 指标 | 第 1 次 | 第 2 次 | 第 3 次 |
| :--- | ---: | ---: | ---: |
| 主线程总耗时（插件档） | 377.7 ms | 393.7 ms | 297.9 ms |
| 主线程总耗时（官方档） | 364.2 ms | 387.0 ms | 301.4 ms |
| **增量** | **+13.5 ms** | **+6.7 ms** | **−3.6 ms** |
| 脚本耗时增量 | +3.7 ms (+39%) | +1.2 ms (+9%) | +3.1 ms (+42%) |

**结论：headless（`--disable-gpu`）+ 本量具的噪声（±15 ms）大于待测信号。**
不能据此声称「插件快/慢几个百分点」。**唯一稳定复现的一项是脚本耗时，三次都为正
（+1.2 ~ +3.7 ms，+9% ~ +42%）** —— 方向一致（确有一处 JS 成本），量级待更好的量具确定。

⇒ **待办（M0，先于一切视觉改动）**：换量具后再定基线。候选：
① 真实 GPU 下用 `Tracing` 抓 `UpdateLayoutTree` / `Paint` 事件并做 P95（本仓库已有
`handlers/sessions` 时用过的 trace 手法）；② 官方 dsh 与本插件各跑同一段固定脚本交互，
比较 **P95 帧时长**而非累计耗时（累计值对样本数敏感，正是本量具噪声来源）。

**在量具换好之前，§4.3 的预算只对「静态结构项」生效**（那些是确定性的、可逐条静态核验），
时间类预算（主线程增量）暂不设数值 —— 设了也无法验收。

### 4.2 静态结构成本（确定性统计，可重复）

| 模块 | 规则数 | 字节 | `:has()` | `backdrop-filter` | `position: fixed` | `!important` |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| surface.ts | 32 | 15164 | **8** | 0 | 0 | **36** |
| glass.ts | 19 | 7795 | 0 | **3** | 0 | 1 |
| backdrop.ts | 11 | 1844 | 0 | 0 | **1**（全屏 + `mix-blend-mode`） | 0 |
| **合计** | **62** | **24803** | **8** | **3** | **1** | **37** |

已知的三个结构性隐患：

1. **全屏 `mix-blend-mode` 层**（地面）：视口每帧都要参与混合。
2. **8 处 `:has()`**：每轮样式重算对全文档求值；其中 `body > :has(> [role='tree'])`
   （复杂度 7）与三处 `:has(> …)` 只为极少数浮层服务。
3. **37 处 `!important`**：与官方同特异度规则军备竞赛，任何官方改动都可能失配。

### 4.3 预算（MUST，实现阶段逐条核）

> 术语严格区分，勿混：
> * **层（layer）** = `background-image` 里的一项（颗粒 / 顶光 / 底光 / 左光）⇒ 每个表面**恒为 4**。
> * **载体（carrier）** = 实际参与绘制的盒子（元素本体 / `::before` / `::after` / 子元素）
>   ⇒ 每个表面**只许 1 个**。现状有 2 个（元素级 + `::after`），这是强度失控的根源。

| 约束 | 上限 | 现状 | 差 | 类型 |
| :--- | :--- | :--- | :--- | :--- |
| 每表面**层数** | 恰好 4 | 2 或 4（按表面而异） | ❌ | 静态 |
| 每表面**绘制载体数** | **1** | 2（元素级 + `::after`） | ❌ | 静态 |
| `:has()` 规则数 | **≤ 5**，每处配断言 | 8 | ❌ | 静态 |
| `position: fixed` 全屏层 | ≤ 1 | 1 | ✅ | 静态 |
| `mix-blend-mode` 全屏层 | ≤ 1 | 1 | ✅ | 静态 |
| `background-attachment: fixed` | **0（禁止）** | 1（顶栏） | ❌ | 静态 |
| `!important` | 仅用于压过官方同特异度规则，逐处注明理由 | 37（多数无注明） | ❌ | 静态 |
| 主线程增量 | **待量具（M0）后再定** | 不可测 | — | 时间 |

**只有「静态」列是可验收的**；时间项在 M0 完成前不设数值。

> `background-attachment: fixed` 已在本仓库踩过一次坑（百分比几何按视口而非盒子解析，
> 76px 高的顶栏会被重采样成硬边带），且滚动时要求整条带重新采样 ⇒ 列入禁止项。
> 顶栏改用**盒子内几何 + 显式 `100vw/100vh` 对齐**（右栏已经这么写了，可复用其做法）。

## 5) 迁移计划（分步、每步可独立验证与回退）

| 步 | 动作 | 验收 |
| :--- | :--- | :--- |
| **M0** | 换性能量具（trace / P95 帧时长），定下可信基线 | 同条件重复 3 次，离散度 < 5% |
| **M1** | 把 §3.2 / §3.3 两张表抽成**常量**（几何三档 + 强度一表），现有规则改为读表 | 纯重构，像素不变；测试全绿 |
| **M2** | 收敛到**单载体**：删掉元素级那份配方，只留伪元素 | 每个表面 computed 层数 = 4、载体数 = 1 |
| **M3** | 矮条族补上顶光与左光（几何缩一档） | todo / goal-bar / queue-dock 三道齐备 |
| **M4** | 颗粒收敛到**单一管线**（去掉烘 alpha），弹层改用运行期变量 | 调 `--…-grain-alpha` 两处同时变 |
| **M5** | 按 §3.3 重新定标颗粒与光强（**同口径**，无双层混淆） | 每类与地面的比值落在 1.0 ± 0.1 |
| **M6** | 性能收口：消 `:has()` 至 ≤5、去 `background-attachment: fixed`、注明 `!important` | §4.3 静态项逐条达标 + M0 量具复测 |
| **M7** | 真机复核 owner 点名的全部表面 | 逐项签字 |

每步一个 commit、一次 verify。**M1 之前不要再做任何定标** —— 现状是双层叠加，
按单层 alpha 定出来的系数必然是错的（我已为此连错两轮：先定 0.33 后改 0.7）。

## 6) 验收标准

1. **构成一致**：任取一个抬升面，computed 层数 = 4（颗粒 + 三道光），各 1 份。
2. **强度一致**：同一类的光强与颗粒强度系数取自 §3.3 表，无就地硬编码。
3. **变量一致**：颗粒与光各只有**一个**运行期变量，改它即全场景同步。
4. **性能达标**：§4.3 七项逐条通过；主线程增量 ≤ +15%。
5. **官方默认不动**：`PLAIN_ATTR` 档下逐像素与官方一致（沿用既有守卫）。
6. **测试钉住**：上表每一项都有断言；关键项做**反向注入**（改坏能测出来）。

## 8) 本篇事实性断言的核验
