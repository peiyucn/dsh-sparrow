# 10 · 去掉「视口锚定」的 `background-attachment: fixed`（座底不透带 + 卡片缺口）

> **状态**：已实现、已真机验收。**范围**：`glass.ts` 的座底不透带 + 卡片缺口两条规则。
> **依据**：本机真机实测（2880×1800 与 1920×1200，dsh 0.2.0-rc.2，Edge/ANGLE-D3D11 真机 GPU）。

## 1) 问题

owner 反馈：**模型 think（流式输出）时，插件主题下滚动明显变卡**，官方深浅主题不卡。

真机实测（真实会话、CDP `Paint` 分项 + rAF 帧间隔）：

| 档位 | 帧间隔中位 | Paint / 60 帧 | 绘制次数 |
| :--- | ---: | ---: | ---: |
| 插件档（改前） | 10.9 ~ 13.2 ms | 140 ~ 195 ms | 417 ~ 429 |
| 插件档（改后） | 8.4 ~ 11.3 ms | **25 ~ 31 ms** | **183 ~ 186** |
| 本机满帧基线（空转 rAF） | 8.3 ms | — | — |

Paint 降 **80~84%**、绘制次数（`paintN`）**−56%**。
⚠️ **帧间隔那两列不可作为结论**（差值多在噪声内、且出现过反号）—— 理由见 §6。

## 2) 机制

**① 成本来自 `fixed` 本身，与图片面积无关。**

| attachment | 声明尺寸 | Paint |
| :--- | :--- | ---: |
| `fixed` | `auto`（= 视口 2880×1800） | 157 ms |
| `fixed` | 2880×**46**（小 39 倍） | 190 ms |
| `fixed` | 2880×**8**（小 225 倍） | 144 ms |
| **`scroll`** | 2880×**1800**（视口大小） | **44 ms** |

⇒ 把声明尺寸缩到 1/225 也不省。`fixed` 让**定位区 = 视口**，无论声明多小，
每帧都要按视口重新解析/栅格化。

**② 两条规则**必须一起**改才有效（超加性）。**

同轮内 A/B 交替取差、主判据用**计数** `paintN`（受调度抖动影响远小于耗时）：

| 臂 | paintN | 相对基线 |
| :--- | ---: | ---: |
| 基线 | 435 | — |
| 只改座底带 | 361 | −17% |
| 只改缺口 | 370 | −15% |
| **两条都改** | **201** | **−54%** |

⇒ 滚动容器里只要还留着**一条** `fixed`，那笔按视口栅格化的开销就仍然要付。
（这也是 07 §4.1b 记的「两项各 3.8 ms 却不相加」的同一现象。）

**③ 「think 时卡」不是 think 的锅。**
四臂正交（`fixed`/`scroll` × 有无流式）：流式对掉帧数**无影响**。
准确表述是「**滚动时卡，而 think 时你正在滚动**」。

## 3) 修法（纯 CSS，零魔数、零 JS）

`fixed` 的语义 = **图片盒与视口重合**。改用 `scroll` 后必须显式复现该相位：

| 层 | 写法 |
| :--- | :--- |
| 颗粒（200×200 repeat） | x `calc(0px - (100vw - var(--dsh-conversation-column-width, 100vw)))`，y `calc(100% - 100vh)` |
| 三渐变（`100vw 100vh`） | x `calc(100% + (2px + var(--dsh-scrollbar-width, 5px)))`，y `100%` |

配套（**不可省**，见 §3.1）：

```
background-size: auto, 100vw 100vh, 100vw 100vh, 100vw 100vh;
background-repeat: repeat, no-repeat, no-repeat, no-repeat;
```

推导要点（`p` 为百分比解析式 `p·(定位区 − 图片)`）：

* 渐变 y = `100%` ⇒ 图片顶 = `定位区下缘 − 100vh = 0`（因下缘贴视口底）✓
* 颗粒 y = `calc(100% − 100vh)` ⇒ 原点 = `下缘 − 200 − 100vh = −200` = **正好一个贴图周期**，
  与视口原点等价，**且与元素高度、视口高都无关** ✓
* 渐变 x = `100% + inset` ⇒ 图片左 = `定位区右缘 − 100vw + inset = (100vw − inset) − 100vw + inset = 0` ✓

### 3.1 三处**必须**逐层 / 逐处给值

1. **`background-size` 必须逐层**：第 1 层是 200×200 的颗粒贴图，`auto` 才是它的固有尺寸；
   写成 `100vw 100vh` 会把噪声拉成 14 倍粗。
2. **两种层的 y 不一样**：渐变是 `100%`，写成 `calc(100% - 100vh)` 会多减一个图片高、
   把整块推到视口外（本轮真犯过：逐像素差 2.65 / 31% 像素超 2 级）。
3. **缺口那条的盒子要 `inset: 0` 撑满宿主，且遮罩必须重算**（见 §4）。

## 4) 缺口那条的两个坑（都靠控制组实验分清）

**坑 ①：盒子不能保持 `height: 28px`。**
相位的 `100%` 指**元素自身高度**，只有下缘贴视口底才能把「元素顶到视口顶的距离」消掉。
故改用 `inset: 0`（同时定 left/right/top/bottom）。
⚠️ 只写 `left: 0; width: auto` 会让绝对定位伪元素**宽度塌成 0**（实测 canary `w=0px`），
整条臂都在量一个坏布局 —— 本轮据此误判过一次「某个候选更差」。

**坑 ②：盒子变宽 ⇒ 遮罩的两块瓦片会跑到宿主两角。**
遮罩百分比按 `(定位区宽 − 瓦片宽)` 解析；盒子从「卡片宽」变成「宿主宽」后基准整个变了。
推导（要求瓦片落在卡片左缘）：

```
0.5·(A − R) + c − cardW/2 = (A − cardW)/2   ⇒   c = R/2
```

**`c = R/2` 与 A 无关** ⇒ 视口/列宽/卡片宽变化都不用改。右瓦片同理整体相差 `cardW − R`。

> 如何确认「不是盒高/遮罩抗锯齿」：控制组「**只**把盒高改成 128px、attachment 仍 `fixed`」
> 实测 **0 个像素改变**；而相位臂的差异**只落在卡片两端的角弧上**（中间列全 0）
> —— 典型的 x 相位错，不是边缘抗锯齿。

## 5) 守卫：`data-rightbar-collapsed`（**不是可选项**）

相位要求「定位区右缘贴视口右缘」。逐状态实测：

| 状态 | 座右缘缺口 | 相位 vs `fixed` 逐像素 |
| :--- | ---: | ---: |
| 默认 | 7px | **0** |
| 左栏折叠 | 7px | **0** |
| **右栏打开** | **1303px** | **4.53（肉眼可见的错位）** |
| 右栏全屏 | 1303px | 不适用 |

官方在「右栏轨道不存在」时输出 `data-rightbar-collapsed`（`AppFrame.tsx`），
实测它就是那条分界线。故：

* 新写法**只在该属性存在时生效**（选择器多一个属性 ⇒ 特异度更高，与书写次序无关）；
* 其余状态自动退回**原有**的 `fixed` 档 —— **退回去只是慢，绝不会错位**。

### 5.1 ⚠️ 已知局限：该会话右栏开着时，性能档完全不生效

**这是本方案最重要的限制，必须让 owner 知道。** 官方把右栏宽度按**会话**持久化
（`localStorage` 的 `dsh.sidebar-right.v1.session-<id>`），所以「右栏开着」是**会话级**状态、
不是一次性动作。实测（同一会话）：

| 会话右栏状态 | 守卫 | 座 `::after` | paintN | Paint |
| :--- | :--- | :--- | ---: | ---: |
| 关 | ✅ 在 | `scroll` | **183** | 20.2 ms |
| 开 | ❌ 不在 | `fixed` | **417** | 115.2 ms |
| 开 → 重载页面 | ❌ 不在 | `fixed` | 417 | 125.0 ms |
| 全新 context（无持久化） | ✅ 在 | `scroll` | — | — |

⇒ 「丢失」是**该会话内持续**的。**若 owner 在右栏打开的那个会话里滚动，这次改动救不了他。**

**为什么不用相位覆盖那一档**：相位需要「定位区右缘到视口右缘」的距离
（开栏时 = `7 + 面板宽 1296 = 1303`）。而面板宽只写在**面板元素自己**的
`--dsh-sidebar-width` 上（`SidebarRight.tsx:311` 的 inline style），
面板与座**不是祖先关系** ⇒ 该变量**不会继承到座上**，纯 CSS 读不到。
（`--dsh-conversation-column-width` 也变（2600 → 1528），但左缘偏移同时变了，
单靠它推不出右缘。）

若要覆盖这一档，需要改走「client half 观测面板宽 → 注入一个 CSS 变量」，
属**新增运行期机制**，风险与工作量都不是本次范围。已如实记为待办。

## 6) 验收（真机、产物本体，非探针）

**可复现、可背书的两项**（多次独立运行，含换分辨率）：

| 项 | 结果 |
| :--- | :--- |
| 座底带逐像素（各 6 个滚动位累计） | **0 改变像素 / 0 超 8 级** |
| 缺口卡片顶边逐像素 | **0 改变像素 / 0 超 8 级** |
| `paintN`（绘制次数） | **417~429 → 183~186**（−55.7% / −56.1% / −56.4%，三次） |
| Paint 耗时 | 140~195 → 25~31 ms（−80% ~ −84%，**该臂本身抖动较大**） |
| 两视口 | 2880×1800 与 1920×1200 均 0 差 |

**⚠️ 不能背书的一项：帧间隔（rAF 中位）**。八次运行里的「旧 − 新」差值为
+2.8 / +2.1 / +1.9 / +0.6 / +0.4 / **−0.2** ms —— **落在噪声内、且有一次反号**。
故：

* 「帧率从 60 回到 120」这类说法**不成立**，不要写进任何交付物；
* 唯一干净的性能结论是 **绘制次数 `paintN`（计数，不受调度抖动影响）**，
  Paint 耗时同向但该臂抖动大（140~195 ms）。

> 教训：`paintN` 之所以可信，是因为它是**计数**；帧间隔与累计耗时都受调度/合成影响。
> 报告性能收益时优先给计数，给出耗时/帧率时必须**附多次运行的离散度**。

产物层面另核对：两条性能档规则**选择器均命中 1 个元素**、computed
`background-attachment` 为 `scroll`、守卫属性存在。

> ⚠️ 另有两条**量具缺陷**（验证者发现，已确认）：
> 1. `gui-shipped.mjs` 的 `canary` 是**死指标** —— 探针表处于 `disabled` 时
>    computed **仍会**受其影响，于是 canary 恒读 `fixed`，与同一次运行的
>    `shipped.seat=scroll` 自相矛盾。**不要用 canary 当证据**（主结论不依赖它）。
> 2. `gui-guard.mjs` 里 C/D 两行的「0 差」是**同义反复** —— 两臂都带同一守卫、
>    都退回 `fixed`。守卫是否承重须用**去守卫探针**另测（已测：默认态 0 差、
>    右栏打开态 mean 4.13 / max 27 / 41542 个像素改变 ⇒ 守卫**确实承重**）。
>    另：该脚本的「关栏」步骤按钮正则没匹配上，E 行不是「关栏后」而是「仍开着」。

## 7) 明确不做（附理由）

| 站点 | 为何不改 |
| :--- | :--- |
| 顶栏玻璃 | 在滚动容器**外**（实测只值 2.9 ms）；且它靠 `fixed` 让 76px 盒子不被重采样成硬边带 |
| 吸顶 Think 行 | 居中列内，且**只在用户手动展开时**出现；本页命中 0 |
| 轨迹视图铺满 | 只在轨迹标签页出现，本页命中 0 |
| 三处缝挡板 | 只在有停靠卡时出现，本页命中 0 |
| 背景层 `mix-blend-mode` | 另有 140–238 ms 成本，但有观感风险（07 §4.1c/§4.1d 已证「提 alpha 补偿」走不通），本次不并入 |

## 8) 复现方式

```powershell
# 合成基准（无官方代码、无流式，最干净的机制验证）
node TEMP/bench.mjs

# 真机（需 GUI 令牌）
$env:DSH_TOKEN='<令牌>'; $env:BENCH_W='2880'; $env:BENCH_H='1800'
node TEMP/gui-shipped.mjs      # 产物本体验收：像素 + Paint + 帧间隔
node TEMP/gui-guard.mjs        # 守卫：四状态 × 相位 vs fixed
node TEMP/gui-origin.mjs       # 缺口遮罩基准（三臂控制组）
node TEMP/gui-states.mjs       # 前提 P1/P2/P3 逐状态自检
```

> ⚠️ **量具纪律**：分组/单条时序的原始离散度可达 ±90 ms，**超过**单条规则的真实效应。
> 故：**性能判据只用「分组」粒度 + 计数（paintN）**，**单条规则的正确性只用确定性像素比对**
> （噪声底 0.0094）。这条是本轮最贵的教训 —— 曾据噪声排出一份「逐条优先级」，
> 其中命中 **0** 个元素的规则竟测出「省 85.8 ms」，该排序已作废。
>
> ⚠️ 另：**探针验证 ≠ 产物验证**。探针只证明「配方对不对」；产物里到底有没有这条规则、
> 选择器命不命中、守卫在不在，必须另做一次（`gui-shipped.mjs` 就是干这个的）。
