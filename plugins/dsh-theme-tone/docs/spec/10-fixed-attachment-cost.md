# 10 · 去掉「视口锚定」的 `background-attachment: fixed`（座底不透带 + 卡片缺口）

> **状态**：已实现、已真机验收。**范围**：`glass.ts` 的座底不透带 + 卡片缺口两条规则。
> **依据**：本机真机实测（2880×1800 与 1920×1200，dsh 0.2.0-rc.2，Edge/ANGLE-D3D11 真机 GPU）。

## 1) 问题

owner 反馈：**模型 think（流式输出）时，插件主题下滚动明显变卡**，官方深浅主题不卡。

真机实测（真实会话、CDP `Paint` 分项 + rAF 帧间隔）：

| 档位 | 帧间隔中位 | Paint / 60 帧 | 绘制次数 |
| :--- | ---: | ---: | ---: |
| 插件档（改前） | 10.9 ~ 13.2 ms | 140 ~ 195 ms | 417 ~ 429 |
| 插件档（改后） | 8.4 ~ 11.3 ms | **25 ~ 31 ms** | **183 ~ 186** |
| 本机满帧基线（空转 rAF） | 8.3 ms | — | — |

Paint 降 **80~84%**、绘制次数（`paintN`）**−56%**。
⚠️ **帧间隔那两列不可作为结论**（差值多在噪声内、且出现过反号）—— 理由见 §6。

## 2) 机制

**① 成本来自 `fixed` 本身，与图片面积无关。**

| attachment | 声明尺寸 | Paint |
| :--- | :--- | ---: |
| `fixed` | `auto`（= 视口 2880×1800） | 157 ms |
| `fixed` | 2880×**46**（小 39 倍） | 190 ms |
| `fixed` | 2880×**8**（小 225 倍） | 144 ms |
| **`scroll`** | 2880×**1800**（视口大小） | **44 ms** |

⇒ 把声明尺寸缩到 1/225 也不省。`fixed` 让**定位区 = 视口**，无论声明多小，
每帧都要按视口重新解析/栅格化。

**② 两条规则**必须一起**改才有效（超加性）。**

同轮内 A/B 交替取差、主判据用**计数** `paintN`（受调度抖动影响远小于耗时）：

| 臂 | paintN | 相对基线 |
| :--- | ---: | ---: |
| 基线 | 435 | — |
| 只改座底带 | 361 | −17% |
| 只改缺口 | 370 | −15% |
| **两条都改** | **201** | **−54%** |

⇒ 滚动容器里只要还留着**一条** `fixed`，那笔按视口栅格化的开销就仍然要付。
（这也是 07 §4.1b 记的「两项各 3.8 ms 却不相加」的同一现象。）

**③ 「think 时卡」不是 think 的锅。**
四臂正交（`fixed`/`scroll` × 有无流式）：流式对掉帧数**无影响**。
准确表述是「**滚动时卡，而 think 时你正在滚动**」。

## 3) 修法（`background-attachment: scroll` + 实测视口相位）

`fixed` 的语义 = **图片盒与视口重合**。改用 `scroll` 后必须显式复现该相位。
最终写法：**两个方向都用长度**，取「该载体定位区原点在视口里的坐标」取负：

| 层 | 写法 |
| :--- | :--- |
| 颗粒（200×200 repeat） | x / y 都 `calc(0px - var(--…-phase-…))` |
| 三渐变（`100vw 100vh`） | 同上（四层同一配方） |

配套（**不可省**）：

```
background-size: auto, 100vw 100vh, 100vw 100vh, 100vw 100vh;
background-repeat: repeat, no-repeat, no-repeat, no-repeat;
```

`background-position` 是「图片左上角相对**定位区**左上角的偏移」，取负即把图片左上角
钉回**视口左上角** —— 正是 `fixed` 的语义，且与元素自身宽高**完全无关**。
相位形状的推导与「为什么不能用百分比」见 §4；两个量的来源见 §5。

### 3.1 一处**必须**逐层给值

**`background-size` 必须逐层**：第 1 层是 200×200 的颗粒贴图，`auto` 才是它的固有尺寸；
写成 `100vw 100vh` 会把噪声拉成 14 倍粗。

## 4) 相位的**形状**：为什么两个方向都用长度

第一版（已废弃）用**百分比**写相位：颗粒 `calc(100% − 100vh)`、渐变 `100%`，横向量靠
`100vw − var(--dsh-conversation-column-width)` 推。它有两个后果：

1. **依赖元素自身几何** —— 百分比按「(定位区尺寸 − 图片尺寸)」解析，于是同一个配方
   在不同盒子上给出不同相位；
2. **前提会随状态漂移** —— 为了让 `100%` 落在视口底，缺口那条必须把盒子改成 `inset: 0`
   撑满宿主，而盒子一宽，遮罩的两块瓦片就跑到宿主两角，于是又要补一个 `c = R/2` 的偏移
   （推导：`0.5·(A − R) + c − cardW/2 = (A − cardW)/2`）。

**现在改成：两个方向都用长度**，取「定位区原点在视口里的坐标取负」：

```css
background-position: calc(0px - var(--…-phase-band)) calc(0px - var(--…-phase-band-top)), …
```

`background-position` 是「图片左上角相对**定位区**左上角的偏移」，取负即把图片左上角
钉回**视口左上角** —— 正是 `fixed` 的语义，且**与元素宽高完全无关**。收益：

* CSS 侧**不必为了相位改盒子几何** ⇒ 盒子与遮罩都保持修复前的样子（`height: 28px`、
  `mask-position: 0 0, 100% 0`），**逐像素等价**；
* 不再有「元素下缘是否贴视口底」这类会随布局漂移的前提。

> 代价是这两个量必须**运行期实测**（见 §5）。

## 5) 相位量：实测，不推

### 5.1 为什么推不出

纯 CSS 只能写出「右栏折叠」时的值。**右栏一开就推不出** —— 左栏偏移与右栏宽同时变，
一个方程两个未知量（实测：载体左缘仍是 280、右缘却从 2873 变 1577）。
官方把右栏宽只写成 `gridTemplateColumns` **内联样式**、没发布成 CSS 变量，
面板宽也只写在面板元素自己的 `--dsh-sidebar-width` 上（面板与座不是祖先关系）
⇒ 该变量不会继承到座上，纯 CSS 读不到。

### 5.2 怎么测（统一公式，两个载体同一条推导）

两条规则都是「宿主里的一个绝对定位伪元素」，故都用同一条：

```
伪元素视口左缘 = 宿主边框盒左缘 + 宿主左边框 + 伪元素自身的 left（计算值即用值）
伪元素视口上缘 = 宿主边框盒上缘 + 宿主上边框 + 伪元素自身的 top
```

* 座底带：宿主 = 座位自身（`sticky`，正是 `::after` 的包含块）。
* 卡片缺口：宿主 = **卡片的父元素**。

⚠️ **不能拿宿主矩形代替**（缺口伪元素是卡片宽的、宿主是全宽的，两者差一个大内边距
—— 本轮真拿宿主算过，卡片顶边因此画错）**，也不该拿卡片矩形代替**（那依赖「卡片与
伪元素同宽同左、宿主无上内边距」这类实测不变量，官方一改内边距就静默错位）。
上式只依赖 CSS 定位语义。

### 5.3 门：两道，各自独立

测到有效值才挂对应属性；挂不上则该条退回 `fixed`（**慢但一定正确**）。
两个门分开的理由：两个载体的可见性各自独立（hero 没有会话座；卡片不渲染时没有缺口），
合成一道门会让「一个载体暂不可用」连带把另一个已经能测到的也拖回慢档。

⚠️ **不能用「变量缺失即降级」代替门**：相位声明里的 `var()` 不带回退值，
变量缺失时 `background-position` 会在计算值阶段整条失效、退成 `0% 0%` ——
那是**错位**，不是降级。

| 门属性 | 管哪条规则 |
| :--- | :--- |
| `data-dsh-theme-tone-phase-band` | 座底不透带 |
| `data-dsh-theme-tone-phase-notch` | 卡片缺口 |

### 5.4 ⚠️ 曾经的坑：相位量**陈旧**（动画期间采样，之后再无事件）

右栏开合是**动画**改 `grid-template-columns` **内联样式**：

* 不改 class ⇒ `MutationObserver`（只过滤 `class`）看不到；
* 视口没变 ⇒ 不触发 `window.resize`；
* `ResizeObserver` 也可能只落在**动画中途**那一帧。

于是采到一个中间值后**再无事件** ⇒ 变量永久停在错相位（实测停在 452.5px，
正确值 495.22px，卡片顶边 **371 个像素**因此画错）。

修法：相位重测做成**收敛循环** —— 每次测量后比对「六个原始几何输入」拼成的签名，
**连续两帧一致才停**（上限 `PHASE_SETTLE_FRAMES = 120`，防止持续动画下无限轮询）。
于是不论动画由什么触发、持续多少帧，最终稳定值一定被采到。

> 另有一条同源教训：收敛循环**必须用自己独立的 rAF 句柄**。初版借用了
> `scheduleProbe` 的句柄，一取消就把 `probeScheduled` 永久留在 `true`，
> 之后所有 MutationObserver 触发的探测都被「同帧合并」静默吞掉 —— 观测彻底停摆。

## 6) 验收（真机、产物本体，非探针）

**可复现、可背书的几项**（多次独立运行）：

| 项 | 结果 |
| :--- | :--- |
| 座底带逐像素（5 个滚动位累计） | **0 改变像素 / 0 超 2 级**（两状态各一次） |
| 缺口卡片顶边逐像素 | **0 改变像素 / 0 超 2 级**（两状态各一次） |
| `paintN` 右栏折叠 | **312 → 266**（−14.7%，六轮中位；区间 304~352 vs 253~290 不重叠） |
| `paintN` 右栏**打开** | **328 → 263**（−19.8%，六轮中位；区间 308~356 vs 244~287 不重叠） |
| Paint 耗时 | 同向、且降幅更大（−91% ~ −93%），但**该臂抖动大**，只作旁证 |

> ⚠️ 上表的 `paintN` 与早期版本（417→183，−56%）不可直接比：早期基线是**未优化**的
> 整片背景（含 `mix-blend-mode` 与更大的绘制面积）；本轮两臂**只差相位档本身**
> （同一次运行内切换门属性），故差值是这条改动的**净效应**。
> 这也解释了为何净效应（−15% ~ −20%）小于早期端到端读数。

**⚠️ 不能背书的一项：帧间隔（rAF 中位）**。八次运行里的「旧 − 新」差值为
+2.8 / +2.1 / +1.9 / +0.6 / +0.4 / **−0.2** ms —— **落在噪声内、且有一次反号**。
故：

* 「帧率从 60 回到 120」这类说法**不成立**，不要写进任何交付物；
* 唯一干净的性能结论是 **绘制次数 `paintN`（计数，不受调度抖动影响）**。

> 教训：`paintN` 之所以可信，是因为它是**计数**；帧间隔与累计耗时都受调度/合成影响。
> 报告性能收益时优先给计数，给出耗时/帧率时必须**附多次运行的离散度**。

产物层面另核对：两条相位档规则**选择器各命中 1 个元素**、computed
`background-attachment` 为 `scroll`、两道门属性存在、四个变量与实测几何一致。

> ⚠️ **量具纪律（本轮最贵的教训）**：报告任何 A/B 结论前，**先断言两臂真的切到了
> 预期状态**。本轮踩过三次：
> 1. 用 `window.resize`/`<style>.disabled` 当切换手段 —— 前者在本场景**不触发**，
>    后者早已被发现**不可靠**（探针表 `disabled` 仍影响 computed），两臂其实是同一个状态；
> 2. 「打开右栏」的按钮正则只匹配英文，而本机 GUI 是**中文**（标签「打开右侧边栏」）
>    ⇒ 点击静默失败，整轮读数其实是**默认态**，一度被当成「右栏打开」的结论；
> 3. 会话列表过滤只认英文 `new session` ⇒ 点到了「新会话」，页面停在 hero，
>    `disclosureRows` 恒为 0，读数全部无效。
>
> 现在 `gui-ab.mjs` 每次切换后都断言两个载体的 computed `attachment`，
> 并断言右栏**真的开了**（座位右缘变化）；断言不过直接报错，不给结论。

## 7) 明确不做（附理由）

| 站点 | 为何不改 |
| :--- | :--- |
| 顶栏玻璃 | 在滚动容器**外**（实测只值 2.9 ms）；且它靠 `fixed` 让 76px 盒子不被重采样成硬边带 |
| 吸顶 Think 行 | 居中列内，且**只在用户手动展开时**出现；本页命中 0 |
| 轨迹视图铺满 | 只在轨迹标签页出现，本页命中 0 |
| 三处缝挡板 | 只在有停靠卡时出现，本页命中 0 |
| 背景层 `mix-blend-mode` | 另有 140–238 ms 成本，但有观感风险（07 §4.1c/§4.1d 已证「提 alpha 补偿」走不通），本次不并入 |

## 8) 复现方式

```powershell
# 合成基准（无官方代码、无流式，最干净的机制验证）
node TEMP/bench.mjs

# 真机（需 GUI 令牌）
$env:DSH_TOKEN='<令牌>'; $env:BENCH_W='2880'; $env:BENCH_H='1800'
node TEMP/gui-ab.mjs           # 性能 A/B：同一次运行内切换两道门（自断言两臂状态）
node TEMP/gui-pixel.mjs        # 逐像素等价：右栏折叠 / 右栏打开 两状态
node TEMP/diag-gate-stability.mjs  # 门与变量在连续采样下是否稳定（不抖）
```

> ⚠️ **量具纪律**：分组/单条时序的原始离散度可达 ±90 ms，**超过**单条规则的真实效应。
> 故：**性能判据只用「分组」粒度 + 计数（paintN）**，**单条规则的正确性只用确定性像素比对**
> （噪声底 0.0094）。这条是本轮最贵的教训 —— 曾据噪声排出一份「逐条优先级」，
> 其中命中 **0** 个元素的规则竟测出「省 85.8 ms」，该排序已作废。
>
> ⚠️ 另：**探针验证 ≠ 产物验证**。探针只证明「配方对不对」；产物里到底有没有这条规则、
> 选择器命不命中、门在不在，必须另做一次（`gui-ab.mjs` / `gui-pixel.mjs` 都是读产物本体的）。
