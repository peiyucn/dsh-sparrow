# 03 · 调色板规划 — dsh-theme-tone

> 本文是**所有色调取值的唯一事实来源**（00-overview 只留状态与指针）。几何不在本文 ——
> 形状与收束位置住在 `src/backdrop.ts` 的 `*_SHAPE` / `*_STOP` 常量里，**全色调共用一套**。

## 1) 统一的几何

「渐变的位置统一」在结构上已经成立：色调表里**没有**任何几何字段，只有颜色。

| 层 | 角色 | 形状常量（`backdrop.ts`） |
| :--- | :--- | :--- |
| `top` | 上方光源 | `DARK_RADIAL_SHAPE` = `ellipse 80vw 45vh at 50% -10vh`，`RADIAL_STOP` = `transparent 62%` |
| `bottom` | 底部辉光 | `BOTTOM_RADIAL_SHAPE` = `ellipse 70vw 45vh at 50% 112vh`，**`BOTTOM_RADIAL_STOP` = `transparent 95%`**（pyai.site 是 62%） |
| `left` | 左上光晕（左栏 / 接缝） | `LEFT_RADIAL_SHAPE` = `ellipse 38vw 58vh at 0% -6vh`，`LEFT_RADIAL_STOP` = `transparent 68%` |

> **整屏几何一律用视口单位 `vw` / `vh`，不用 `%`**：背景层本身是满视口的 `position: fixed`，
> 两者对它完全等价；但顶栏（76px 高）要复用同一串渐变，`%` 会按**顶栏自身的盒子**解析，
> 把 `45%` 压成 34px 的扁椭圆，金光只剩顶部一条细边。
> 唯一的例外是横向中心 `at 50%`：它按盒子居中（背景层 = 视口中心；顶栏 = 中列中心，
> 相差约一个左栏宽度，可接受 —— 用 `50vw` 反而会以盒子左缘为原点，偏得更多）。

> **`bottom` 有自己独立的收束常量**：62% 时它只覆盖约 **16% 屏高**——一条极淡的窄带，而屏幕底部那带正是 composer 与各种面板最密的地方，很容易看漏。95% 则覆盖约 **31% 屏高**，从「一条边带」变成「一片底光」。把 `top` / `bottom` 的收束拆开，就是为了能单独调这一个方向。

色调卡复用同一批角色，只把形状换成卡片尺度的 `PREVIEW_*`
（`PREVIEW_TOP_SHAPE` = `ellipse 86% 70% at 50% -14%`、`PREVIEW_BOTTOM_SHAPE` = `ellipse 83% 70% at 50% 114%`、
`PREVIEW_LEFT_SHAPE` = `ellipse 44% 80% at 0% -7%`、`PREVIEW_STOP` = `transparent 71%`；
卡面是盒子尺度，故用 `%`）。→ **新增一款色调永远只填颜色，不碰几何。**

> **派生色不另立取值**：`bottom` 与抬升面（弹出来的框）染色都不另立数值 ——
> 两轴 `bottom = rgba(本色, DEPTH_ALPHA[轴])`（浅色轴上「本色」同时也是三层光的颜色）；
> 浮层 = `color-mix(本色 P%, 官方中性 rung)`。
> 所以新增一款色调要填的**新的**数值只有 `base` / `sidebarFill` / `tint` 三个，
> 三层光与浮层自动跟随。规则与两轴比例见 [05-surfaces.md](05-surfaces.md)。

### 卡面与实况的关系（**同一条规则：色卡是承诺，实况必须兑现**）

色卡上读得出来的渐变，实况里必须同样读得出来。落实这条规则的旋钮是 `PREVIEW_ALPHA_SCALE`，
判据 **卡面倍数 = 「卡面需要多少」÷「实况已有多少」**，且**按层**给：

* **实况本身够显的层就是 ×1** —— 放大「三款共享的那层光」只会让三张卡互相盖住，反而看不出区别。
* **小卡（135×83）面积小、渐变被压缩**，各款自己的纵深层需要放大才读得出来。

| 轴 | 层 | 实况 α | 卡面倍数 | 卡面 α |
| :--- | :--- | :--- | :--- | :--- |
| 深色 | `top` / `left`（三款共享的金） | `.09` / `.11` | ×1 | `.09` / `.11`（与实况逐字相同） |
| 深色 | `bottom`（各款纵深） | `.18` | ×3 | `.54` |
| 浅色 | `top` / `left`（本色） | `.16` / `.19` | ×3 | `.48` / `.57` |
| 浅色 | `bottom`（本色） | `.30` | ×1.8 | `.54` |

**两轴底色余量不同，这是浅色 alpha 约为深色 1.8 倍的根因**：近黑底 `#0a0a10` 到纯黑**余量大**，
同样 α 叠上去 Δ亮度 +9~12 本来就显；浅色底到纯白只剩个位数余量，`α .18` 只换来 Δ亮度 −6~9。
浅色实况 alpha 降到 `.16/.30/.19` 后卡面若跟着降，**三款区分度会掉到人眼阈下**
（实测 5.7 / 5.8，阈约 8），所以浅色卡面同样必须放大 —— 与深色轴 `depth ×3` 同一个道理。

**其余按卡片尺度的调整仍然保留**（它们是「小卡适配」，不是放大承诺）。
浅色 `depth` 取 `1.8` 而非 `3`，是因为浅色实况本就更显，倍数该更小。

> **「色卡为什么看着比实况艳」还有一个次要原因**：卡面上没有输入框。
> 实况在对话列底部中间被不透明的输入框卡片盖住一大块，所以底光在实况里主要出现在
> ① 输入框左右的留白 ② 输入框上方那条带 ③ 左栏整列。这是**结构差异**，不是强度差异。

### `bottom` 是「底部辉光」，不是阴影

命名沿用了 pyai.site 源码注释里的「底部…深空纵深」，但**物理上它是加亮**：底色是近黑（`[10,10,16]`），叠任何颜色都只会更亮。所以：

| | 底部合成色（峰值） | 比底色亮 | 覆盖范围 |
| :--- | :--- | :--- | :--- |
| **深色实况**（`bottom` α `.18`，`ellipse 70vw 45vh at 50% 112vh` / `BOTTOM_RADIAL_STOP 95%`） | `[25,22,43]` | `+15 / +12 / +27` | 屏底约 **31% 屏高** |
| **深色卡面**（×3 → α `.54`，`ellipse 83% 70% at 50% 114%` / `71%`） | `[56,47,98]` | `+46 / +37 / +82` | 卡底约 **36% 卡高** |

> **浅色轴上这一层的方向相反**：底色近白，叠本色只会**变暗**（实测 green 底光峰值 Δ亮度 −8.3）。
> 所以「辉光」在浅色轴其实是一层**底部暗晕** —— 名字沿用，语义按轴理解。

> **实况这一层的两个参数都不是 pyai.site 的**：alpha `.18`（pyai.site `.08`）、收束 `95%`（pyai.site `62%`）。
> 依据是 pyai.site 是留白为主的博客，同浓度放到 DSW 这种满屏 UI 上会显得太淡。
> **色相 / 底色仍逐字是原值**，偏离的只有这一个 alpha 和一个收束百分比。

### 卡面的颗粒（深色轴的「质感」）

深色轴的实况有 stardust 颗粒层（`mix-blend-mode: screen` / `opacity .13`）。**卡面同样叠一层**，
参数逐字相同（同一条 data URI、同一不透明度、同一 screen 混合），由 `.cube::after` 承担 ——
`mix-blend-mode` 没法用 inline style 表达，所以放在样式表里、组件只按 `tone.grain` 打 `data-grain` 属性。

* 卡加 `overflow: hidden` 把颗粒裁进圆角、`isolation: isolate` 让混合只在卡内发生（不渗到卡片外的页面）。
* `data-grain='off'`（两轴的**官方默认**款）时 `::after` 不渲染 —— 与实况的「官方默认不叠颗粒」口径一致。

## 2) 生成规则

规则的目的不是好看而已：**亮度锁死、只变色相**，这样 8 款色调的**文字对比度天然等价**
（正文 `--dsw-alias-label-primary` 等 token 在每款底上都不劣于官方），不用逐款重调。

### 暗色轴（月食语言）

| # | 规则 | 取值 |
| :--- | :--- | :--- |
| D1 | **共享金色光源**：`top` 与 `left` 全部用 pyai.site 的金 `rgb(232, 162, 74)` | `top` α = `.09`；`left` α = `.11` |
| D2 | **底色 = 色相染过的近黑**，亮度锁在 violet 的基准 `rgb(10, 10, 16)`（**三通道和恒为 36** → 三款亮度严格相等、对比度等价），只挪最高通道定色相。**色相跨度是「音量钮」**：violet `6`（基准），crimson / forest `5`（中间档） | 见下表 `base` |
| D3 | **底部辉光 = 该色调本色**，α = `.18`（三款同档；pyai.site 原值 `.08`，放到满屏 UI 上偏淡故上调），收束用独立的 `BOTTOM_RADIAL_STOP`（`95%`，pyai.site `62%`）；**饱和度与 violet 互相控制在 20% 以内** —— S 明显高于 violet（≈.37）就会读成「夸张」 | 见下表 `bottom` |
| D4 | **左栏填充 = 底色逐通道 + 10**（做出「面板浮起」感）。已落地的 `violet` 是 +10/+10/+12 | 见下表 `sidebarFill` |
| D5 | 颗粒 `grain: true`（深色轴保留 pyai.site 的星尘） | — |

> D1 是这套调色板的核心决定：**切换色调改变的是「空间」，不是「光源」** —— 同一轴内三款并排时
> 读成「同一个光源下的三种空间」，而不是三个互不相干的主题。这也是 pyai.site 的视觉签名
> （其源码注释原话：「深空『月食』」）。

> **三款底色不是通道值的严格轮换**（violet 跨度 6、另两款 5），所以 violet 仍**略响于**另两款 ——
> 这是刻意的：它是基准也是默认款。

> **深色轴的光源是金**（`rgb(232,162,74)`，比近黑底亮 → 是光）。
> 「同一轴内三款共享同一层光」这条**只在深色轴成立**：浅色轴的三层光就是本色本身、三款各不相同。

### 浅色轴（白天语言）

浅色轴与暗色轴**结构完全镜像**：**空间用官方底**、一束光当光源（`top` / `left` / `bottom`）。
深色轴那束光是**金**、浅色轴是**本色本身**（三层光同源）。

| # | 规则 | 取值 |
| :--- | :--- | :--- |
| L1 | **底色 = 官方配置**（`--dsw-static-neutral-bluish-00` = `#fff`）—— **三款完全相同、不按本色染** | 见下表 `base` |
| L2 | **左栏填充 = 官方左栏色**（`bluish-50` = `#f9fafb`）—— 同样是官方配置 | 见下表 `sidebarFill` |
| L3 | **`top` / `left` / `bottom` 三层全部来自本色**（α **`.16` / `.19` / `.30`**），打光的方向位置与深色的金光逐字相同 | 见下表 |
| L4 | 颗粒 **`grain: true`**，`.16` / `multiply`（比深色轴 `.13` / `screen` 的质感**弱一档，且这是白底的固有代价** —— 见下） | — |

> **L3 的「比地面亮」是深色轴的判据，不是浅色轴的** —— 浅色轴的本色比白底暗，
> 但**三层都是主色**、纵向有色相渐变，这才是「和深色版相同的渐变质感」。

#### 浅色轴与深色轴**严格镜像**

| 角色 | 深色轴 | 浅色轴 |
| :--- | :--- | :--- |
| **空间** `base` | **官方**近黑（`bluish-950`） | **官方**近白（`bluish-00` = `#fff`） |
| **光源** | **金**（三款共享） | **本色**（三款各用自己的主色） |
| **上光** `top` | **金** @ `.09` | **本色** @ **`.16`** |
| **侧光** `left` | 金 @ `.11` | **本色** @ **`.19`** |
| **底光** `bottom` | 本色 @ `.18` | **本色** @ **`.30`** |
| **收束点** | `62%` | **`62%`**（与深色逐字相同） |
| **颗粒** | `.13` / `screen` | `.16` / `multiply` |

> **三款底色 / 左栏色逐字相同**（都是官方变量）：**空间不随色调变，色调只由打光表达**。
> 三款唯一的差别是 `tint` 与由它派生的三层光（`test/tones.test.mjs` 有一条守「三款 base 逐字相同」）。
> `tint` **只驱动三层光与抬升面染色**，不进底色。

##### 为什么底部必须是本色

判据**不是**「加亮还是压暗」——深色轴的本色比近黑底亮、浅色轴的本色比近白底暗，两轴方向相反；
判据是**有没有色相的纵向渐变**。

| 底部那一层 | 纵向极差（真机实测） |
| :--- | :--- |
| **本色** | **17.5** |
| 银白 | 2.5 |
| 深色参照（本色） | 8.4 |

银白无色相 → 纵向极差只剩 2.5 → 读成纯色。**所以底部必须用本色。**

##### 颗粒为什么要 `.16`（质感 ↔ 亮度的**线性权衡**）

两轴颗粒的**方向相反**：深色轴 `screen` 是**加亮**（白点在暗底上 = 星光），
浅色轴只能 `multiply` 是**压暗**（灰点盖白底）。于是浅色轴的颗粒存在一条**线性权衡**：

| opacity | 整体亮度 | 高频（质感） |
| :--- | :--- | :--- |
| 关 | 246.0 | 0.226 |
| `.28`（质感与深色轴等值） | 236.1 | 3.457 |
| **`.16`（本值）** | **240.1** | **2.129** |

`.28` 能把质感做到与深色轴等值（3.446 ≈ 3.369），但**全屏压暗 ~9 级** ——
那层灰纱正是「不水灵」的来源。

> **为什么停在 `.16`，而不是靠更聪明的噪声两全**：
> 「偏白噪声」（`feComponentTransfer` 把噪声压向白端）的效率只高约 **20%**
> （质感/亮度损失 0.46 vs 0.39），**不值得多引入一张贴图**。
> 根因是物理的：底色已近白，往上只剩几级余量，而**纹理 = 方差** —— 近白面上要出纹理
> **只能往下刻**，刻多深就掉多少亮度。所以**浅色轴的质感注定比深色轴弱一档**，
> 这是近白底的固有代价，不是取值没调好。

##### 顶光的收束点两轴相同（`62%`）

整屏椭圆 `at 50% -10vh` + `ry 45vh`、收在 `62%` → 顶光在 `-81 + 0.62 × 364 ≈ 145px` 归零，
**屏高 18% ~ 84% 是一大片没有任何渐变的死区**，上下两条硬边夹一片平底。

> **是否需要单独推后浅色轴的收束点，取决于那条边看不看得见，而可见度由 alpha 决定。**
> 深色轴 `.09` 看不见边，所以 `62%` 从不出问题；浅色轴 `.16` 与它**同量级**，同样看不见边。
> 只有当浅色轴的光强到 `.55` 那种量级（比深色重一个量级）时，`62%` 才显出一条硬边，
> 那时才需要把收束点推到 `100%` 摊开色量 —— **而且必须同时压 alpha，只推收束点会把「愣」换成「糊」**。
> 现在两轴 alpha 同量级，几何逐字相同即可，那个补丁与它要解决的问题一起消失了。

值由 `tones.ts` 的 `TOP_STOP_BY_SCHEME` 按轴发（**两轴都是 `62%`**）。
`backdrop.ts` 的 `RADIAL_STOP`（`62%`）只作 **CSS 变量的 fallback**，不参与实际取值 ——
变量缺失时退回原值，而不是退成「没有收束点」。

##### 判据：每层用的物理量不同

* 渐变（「不显纯色」）= **纵向极差**（本色 17.5 / 无色相 2.5）—— 色相是必需的。
* 质感（「不显平」）= **高频相邻差**（关颗粒 0.2 / 开颗粒 2.1~3.4）—— 颗粒是必需的。
* 明暗（「是不是光」）= 该层与底色的**亮度差**，且**只在深色轴**成立（浅色轴本色比底暗是正常的）。
* **「主色有没有跑到地面上」= 中段（无光区）的定向通道差 B−R** —— 应 ≈0。

用错量就会看着像在调、实际上调错了旋钮。**主色只应在光里，不进地面。**

#### 用户内容豁免

背景层是**覆盖全屏的 `position: fixed`**，压在**所有内容**之上才给得了「应用底 + 左右栏 + 对话区」着色。
代价是**图片也被染色 + 上颗粒** —— 实测深色轴（`screen` 混合）把一张三色带测试图的红通道
**92 → 131**，图像被洗白。

**修法：把「对话内容」整体抬到背景层之上。**

```css
body:not([data-dsh-theme-tone-plain]) [data-conversation-scroll] { position: relative; z-index: 81 }
body:not([data-dsh-theme-tone-plain]) [data-sidebar-right-panel],
body:not([data-dsh-theme-tone-plain]) [data-shell-overlay],
body:not([data-dsh-theme-tone-plain]) [data-sidebar-right-float-host] { z-index: 82 }
body:not([data-dsh-theme-tone-plain]) [data-dockkit-tab-menu] { z-index: 83 }
```

三个关键判断，都是实测出来的：

* **抬整个容器，不抬单个 `img`** —— 抬 `img` 也能免疫（实测 Δ=(0,0,0)），但 `img` 会同时高过
  **没有 z-index 的输入框**，于是图片滚动时**浮在输入框上**。而输入框**就在同一个滚动容器里**
  （`composerSeat > scrollBody[data-conversation-scroll]`），**整体抬升**既解决图片，
  又天然保住容器内的前后序。实测输入框中心色 Δ=(0,0,0)。
* **背景色不受影响** —— 对话区底色**不是**这个容器画的，而是它的祖先 `root`
  （`position: relative; z-index: auto`）画的；那一层仍在背景层之下，**照常着色**。
  观感因此是：**背景照常有色调与颗粒，内容（正文 / 图片 / 输入框）干净。**
* **输入框一起被豁免是「有意为之」，不是副作用** —— 输入框是**注视焦点**，被环境色 + 颗粒压着会干扰输入。
  它自身的**玻璃效果与 token 着色照旧**（见 [04-glass.md](04-glass.md)），只是不再吃背景层那一层。
  ⚠️ **别把它「修」回去** —— 这条是设计意图。
* **用稳定属性，不用哈希类名** —— `data-conversation-scroll` / `data-sidebar-right-panel` /
  `data-shell-overlay` / `data-dockkit-tab-menu` 都是官方挂的语义属性
  （仓库规矩也禁止依赖 CSS-module 哈希类名）。

#### ⚠️ 抬内容带来的**不变式**：凡压在内容之上的官方层都要跟着抬

这是这条修法**必然**的代价，不是意外。内容层是**正 z-index 的定位元素**
（CSS 绘制顺序 Appendix E 第 7 步），它会盖掉一切 **z-index 更小**的层 —— 包括官方那些
本来压在内容之上的 chrome：

> **凡 z-index < 81 且要压在内容之上的官方层，都必须抬到 82（`ABOVE_CONTENT_Z_INDEX`）。**

| 官方层 | 原 z-index | 状态 |
| :--- | :--- | :--- |

**抬的时候必须保住官方的相对次序**：`floatHost 60 < tabMenu 70` 是官方注释里写明的意图
（「a menu opened from a tab must never sit under a panel」），所以两档要**一起抬**
（82 / 83），不能都塞进 82 —— 同号时靠 DOM 次序决胜，那是碰运气。

**新增官方浮层时按这张表核对** —— 官方加一个 z-index 在 1–80 的浮层，就会被内容盖住。
这是「抬内容」方案与生俱来的维护面，**要一直记账**。

##### 第二条代价：抬上去的 chrome **吃不到那层光**，得自己画

> 背景层（z-index 80）本来压在顶栏之上，**顶光其实是直接盖在顶栏上的**。
> 顶栏为了不被内容盖住抬到 82，就再也吃不到那层光了 —— **它必须自己画一遍**。

修法：顶栏同时输出**玻璃填充**（`background-color`）与**背景层同一串渐变**
（`background-image: BACKDROP_GRADIENTS`，与背景层**同源**，不复制粘贴），
并加 **`background-attachment: fixed`** —— 顶栏只有 76px 高，同一串 `ellipse 80vw 45vh`
若按**自身盒子**解析会重新缩放成一条硬边带（`surface.ts` 记过这个坑）；
`fixed` 让百分比按**视口**解析，于是两处渐变**逐像素对齐**。

> **判据（可推广）**：任何被抬到背景层之上的 chrome，只要它是**半透明**的，
> 就会丢掉那层环境光 —— 不透明的（右栏面板 / 外壳浮层 / dockkit 菜单，走 token 实色）不受影响。

**验收方式（差分法，自证）**：同一位置连拍两张 —— 覆盖层开 / 关，逐像素求差。

| 区域 | 实测差异 | 判读 |
| :--- | :--- | :--- |
| 图片区 | **0** | 完全免疫 ✓ |
| 背景区（对照组） | **11.46** | 开关确实起作用 → 上一个 0 可信 |

> **为什么要设对照组**：只看「图片区差异=0」无法区分「修好了」和「图片根本没加载 / 页面是死的」。
> 背景区必须同时有差异，这个 0 才是证据。

三层光**全部来自本色** —— 所以三款的光色**各不相同**（那是「用主色打光」的必然结果）。
α 三档由 `LIGHT_GLOW_ALPHA`（**`.16` / `.19`**）与 `DEPTH_ALPHA.light`（**`.30`**）给。

**三层光的强度次序 `top < left < bottom`（两轴一致，这是「光从左上来」的几何含义）**：
`left` 的 α 略高于 `top`，因为它铺在**大面积的左栏**上，同 α 会显得更浓；
`bottom` 是纵深 / 焦散，最强。（`test/surfaces.test.mjs` 有次序守卫。）

**为什么浅色的 alpha 约为深色的 1.8 倍（物理约束，不是口味）**：
白底对浅色主色的**通道余量只有深底对金的一半** ——
深底 `#0a0a10` → 金 `232,162,74` 的 R 差 **222**；白底 `#fff` → 霜蓝 `145,215,235` 的 R 差只有 **110**。
逐字照抄 `.09/.11/.18` 实测顶光主色只有 **1.49**（明显偏弱），本档 **2.39**。

#### 樱花：本色色度为什么取到 50

本色在实况里只以 **`.16 ~ .30` 的 alpha** 出现，叠在官方白底上后**色度被压掉约 3 倍** ——
色度给低了根本读不出来：旧款本色色度只有 8，压完只剩 2，实测中段 R−B ≈ 0.1，就是一个中性灰。

**取 50 是为了与另两款的音量对齐**（绿 50 / 蓝 90），压完得 6.3 ≈ 绿款的 5.8；
本款顶光 R−B 实测 **1.4**。本款也是色序里与深色轴 `crimson`（余烬，红）**逐位对应**的一档，
必须是**暖**色（两轴这一位都是暖色，有测试钉住逐位对齐 `test/tones.test.mjs`）。

⚠️ **改 id 的代价**：`toneFor` / `toneIdOf` 对脏值（不属于该轴、或已不可用）**静默回落到该轴默认**、
不崩 —— 所以旧 id 会失效并回落。**若插件已发布，这种改名需要写迁移**（把旧 id 映射到新 id），
不能只改常量。

⚠️ 英文名 `Sakura` 是 **6 字母**，是「英文标签 4–5 字母」那条节奏守卫的**唯一例外**。
测试的上限已相应放宽到 6 并注明原因（`test/tones.test.mjs`）；若要严格回 5 字母，替代是 `Petal`。

## 5) 命名规划

命名走**意境名**，颜色由卡面表达。暗色轴偏「一片空间 + 一束光」的景观，浅色轴偏「一种材质表面」。

| 轴 | id | zh | en | 命名的意思 |
| :--- | :--- | :--- | :--- | :--- |
| 深 | `official` | 默认 | Default | 功能性选项（不参与下面的节奏规则） |
| 深 | `violet` | 深空 | **Space** | 蓝紫近黑 + 金色月食光，pyai.site 原款 |
| 深 | `crimson` | 余烬 | Ember | 暗红空间里的金色余温 |
| 深 | `forest` | 幽林 | Glade | 深绿空间，同一束金光的另一种落点 |
| 浅 | `blue` | 霜蓝 | Frost | 冷调晨霜 |
| 浅 | `sakura` | 樱花 | Sakura | 暖粉的打光 |
| 浅 | `green` | 苔青 | Moss | 湿润苔色 |

* **顺序 = 渲染顺序，且两轴逐位对应**：

  | 位 | 深色轴 | 浅色轴 |
  | :--- | :--- | :--- |
  | 1 | `violet` 深空（蓝紫） | `blue` 霜蓝 |
  | 2 | `crimson` 余烬（红） | `sakura` 樱花（粉）—— **两轴这一位都是暖色** |
  | 3 | `forest` 幽林（绿） | `green` 苔青 |

  顺序由 `DARK_TONE_IDS` / `LIGHT_TONE_IDS` 的插入顺序决定（`toneIdsFor` 直接返回），
  `test/tones.test.mjs` 同时钉住逐位对应与具体数组。

* **文档里的「官方默认」与卡面文字「默认」不是一回事**：前者指 `official` 这一**档**代表的语义
  （= 官方原值、不装插件的样子），后者是它印在卡上的两个字。卡面只印「默认」—— 四个字在一排
  两字标签里会把整行节奏带歪。**改动只动 locale，正文里的「官方默认」作为概念继续用。**
* `深空` / `余烬` / `幽林` 是**同一族**（都指「一片空间 + 一束光」），`樱花` / `霜蓝` / `苔青` 是另一族（都指**一种自然物**：樱、霜、苔）—— 两族各自内部一致，与「暗色轴是景观、浅色轴是材质」的区分对齐。
* **中文标签一律两个字**（默认 / 深空 / 余烬 / 幽林 / 樱花 / 霜蓝 / 苔青）；**英文标签一律单个单词**，多数落在**4–5 字母**（`Sakura` 是 6 字母的例外）（`Space` / `Ember` / `Glade` / `Frost` / `Moss`）—— 整排卡的文字节奏才一致。两条都由 `test/tones.test.mjs` 钉住（`Default` 作为功能性选项豁免英文长度规则，中文那条**不豁免**）。
* **保真优先于节奏**：「深空」在英文里没有一个恰好对应的单词 —— 取 `Space`（deep **space** 的核心词；丢掉的 "deep" 本来由卡面自己表达）。`Deep space` 双词破坏节奏、`Void`（虚空）语义偏离，都不取。**别为了凑 4–5 字母去挑语义不贴的词。**
* 备选（若不满意可换）：`violet` en → `Deepspace`（唯一把「深」也带上的单字写法，9 字母、节奏会破）；`crimson` → 赤霞 / 暗烬；`forest` → 苍林 / 松墨；`green` → 新苔 / 竹青。

## 6) 待定与待复核

**待真机复核**：

1. **深色卡是否够分辨 / 够质感**：共享光 **不放大**（×1，与实况 1:1）、各款纵深 **×3**，卡面补上 stardust 颗粒。
   * **三张还分不出** → `PREVIEW_ALPHA_SCALE.dark.depth` 提到 `4`
   * **卡面又偏过** → `depth` 降到 `2`
   * **颗粒太重 / 发脏** → 卡面颗粒单独降 `opacity`（实况那层不动）
2. **浅色轴的窗口** —— 当前是「官方底色 + 主色打光（几何同深色金光）+ 颗粒 `.16`」。
   下面几条是日后若要再调的旋钮：
   * **质感不够 / 像纯色** → 量**纵向极差**与**高频相邻差**（应 ≈2.1）。前者低说明
     底部那层丢了色相（检查 `bottom` 是否还在用本色）；后者低说明颗粒被关了
   * **嫌颗粒重 / 不够水灵** → `GRAIN_OPACITY_LIGHT` `.16` → `.12`（一次一格，约 +1.5 亮度 / −0.5 质感）
   * **嫌主色在光带上太重** → `LIGHT_GLOW_ALPHA` 的 `top` / `left` 与 `DEPTH_ALPHA.light`
     **三层一起**收一格（现 **`.16` / `.19` / `.30`**）。**别只收一层** —— 底部是纵深、最强，
     只收顶/侧会让「光从左上来」的几何关系歪掉（`test/surfaces.test.mjs` 有次序守卫）
   * **嫌主色跑到地面上了** → 量**中段（无光区）的定向通道差**（如蓝的 `B−R`），应 **≈0**。
     若明显大于 0，说明有人把本色染进了 `base` —— **主色应当只在光里**，退回官方底色
   * **想让主色更浅（水灵）** → 抬 `tint` 的 L（`.05` 一格），**同时把 S 补上去保住 RGB 色度**；
     注意 `maxChroma(L) = (1-|2L-1|)×255` —— L 越高能保的色度越低
   * **三款还是分不出** → 提 `SURFACE_TINT.light`（`.14` → `.18`，一次一格），
     或把三层光的 alpha 提一档（注意白底余量只有深色底对金的一半）
   * **弹层显得比内容底暗太多** → `SURFACE_TINT.light` 回收一档（`.14` → `.11`），
     代价是三款在弹层上的区分度同步下降（实测 Δ 从 11.0 降到约 9.4）
3. **浅色轴 `left` 层是否显得脏**：真机上若不好看就把 `LIGHT_GLOW_ALPHA.left` 收一档或退回两层（`left: ''`）。**改用本色后此风险已大幅降低**（不再引入外来色相）。
4. **红/绿的音量**：现为跨度 `5` + crimson 底部 S≈.43（中间档）。真机上若还偏响 → 降到 `4`；若又显得不够 → `6`（与 violet 等响）。**跨度是一个整数，改一个数字即可**，测试会自动守住「三通道和 36」这条不变式。

> **若日后要改「各自光源」**（深色轴不再共享金）：`crimson` 的 `top`/`left` 换暖橙
> `rgba(226, 116, 80, ·)`、`forest` 换苔绿光 `rgba(150, 196, 110, ·)`，其余不变。

## 7) 逐款验收

* 8 款色调下 `--dsw-alias-label-primary` / 二级 / 三级文字、链接、错误/成功/警告色在各自底上可读（目视）。暗色三款因底色亮度严格相等，这一项理论上三款同时过或同时不过。
* 色调卡并排时能一眼看出区别（卡面按 `PREVIEW_ALPHA_SCALE` 放大后）；暗色三款的**金色光源位置与强度一致**，只有空间色不同；浅色三款的**主色光与颗粒也按同一套几何**，三款差异来自主色本身。
* **浅色三款的底色应当完全相同**（都是官方白）—— 这是「色调只由打光表达」的可测判据
  （`test/tones.test.mjs` 有一条守「三款 base 逐字相同」）。
* **浅色轴的中段（无光区）应当没有主色**（可测：定向通道差 ≈0；主色若铺满整屏会升到 4.9 量级）。
* **浅色轴的质感弱深色轴一档是已知且接受的**（可测：浅色高频 ≈2.1、深色 ≈3.4）—— 白底上
  纹理只能往下刻，刻多深就掉多少亮度。
* **浅色轴的纵向必须有色相渐变**（可测：纵向极差非 0）—— 这是「不读成纯色」的判据。
  具体幅度随 alpha 档变化（现档实测约 −7 ~ −9），不必钉死数值，**不可为零**才是要点。
* 「官方默认」与停用插件时逐像素一致（真机实测：背景层 `display: none`，`base`/`layer*` 全部回到官方字面量 `#fff` / `#f9fafb`）。
