# 04 — 图片被上游丢弃：连续 user 消息合并

> 状态：已实现（2026-09-08）。owner 实测反馈：CodeBuddy 的 DS 模型「检测到支持图片，但模型回复说不能读图」。
> 全部结论来自**真实请求对照实测**（非推测），对照数据见文末。

## 现象

会话用 `codebuddy-credits/deepseek-v4-flash`（`/v3/config` 的 `supportsImages: true`，
插件据此声明 `inputModalities: ['text','image']`），贴图提问后模型回答：

> 当前会话模型（deepseek-v4-flash）不支持图片输入——你贴的这张图在送达时已被系统过滤

即：能力声明正确、图片也确实进了会话，但模型看不到。

## 定位过程（每一步都是真实请求）

用插件**自己的编译产物**（`lib/adapter.js`）直连 CodeBuddy，逐步逼近：

| 用例 | 请求形状 | 结果 |
| :--- | :--- | :--- |
| 基线 | 单条 user（文本 + 图片） | ✅ 正确描述图片 |
| A/B | 真实 system + 28 工具 + 全部历史 | ❌ 模型称图片被过滤 |
| 1–6 | 真实 system 或 28 工具（单独）+ 图片 | ✅ 读到图 |
| F/G/H/I | 图片消息 + 任意**第二条** user 消息 | ❌ 被丢弃 |
| **J** | `[其它消息, 图片]`（图片在最后） | ✅ 读到图 |
| **K** | `[图片, 普通文本]`（图片不在最后） | ❌ 被丢弃 |
| **L** | 真实 system + 28 工具 + `[其它消息, 图片]` | ✅ 读到图 |

结论：**上游网关只认最后一条 user 消息里的图片**；更早消息中的图片被静默丢弃，
并注入「当前模型不支持图片」的提醒（模型转述为用户看到的那句话）。system 提示、
工具、思考档位、历史长度都与触发无关。

## 根因

DSH 会把工作区指令、运行时上下文、技能目录等**以 user 消息追加在真实用户消息之后**
（本机会话日志实测 seq 10 = 用户「图片 + 这是啥？」，seq 11/12/13 = AGENTS.md、
runtime context、技能目录）。于是带图的那条 user 消息**永远不是最后一条**，
上游必然丢弃图片——与模型能力无关。

## 设计

`toWireMessages` 把**连续的 user 消息合并为一条**（内容块按原顺序拼接）：

```
[user(图片 + "这是啥？"), user(AGENTS.md), user(runtime), user(技能目录)]
   → [user(图片 + "这是啥？" + AGENTS.md + runtime + 技能目录)]   ← 图片落在最后一条 user 里
```

- 合并范围仅限「映射为 wire role=user 且非工具结果」的相邻消息；
  `tool` 消息（工具结果）不参与合并，`user → tool → user` 的交替结构保持不变；
- 被 assistant 消息隔开的 user 消息不合并（多轮结构不变）；
- 内容顺序完全保持（拼接顺序 = 原消息顺序），不改写任何文本。

## 已知上游限制（无法在插件侧消除）

图片只被「最后一条 user 消息」识别，因此**多轮对话里更早轮次的图片，上游会丢弃**
（例如第 1 轮贴图、第 3 轮追问图片细节时）。要重新引用需重新贴图，
或改用原生视觉路由（`deepseek-v4-pro` 同样受此规则约束——它是同一条网关路径）。

## 涉及文件

- `src/adapter.ts`：`toWireMessages` 连续 user 消息合并。
- `test/adapter.test.mjs`：合并顺序、图片落到最后、工具消息不合并、assistant 隔开不合并。

## 验证

- `npm run verify` 全绿（72 tests）。
- 真实请求重放失败会话（真实 system + 4 条用户消息，修复后合并）：
  模型直接描述图片内容（「DeepSeek 图标 / 吉祥物」），不再称看不到图。
- 无工具变体与带工具变体均不再出现「图片被过滤」表述。

## 风险

- 合并改变 wire 消息边界（内容不变）。OpenAI 兼容端普遍不接受相邻同角色消息，
  合并是常见归一化；如上游未来支持多条 user 消息中的图片，本改动仍无害。
- 合并后单条消息更长，可能影响上游侧前缀缓存命中粒度（未观测到问题）。
